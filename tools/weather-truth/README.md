# 날씨 자 (weather-truth)

셰이더 자들이 **화면 픽셀**을 재듯, 여기 자들은 **앱이 받아오는 예보 자체**를 잽니다.
"흐린 날은 거의 못 맞춘다" 는 말이 렌더링 탓인지 입력 자료 탓인지 갈라야 했기
때문입니다.

모두 네트워크를 씁니다(Open-Meteo). 인자 없이 실행하면 됩니다.

## verify-grid-spacing.js

`src/utils/cloudGrid.ts` 의 **진짜 팬**(방위 ±30° 7줄기 × 거리 10~380km 10링
= 70점)을 그대로 던지고, Open-Meteo 가 응답에 돌려주는 격자점 좌표를 세서
**요청 70점이 실제 격자 몇 칸으로 뭉치는지** 잽니다.

```
node tools/weather-truth/verify-grid-spacing.js [모델명]
```

읽는 법: "뭉침배수" 가 1.0 에 가까우면 팬이 격자보다 성겨서 정보를 잃지 않고
있다는 뜻입니다. 2 배가 넘어가면 그 지역에서는 팬을 좁혀도 새 정보가 없습니다.

## verify-lead-time.js

예보를 **며칠 전에** 봤을 때 얼마나 맞나 — 여행 계획용(§98).

```
node tools/weather-truth/verify-lead-time.js [일수, 기본 30] [모델들]
```

아래 `verify-cloud-forecast.js` 는 그날 가장 최근 실행(선행 0~24시간)만 봅니다. 이것은 이전 실행
API 의 `cloud_cover_previous_dayN`(N일 전 실행이 그 시각에 내놓았던 값)을 **같은 위성 τ 자**로
잽니다. 선행 0~3일별 τ 오차, "맑음(τ≥0.7)/아님" 맞힘률, 짙은 흐림 편향, 장소별 오차, 앱 두 모델이
갈리는 폭과 오차의 관계를 찍습니다. 판정이 아니라 재는 자라, 종료 코드는 자료를 못 받았을 때만
1 입니다. 못 재는 것은 아래 `verify-cloud-forecast.js` 와 같습니다(낮만, 미 대륙 없음).

## measure-bias-distance.js

위성 보정(`satelliteBias.ts`)은 **관측점 1점**에서 편향을 냅니다. 그 편향을 해 경로의 먼 점과
**층**에 어떻게 나눌지를 잽니다(2026-10-02 후쿠이 사례, `docs/SKY_REBUILD_PLAN.md` §121).

```
node tools/shader-preview/stage-esm.js
node tools/weather-truth/measure-bias-distance.js [일수, 기본 30] [끝날짜, 기본 어제]
WEATHER_TRUTH_CACHE=<디렉터리> node …   # 응답을 디스크에 둡니다
```

12곳 × 30일. 관측점의 편향을 **앱의 `estimateBias` 그대로** 내고, 서·동 25/50/100/200/400km 점에
앞선 0~3시간으로 걸어 **그 점의 위성 τ** 로 채점합니다(위 자와 같은 규약, 배율은 점마다). 층은
위성이 못 가리므로 앱이 **그리는 세 층을 겹친 기둥**(무작위 겹침)의 τ 로 봅니다. 판정과 측정
문턱은 머리말에 재기 전에 박아 두었고(D1~D4, A1~A4), 끝에 앱의 `correctCloudAt` 이 자가 잰 식과
같은지도 견줍니다. 판정이 아니라 재는 자라, 종료 코드는 자료를 못 받았을 때만 1 입니다.

## verify-cloud-forecast.js

예보 운량을 **위성이 실제로 본 하늘**과 견줍니다.

```
node tools/weather-truth/verify-cloud-forecast.js [일수, 기본 30]
```

- 관측: `satellite_radiation_seamless` 의 시간별 일사량.
- 맑은하늘 기준: Haurwitz `1098·cosZ·exp(-0.059/cosZ)`.
- 투과율 `τ = 관측 / 맑은하늘`. 1 이 맑음, 완전 흐림이 0.25 근처.
- 모델 운량도 같은 식(`τ = 1 - 0.75·(N/8)^3.4`)으로 τ 로 바꿔 **τ 끼리** 뺍니다.

### 왜 운량(%)이 아니라 τ 로 견주나 — 1판의 실패

처음에는 위성 τ 를 Kasten-Czeplak 로 되돌려 **운량 %** 로 견줬습니다. 그 식은
지수가 3.4 라 맑은 쪽에서 거의 수직입니다. τ 0.95 → 운량 45%, τ 0.90 → 55%.
일사 5% 오차가 운량 45%p 오차가 되니, 그때 나온 "모델 평균오차 30~37%p" 의
상당 부분은 **모델이 아니라 자 자신의 잡음**이었습니다. 그래서 잘 조건화된
τ 공간에서 견주도록 고쳤습니다. 앱이 실제로 그리는 것(하늘이 얼마나
어두워지나)에도 τ 쪽이 가깝습니다.

### 맑은하늘 배율 (지역 보정)

Haurwitz 는 연무·수증기를 무시해서 지역마다 몇 % 씩 어긋납니다. 서울의 맑은
하늘은 시드니보다 실제로 16% 덜 통과시킵니다. 그래서 **네 모델이 모두 맑다
(≤20%)고 한 시각**의 τ 평균을 그 지역의 배율로 삼습니다. 모델은 여기서 눈금의
크기만 정하고 변동은 정하지 않습니다. 30일 내내 그런 시각이 8개도 안 되는
곳(장마·우기)은 τ 상위 5% 를 대신 쓰고, 표에 `상위5%` 라고 밝힙니다.

### 못 재는 것 — 반드시 같이 읽을 것

- **미 대륙은 못 잽니다.** 위성이 MSG(0°)+IODC(45.5°E)+Himawari(140°E) 뿐이라
  서반구 경도는 전부 `latitude: nan` 을 돌려줍니다. 원반 가장자리(경도 -60°
  부근 등)도 못 믿습니다.
- **낮에만 잽니다.** 태양고도 15° 미만은 버립니다. 즉 **일몰 순간 자체는 이
  자로 검증되지 않았습니다.** 앱이 가장 신경 쓰는 시각이 사각지대입니다.
- **얇은 상층운은 거의 안 가려서 과소평가됩니다.** 이 자가 재는 것은
  "하늘을 **가리는** 구름" 이지 "하늘에 **있는** 구름" 이 아닙니다.
- 층별(low/mid/high) 운량은 검증하지 않습니다. 위성 일사는 기둥 전체의 합입니다.
