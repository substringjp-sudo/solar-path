# 정적 슬롯 계획 — "계산 끝내고 렌더링만"의 마지막 조각

지금 타임라인은 **하늘 기둥**(방향별 운량·층별 광학)까지만 미리 계산합니다.
빌보드는 여전히 매 갱신마다 다시 **고르고 배치**합니다. 이 문서는 그 마지막
단계를 없애는 계획입니다.

---

## 1. 지금 남아 있는 매 갱신 작업

`buildCloudsFromColumns` 안에서 벌어지는 일:

| 단계 | 왜 매번 하나 | 비용 |
|---|---|---|
| 방향 필터 + 층별 정렬 | 운량이 바뀌면 순위가 바뀜 | O(n log n), n=576 |
| 해시 게이트 (`seed2 > 0.12 + cover*0.95`) | 운량에 의존 | O(n) |
| 운형 판정 | 운량·강수에 의존 | O(n) |
| 아틀라스 조각 선택 | 운형에 의존 | O(n) |
| `skyRadiance` × 빌보드 수 | 태양 위치에 의존 | 1.8µs × N |
| 인스턴스 행렬 계산 | 방향에 의존 (**사실은 안 바뀜**) | O(N) |

마지막 줄이 핵심입니다. **방향은 절대 안 바뀝니다.** 격자가 고정이니까요.
그런데 매번 다시 계산하고 GPU에 다시 올립니다.

---

## 2. 목표 상태

방향마다 **영구 슬롯**을 하나씩 줍니다. 운량은 존재 여부가 아니라 **불투명도**를
결정합니다.

```
슬롯 i  ↔  (층, 방위, 고도)   — 영구 고정
  instanceMatrix   : 한 번 계산하고 끝  ← GPU 업로드 0
  aUvRect(운형)     : 키프레임마다 저장
  aOptics.x(불투명) : 키프레임마다 저장 → 보간
  aBeam / aAmbient  : 키프레임마다 저장 → 보간
```

렌더 경로가 **"두 키프레임 attribute를 lerp해서 업로드"** 하나로 줄어듭니다.
정렬도, 해시도, 운형 판정도, `skyRadiance`도 없습니다.

---

## 3. 넘어야 할 문제 — 불연속

### 3-A. 운형과 아틀라스 조각

`aUvRect`는 보간하면 안 됩니다. 아틀라스의 다른 조각 사이를 lerp하면
두 그림이 뭉개진 UV가 나옵니다.

**해법: 슬롯당 운형을 하루 단위로 고정한다.**

사전 계산 때 각 방향의 **하루 최빈 운형**을 구해 슬롯에 박습니다. 시간에 따라
바뀌는 것은 불투명도뿐입니다. 실제로도 한 방향의 구름이 하루 사이 권운→적란운으로
바뀌는 일은 드물고, 바뀔 만큼 큰 변화라면 운량도 함께 크게 움직여서 불투명도로
표현됩니다.

*대안(더 정확하지만 비쌈)*: 슬롯을 운형별로 2개씩 두고 크로스페이드.
메모리 2배. 1단계에서는 하지 않습니다.

### 3-B. 해시 게이트

`seed2 > 0.12 + cover*0.95`는 이진 게이트입니다. 이걸 **불투명도 램프**로
바꿉니다:

```
opacity = smoothstep(seed2 - 0.12, seed2 + 0.12, cover) * presetOpacity
```

같은 통계(운량이 낮으면 듬성듬성)를 주면서 연속입니다. **이게 3번 불만의
"틈새" 완화에도 직접 기여합니다** — 지금은 게이트에 걸린 방향이 그냥 빈 하늘이지만,
램프면 옅게라도 채워집니다.

### 3-C. 슬롯 수 = 576 > 현재 예산 160

전부 그리면 오버드로가 늘어 3번 불만이 되살아납니다.

**해법: 그리기 직전에 압축(compaction).**
불투명도가 임계 아래인 슬롯은 인스턴스 버퍼에서 건너뛰고, 보이는 것만 앞으로
모아 `mesh.count`를 그 수로 둡니다. 정렬이 아니라 **한 번의 선형 스캔**이라
O(n)이고 순서가 바뀌어도 상관없습니다(빌보드는 서로 정렬 무관).

덱 밀폐(§9-C의 `deckSeals`)도 그대로 적용되므로, 8/8에서는 여전히 0장입니다.

## 4. 메모리

슬롯당 키프레임에 저장할 값:

| 항목 | float |
|---|---|
| 불투명도 | 1 |
| τ | 1 |
| beam RGB | 3 |
| ambient RGB | 3 |
| **합계** | **8** |

576 슬롯 × 8 × 4B = 18KB/키프레임. 289 키프레임이면 **5.3MB**.

지금 타임라인(0.64MB)보다 8배지만 절대량은 감당 가능합니다. 줄이는 수단:
- beam/ambient를 half float으로 → 2.7MB
- 색은 태양 위치의 매끄러운 함수이므로 **키프레임을 더 성기게**(15분) 잡아도 됨 → 1.8MB
- 운량만 저장하고 색은 렌더 시 계산 (지금 방식) → 0.64MB, 대신 `skyRadiance` 유지

**권장: 색까지 저장하되 색 전용 키프레임을 15분 간격으로 따로 둡니다.**
운량은 5분, 색은 15분 — 둘 다 매끄럽지만 변화 속도가 다릅니다.

## 5. 단계

| 단계 | 내용 | 검증 |
|---|---|---|
| **1** | 해시 게이트 → 불투명도 램프. 기존 경로 그대로. | 운량별 평균 불투명도가 게이트 시절 채택률과 일치하는가 |
| **2** | 인스턴스 행렬을 슬롯 고정으로. `instanceMatrix.needsUpdate`를 최초 1회만. | 렌더 결과 픽셀 동일 |
| **3** | 압축 패스 + `mesh.count`. | 8/8에서 0장, 3/8에서 기존과 비슷한 수 |
| **4** | 슬롯당 하루 최빈 운형 고정. | 하루를 훑어 운형이 바뀌는 슬롯 비율 측정 (10% 미만이어야) |
| **5** | 키프레임에 슬롯 attribute 저장 + lerp. | 키프레임 시각에서 직접 계산과 픽셀 일치 |
| **6** | `buildCloudsFromColumns` 호출 제거, 순수 업로드로. | 프레임당 JS 시간 측정 |

각 단계가 **독립적으로 배포 가능**하고, 1~3은 지금 구조에서 바로 이득입니다.
5~6이 실제 "렌더링만" 상태입니다.

---

## 6. 예상 효과

| | 지금 | 6단계 후 |
|---|---|---|
| 갱신당 JS | fBm 없음, 정렬+판정+skyRadiance ≈ 2ms(모바일 추정) | attribute lerp만 ≈ 0.3ms |
| 갱신 빈도 제약 | 씬 시각 0.5분 / 태양 1° 스로틀 | 매 프레임 가능 |
| 시간 스크럽 | 계단식 갱신 | 연속 |
| 인스턴스 행렬 업로드 | 매 갱신 | 없음 |

**스로틀을 없앨 수 있다는 게 실질적으로 가장 큽니다.** 지금은 스크럽할 때
구름이 0.5분 단위로 튀는데, 그게 "부드럽지 않다"의 상당 부분입니다.

---

## 7. 안 할 것

- **슬롯을 운형별로 중복 배치**(3-A 대안). 메모리 2배에 비해 얻는 게 적습니다.
- **덱까지 정적화.** 덱은 이미 정점 attribute 하나(`aCover`)만 올리므로
  더 줄일 게 없습니다.
- **색을 텍스처로 굽기.** 픽셀이 아니라 파라미터를 저장한다는 원칙
  (`docs/SKY_TIMELINE.md`)을 깨지 않습니다.
