# 흐린 날 렌더링 설계 (Overcast Rendering Design)

3D 시뮬레이션이 어떤 기상 조건에서도 "듬성듬성한 맑은 날"로 보이는 문제의 원인 분석과
해결 설계입니다. `docs/CLOUD_PHYSICS.md`(광학 공식)의 후속 문서로, 이쪽은 **배치와 계층**을 다룹니다.

> **상태: 0~7단계 전부 구현 완료.**
> 아래 진단은 구현 전 코드 기준으로 남겨둡니다 — 무엇이 왜 틀렸는지가
> 지금 구조의 근거이기 때문입니다. 구현 중 추가로 발견한 것은 §6에 적었습니다.

---

## 1. 진단

증상은 네 가지인데, 원인은 서로 독립적입니다. 하나만 고쳐서는 흐린 날이 나오지 않습니다.

### 1-A. 하늘의 77%가 격자 29칸 중 **1칸**으로 그려지고 있습니다

`cloudPlacement.ts`가 구름의 고도각을 이렇게 정합니다.

```ts
const elevationDeg = Math.max(2.0, Math.atan2(altKm, Math.max(0.5, distanceKm)) * (180 / Math.PI));
```

`cloudMatrix.ts`의 29점 격자는 거리 **0 / 50 / 100 / 200 km** 동심원입니다.
각 링에서 실제로 나오는 고도각을 계산하면:

| 링 | 셀 수 | 권운(11.5km) | 고층운(4.2km) | 적운(1.6km) |
|---|---|---|---|---|
| 0 km (→2km로 클램프) | 1 | **80.1°** | **64.5°** | **38.7°** |
| 50 km | 4 | 13.0° | 4.8° | 2.0°* |
| 100 km | 8 | 6.6° | 2.4° | 2.0°* |
| 200 km | 16 | 3.3° | 2.0°* | 2.0°* |

\* 하한 클램프에 걸림

**29칸 중 28칸이 고도각 13° 이하에 몰립니다.** 그런데 고도각 13° 위쪽은
입체각으로 전체 하늘의 `2π(1−sin13°)/2π = 77.5%`입니다.

즉 하늘의 3/4을 격자 한 칸(중심 셀)이 담당하고, 그 한 칸이 내놓는 빌보드는
`round(cloudCover × 4)` — 최대 4개뿐입니다. 고개를 들면 언제나 비어 있습니다.

**근본 원인은 좌표계 혼동입니다.** 29점 격자는 200km 반경을 내려다보는 *평면도(map)* 격자인데,
이걸 *하늘(dome)* 격자로 그대로 썼습니다. 둘은 다른 공간입니다.
고도 `h`인 구름층을 고도각 `ε`로 볼 때 그 구름의 지상 투영 거리는 `d = h / tan ε` 이므로:

| 고도각 | 저층운 h=1.5km | 상층운 h=10km |
|---|---|---|
| 45° | 1.5 km | 10 km |
| 20° | 4.1 km | 27 km |
| 10° | 8.5 km | 57 km |
| 5° | 17 km | 114 km |
| 2° | 43 km | 286 km |

저층 구름층이 하늘에서 차지하는 영역은 **전부 반경 43km 안**입니다.
50/100/200km 링은 저층운에 대해서는 전부 지평선 연무대(2°)로 눌립니다.

### 1-B. 실제 기상 데이터가 구름에 **전혀** 연결되어 있지 않습니다

`computeCloudCellData()`는 이름과 달리 기상값을 받지 않습니다.

```ts
const seed = Math.abs(Math.sin(lat * 12.9898 + lon * 78.233 + (bearingDeg + 1) * 37.71 + minutesOffset * 0.1));
const cloudCover = Math.min(1, Math.max(0.1, (seed * 1.3) % 1.0));
```

운량도 운형도 위경도 해시입니다. 그래서 **흐린 날과 맑은 날의 3D 화면이 같습니다.**
같은 좌표면 API가 100% 흐림을 주든 0%를 주든 결과가 동일합니다.

게다가 `Sim3DContainer.tsx`는 아예 빈 배열을 넘깁니다.

```tsx
prediction={null}
interpolatedWeather={[]}
```

정작 실제 데이터는 이미 받아오고 있습니다 — `CloudData`에 `low/mid/high`(%),
`visibility`, `humidity`, `precipitation`, `totalColumnWaterVapour`,
그리고 **`directNormalIrradiance`(DNI)** 까지 있습니다. 쓰지 않고 있을 뿐입니다.

### 1-C. 운량이 **면적**이 아니라 **알파**로 들어갑니다

```ts
const opacity = clamp01(opticsConfig.opacity * (0.6 + cell.cloudCover * 0.45));
const count   = Math.max(1, Math.round(cell.cloudCover * maxPerCell));  // maxPerCell = 4
```

운량이 오르면 빌보드가 **반투명하게 진해질** 뿐, 하늘을 덮지 않습니다.
운량 100%의 물리적 의미는 "하늘이 빈틈없이 가려짐"인데 지금은 "구름 4개가 좀 더 불투명함"입니다.
`maxPerCell = 4`라는 상한 때문에 8/8 하늘도 구조적으로 만들 수 없습니다.

또한 빌보드는 개별 스프라이트라서, 아무리 많이 뿌려도 **경계가 보이는 조각들**이지
이어진 구름층이 되지 않습니다.

### 1-D. 태양·하늘·구름이 서로의 존재를 모릅니다

- **하늘**: `Skydome`의 uniform은 `uSunDir, uSunAltDeg, uBeta, uAngstrom, uElevScale, uOzoneDU, uSaturation` — 구름 입력이 없습니다. 8/8 흐림에도 스카이돔은 맑은 하늘색을 칠합니다.
- **태양**: `SunMesh`는 `renderOrder = 5`, `depthWrite: false`. 구름(`renderOrder = 2`)보다 **위에** 그려집니다. 두꺼운 난층운 뒤에서도 태양이 그대로 타오릅니다.
- **구름끼리**: 각 빌보드가 독립입니다. 상층에 고층운이 덮여 있어도 그 아래 저층운은 `beamAtAltitude()`가 준 **직달광 100%** 를 받습니다. 흐린 날 특유의 "직사광 없음 → 명암 대비 소실 → 평평한 회색"이 나올 수가 없습니다.

이게 사용자가 본 "비구름이 태양빛을 제대로 차단하지 못한다"의 실체입니다.
차단 로직이 약한 게 아니라 **차단 경로 자체가 없습니다.**

### 1-E. 노란 구름 — 조명 계산이 **렌더 위치와 다른 좌표**를 씁니다

이게 노란 구름의 주범입니다. 톤매핑이 아닙니다.

`cloudPlacement.ts`는 고도각을 한 번 구해서 조명에 쓰고,

```ts
const elevationDeg = Math.max(2.0, Math.atan2(altKm, Math.max(0.5, distanceKm)) * (180/Math.PI));
const gammaDeg  = /* elevationDeg 기준 산란각 */;
const rawAmbient = skyRadiance(elevationDeg, gammaDeg, sunAltDeg, atmosphere);
```

`isOverheadLowCloud`(≤55km, 저·중층)인 경우 **완전히 다른 좌표에 배치합니다.**

```ts
const mainHorizDist = Math.max(12, distanceKm * 3.6);       // 수평거리를 3.6배로 늘리고
const mainWorldY    = Math.max(35, Math.min(180, altKm * 28.0));  // 높이를 28배로
```

두 고도각이 따로 놉니다:

| 운형 | 거리 | 조명용 elev | 실제 렌더 elev | 차이 |
|---|---|---|---|---|
| Cumulus | 5 km | 17.7° | **68.1°** | +50.4° |
| Cumulus | 15 km | 6.1° | **39.7°** | +33.6° |
| Stratocumulus | 15 km | 7.6° | **46.0°** | +38.4° |
| Nimbostratus | 15 km | 10.6° | **55.4°** | +44.9° |
| Cumulonimbus | 30 km | 6.7° | **42.2°** | +35.6° |

머리 위 40~70°에 그려지는 구름이 **지평선(2~10°) 하늘빛으로 조명됩니다.**
태양고도 12°에서 그 차이는:

```
조명에 쓰인 값 (elev 2°)   ambient = (10.343, 7.069, 3.694)   R/B = 2.80
써야 했던 값   (elev 39.7°) ambient = ( 0.492, 0.604, 0.870)   R/B = 0.57
                                     ↑ 밝기 21배 과다,  R/B 4.95배 과다
```

지평선 노을빛을 **21배 세기로** 뒤집어쓰니 노랗게 타오릅니다.
`vCosView`(실버라이닝)만 실제 월드 좌표를 쓰기 때문에 조명 항끼리도 서로 안 맞습니다.

증상이 "**때도 있고**"인 이유가 이것입니다 — `isOverheadLowCloud` 조건
(`distanceKm ≤ 55 && layerType !== 'high'`)에 걸린 인스턴스에서만 나타납니다.

### 1-F. (부차) 톤매핑 불일치와 노을 틴트 이중 계상

주범은 아니지만 함께 고쳐야 합니다.

| 셰이더 | 톤매핑 |
|---|---|
| `Skydome` | `atm_display()` = 순응 노출 → **ACES** → 채도 복원 → 대비 |
| `CloudField` | `1.0 - exp(-col)` → `atm_toSrgb()` |
| `SunMesh` | `1.0 - exp(-col * uIntensity)` |

`CloudField`의 주석은 "하늘과 같은 톤매핑"이라고 적혀 있지만 실제로는 다릅니다.
정상 범위 복사휘도에서 두 곡선의 색차 자체는 크지 않습니다(적운 밝은 면 R/B 1.06 vs 1.06).
문제는 **노출과 순응**입니다.

- `atm_display`는 `DISP_EXPO = 0.62`를 곱하지만 구름은 1.0 — 구름이 하늘보다 1.6배 밝게 노출됩니다.
- `atm_adaptation()`(최대 16×)이 구름에는 안 걸립니다 → **박명에 하늘만 밝아지고 구름은 검게 죽습니다.**

그리고 `vBeam`은 `beamAtAltitude()`에서 **이미 물리적으로 붉어진** 값인데
셰이더가 그 위에 `sunsetTint × 1.35`를 또 곱합니다:

```
sunAlt 10°  물리 R/B = 2.08  →  틴트 후 R/B = 3.28   (1.58× 과다)
sunAlt  5°  물리 R/B = 3.45  →  틴트 후 R/B = 5.27   (1.53× 과다)
```

또한 `sunsetStrength = clamp((vBeam.r − vBeam.b) × 2.2)`는 **정규화되지 않은 절대 복사휘도의 차**라
빔이 밝기만 하면 색이 희어도 1.0으로 포화합니다. 비율(`r/b`)로 판정해야 맞습니다.

## 2. 설계

네 개의 축으로 나눕니다. 서로 독립이라 순서대로 넣으면서 각각 눈으로 확인할 수 있습니다.

### 2-A. 각도 공간 리샘플링 (Angular Resampling)

지금의 "격자점마다 구름을 하나씩 놓는다"를 뒤집습니다.
**하늘 방향을 먼저 정하고, 그 방향이 어느 기상 격자를 보는지 역산합니다.**

```
for each layer L in {low(1.5km), mid(4.5km), high(10km)}:
    for each dome sample (az, ε) in 층별 각도 격자:
        d = L.altKm / tan(ε)                 # 지상 투영 거리
        (cover, type, precip) = sampleWeather(bearing = az, distance = d)
        → 이 방향의 층 L 운량
```

층별 각도 격자는 고도각을 **등입체각**으로 나눕니다(`sin ε` 균등). 그래야 천정이 비지 않습니다.
제안: 고도각 8단계 × 방위 24단계 = 192 방향/층, 3층 = 576 샘플.
전부 CPU에서 도는 순수 산술이라 프레임당 비용은 무시할 수준이고,
실제로는 **시간 슬라이더가 멈췄을 때만** 재계산하면 됩니다.

**기상 데이터의 각도 커버리지 한계를 명시해야 합니다.**
실제 API 팬은 `angles = [-20,-10,0,10,20]` × `distances = [10,30,70,130,200,280,380]` —
**태양 방위 기준 ±20°뿐**입니다. 360°가 아닙니다. 따라서:

- 태양 방위 ±20°: 실측 팬을 이중선형 보간
- ±20° 밖: 관측점(0km) 운량을 기저로 두고, 팬 가장자리 값과 각도 거리에 따라 블렌드
- 그 위에 **공간적으로 연속인 노이즈**(값 노이즈 2~3옥타브)를 얹어 구조를 만듦.
  노이즈는 평균이 아니라 **분산**만 담당합니다 — 평균 운량은 항상 실측값을 보존해야 합니다.

즉 `cover(az, ε) = clamp(cover_obs(az,d) + σ(cover) · noise(az, d, t), 0, 1)` 형태이고,
`σ`는 운량이 0이나 1에 가까울 때 0으로 수렴시킵니다(맑으면 완전히 맑고, 8/8이면 빈틈없이).

### 2-B. 운량 → 연속성 판단 (FEW / SCT / BKN / OVC)

사용자가 요청한 "연속으로 이어지는 큰 구름 여부 판단"입니다.
기상학의 옥타 척도가 그대로 렌더링 전략이 됩니다.

| 운량 | 코드 | 물리 | 렌더 전략 |
|---|---|---|---|
| 0–1/8 | SKC/FEW | 고립된 적운 | 빌보드만, 성기게 |
| 2/8–4/8 | SCT | 적운 field | 빌보드, 간격 좁게 |
| 5/8–7/8 | BKN | 적운→층적운 병합 시작 | 빌보드 + **덱 셸** 알파 램프 인 |
| 8/8 | OVC | 층운/난층운 | **덱 셸**이 주체, 빌보드는 표면 질감 |

물리적 근거: 적운 field에서 구름 지름 `D`, 간격 `L`일 때 운량 ≈ `(D/L)²`.
운량이 0.5를 넘으면 개별 적운이 서로 닿기 시작하고, 이게 실제 적운→층적운 전이입니다.
그래서 `mergeFactor = smoothstep(0.45, 0.85, cover)` 한 개로 두 표현을 잇습니다.

**덱 셸(deck shell)** — 층별로 돔 캡 메시를 하나씩 둡니다(빌보드와 별개, draw call 3개 추가).
정점마다 `cover`, `τ`, `type`을 attribute로 싣고, 프래그먼트에서:

```glsl
float deckAlpha = mergeFactor * coverage;         // 병합 전에는 0
deckAlpha *= fbm(듬성한 구멍 노이즈);              // BKN의 파란 하늘 구멍
```

BKN(5/8~7/8)에서 덱에 구멍이 뚫려 파란 하늘이 비치고, OVC에서 구멍이 닫힙니다.
이게 "흐린 날"의 핵심 실루엣입니다.

빌보드는 `1 - deckAlpha` 가중으로 남겨서, 덱이 닫힐수록 개별 퍼프가 덱에 흡수됩니다.

**운형 결정도 해시가 아니라 기상값에서 나와야 합니다:**

```
precip > 0.5mm/h  &&  low > 0.8            → Nimbostratus (난층운)
precip > 2.0mm/h  &&  high > 0.5           → Cumulonimbus (적란운)
low > 0.7  &&  precip ≈ 0  &&  RH < 80     → Stratocumulus
low > 0.7  &&  RH > 90                     → Stratus
low 0.3~0.7 &&  DNI 높음                    → Cumulus
mid 주도                                    → Alto{cumulus|stratus}
high만                                      → Cirrus / Cirrostratus
```

### 2-C. 수직 광학 스택 (Vertical Optical Stack)

지금 빠져 있는 전부입니다. 방향마다 **3층을 하나의 기둥으로** 풉니다.

**(1) 광학두께를 물리량에서.**
`τ = (3/2) · LWP / (ρ_w · r_eff)`.
LWP를 직접 주는 API는 없지만 근사할 수 있고, 무엇보다 **DNI라는 직접 관측량**이 이미 있습니다.

```
T_beam(관측)  = DNI / DNI_clearsky(sunAlt, β)
τ_column      = −ln(T_beam) · cos(zenith)
```

`τ_column`을 층별 운량 비율로 배분하면, **관측된 차단량과 렌더가 일치**합니다.
운형별 하드코딩 표(`PRESET_OPTICS`)는 DNI가 없을 때의 fallback으로만 남깁니다.

현재 표의 값은 실제보다 얇습니다:

| 운형 | 현재 τ | 현재 T | 실제 τ | 목표 T |
|---|---|---|---|---|
| Stratus | 12 | 0.53 | 10–30 | 0.3–0.5 |
| Nimbostratus | 50 | 0.21 | 50–150 | 0.05–0.15 |
| Cumulonimbus | 70 | 0.16 | 100–500 | 0.01–0.06 |

(`T = 2/(τ(1−g)+2)`, `g = 0.85`)
난층운 T=0.21은 "비 오는 날인데 꽤 밝음"이고, 적란운 T=0.16은 명백히 과다합니다.

**(2) 층 합성은 adding method로.**
층 사이 다중 반사를 무시하면 두꺼운 다층운이 부자연스럽게 밝아집니다. 표준 adding 공식:

```
R = R₁ + T₁² R₂ / (1 − R₁R₂)
T = T₁ T₂ / (1 − R₁R₂)
```

`atm_cloudRT()`가 이미 층별 `(R,T)`를 주므로 두 줄이면 됩니다.

**(3) 직달광은 위층을 통과해서 와야 합니다.**
`beamAtAltitude()`는 공기만 계산합니다. 여기에 **태양 방향** 기둥의 위층 투과율을 곱합니다.

```
beam_effective(layer L) = beamAtAltitude(...) × Π T_M   (M = L보다 위의 모든 층, 태양 방향 기둥)
```

이 한 줄이 흐린 날 렌더링의 최대 변곡점입니다.
고층운이 덮이면 저층운의 직달광이 사라지고 → 밝은 면/그늘 면 대비가 소멸하고 →
`t = dot(sunDir2D, quad)` 명암이 무의미해지고 → **평평한 회색**이 나옵니다.
지금은 이 경로가 없어서 아무리 두꺼운 구름을 쌓아도 그 아래 구름이 햇빛을 받습니다.

**(4) 확산광(ambient)도 위층을 반영.**
흐린 날 아래쪽 조명은 파란 천공광이 아니라 **덱 바닥에서 나오는 회백색 확산광**입니다.
`ambient = mix(skyRadiance(...), deckBaseRadiance, coverAbove)`.

**(5) 태양 원반 차폐.**
`SunMesh`에 `uOcclusion`(태양 방향 기둥의 `T`)을 넘기고:

- `T > 0.7`: 원반 그대로
- `0.15 < T < 0.7`: 원반이 흐려지고 넓어짐 (권층운/고층운 뒤의 "물먹은 해")
  — 다중산란이 각을 퍼뜨리므로 반경 ∝ `τ^0.5`
- `T < 0.15`: 원반 소멸, 밝은 얼룩만

`renderOrder`도 손봐야 합니다. 현재 태양(5) > 구름(2)이라 항상 구름 위입니다.

**(6) 스카이돔.**
덱이 닫히면 스카이돔은 어차피 가려지지만, BKN의 구멍으로 보이는 하늘은
주변 구름의 다중산란 때문에 맑은 날보다 뿌옇습니다.
`uCloudCoverAbove`를 넘겨 `skyRadiance`에 회색화를 살짝 섞습니다.

### 2-D. 표시 파이프라인 통일

`CloudField`와 `SunMesh`의 `1-exp(-x)`를 **`atm_display(col, uSaturation, uSunAltDeg)`** 로 교체합니다.
이미 `ATMOSPHERE_GLSL`이 두 셰이더에 들어와 있어서 함수 호출만 바꾸면 됩니다.

동시에 **노을 틴트 이중 계상을 제거**합니다.
`vBeam`이 물리적으로 이미 붉으므로 `sunsetTint * 1.35`는 빼고,
필요하면 채도만 `atm_display`의 `saturation` 인자로 조절합니다.

### 2-E. "굴절"에 대해

정직하게 적어둡니다. **구름 내부의 굴절은 벌크 수송 항이 아닙니다.**
가시광에서 구름이 하는 일은 (a) 물방울 Mie 산란(전방 피크, `g≈0.85`)과
(b) 얼음 결정 굴절에 의한 **광학 현상**입니다. 밝기 계산에 굴절률을 넣을 자리는 없고,
넣어야 할 것은 위상함수(이미 `atm_hgPhase`로 있음)와 아래 현상들입니다.

| 현상 | 조건 | 구현 난이도 |
|---|---|---|
| **22° 무리(halo)** | 권층운, 육각 기둥 얼음 | 낮음 — 태양 중심 22° 링 가산, 상층 ice cover로 게이트 |
| 환일(sun dog) | 권층운, 판상 결정 | 낮음 — 22° 링의 좌우 두 점 |
| 광환(corona)·채운 | 얇은 고층운 물방울 | 중간 — 회절 링, `r_eff` 의존 |
| 박명광선(crepuscular ray) | BKN 덱의 구멍 | 높음 — 볼류메트릭 필요 |

권장은 **22° 무리 하나**입니다. 싸고, 권층운과 물리적으로 직결되고,
"엷게 흐린 날"의 시각적 서명이라 흐림 표현에 실제로 기여합니다.

## 3. 실행 순서

각 단계가 독립적으로 눈에 보이는 변화를 냅니다. 순서는 **효과/비용 비**입니다.

| 단계 | 내용 | 파일 | 기대 효과 |
|---|---|---|---|
| **0** | 조명 고도각을 **실제 렌더 위치**에서 다시 구하기 (1-E) | `cloudPlacement.ts` | **노란 구름 해결** — 수 줄짜리 수정, 즉효 |
| **1** | `Sim3DContainer`가 실제 `interpolatedWeather` / `prediction`을 넘기도록 배선 | `Sim3DContainer.tsx` | 데이터 경로 개통 (이게 없으면 아래 전부 무의미) |
| **2** | `CloudField`·`SunMesh` → `atm_display`, 노을 틴트 이중 계상 제거, `sunsetStrength`를 비율 판정으로 | `CloudField.ts`, `SunMesh.ts` | 박명 밝기 일치, 과채도 제거 |
| **3** | 각도 공간 리샘플링 — 방향에서 거리를 역산 | 신규 `skyColumn.ts`, `cloudPlacement.ts` | **천정 빈 하늘 해결** |
| **4** | 실측 운량/운형 결선 (해시 제거), DNI로 τ 앵커링 | `cloudMatrix.ts`, `atmosphere.ts` | 흐린 날과 맑은 날이 달라짐 |
| **5** | 덱 셸 + `mergeFactor` 연속성 | 신규 `CloudDeck.ts` | **이어진 구름층 = 흐린 날 실루엣** |
| **6** | 수직 광학 스택 (adding, 위층 통과 직달광, 태양 차폐) | `atmosphere.ts`, `CloudField.ts`, `SunMesh.ts` | **평평한 회색 흐림**, 태양 차단 |
| **7** | 22° 무리 | `Skydome.ts` | 권층운 표현 |

0단계는 독립적인 버그 수정이라 지금 바로 넣을 수 있습니다.
3단계까지 하면 "하늘이 비어 보이는" 증상이 사라지고,
5~6단계에서 비로소 "흐린 날"이 나옵니다.

**0단계 구체안** — `isOverheadLowCloud` 분기에서 월드 좌표를 먼저 정하고,
그 좌표에서 고도각을 역산해 `beam`/`ambient`/`gamma`를 계산합니다.
근본적으로는 3단계(각도 리샘플링)가 이 이중 좌표계를 없애므로,
0단계는 3단계까지의 가교로 둡니다.

## 4. 검증

기존 하네스(`tools/shader-preview/`)를 그대로 씁니다.

**수치 검증** (`verify-overcast.js` 신규):
- 각도 리샘플링: 층별로 고도각 0~90°를 훑어 **입체각 가중 커버리지**가 입력 운량과 일치하는지
  (8/8 입력 → 덮인 입체각 비율 > 0.97, 0/8 → < 0.03)
- adding 공식: 2층 합성 `T`가 각 층 `T`의 곱보다 크고 두 층 중 작은 값보다 작은지(다중반사 부호)
- DNI 역산: `τ_column`에서 재구성한 `T_beam`이 입력 DNI 비율과 일치(왕복 오차 < 1%)
- 위층 통과 직달광: 상층 OVC일 때 저층운의 `beam`이 clear 대비 **10배 이상** 감쇠
- 톤매핑: 동일 복사휘도를 넣었을 때 `CloudField`와 `Skydome` 출력 색차 ΔE < 2

**시각 검증** (`build-overcast-preview.js` 신규):
8컷 매트릭스 — 운량 {0, 3/8, 6/8, 8/8} × 태양고도 {45°, 5°}.
합격 기준은 눈으로: 8/8·45°가 **평평한 회색 + 태양 원반 소멸 + 명암 대비 없음**이어야 하고,
3/8·5°가 지금처럼 **개별 적운에 노을이 드는** 그림이어야 합니다.

## 6. 구현 중 추가로 발견한 것

설계 단계에서 예상하지 못했고, **렌더 픽셀을 직접 재서** 잡은 것들입니다.

### 6-A. 노란 구름의 주범은 따로 있었습니다 — 한낮에 걸리던 황혼 자색광

§1-E에서 지목한 좌표 불일치(21배 ambient)는 실재했고 0단계에서 고쳤습니다.
그런데 고친 뒤에도 한낮 구름이 여전히 노랬습니다.

수식을 따라가면 중성이 나오는데(적운 밝은 면 R/B 1.00) 실제 픽셀은
`(250, 234, 147)`, R/B 1.70이었습니다. 덱을 끄고 다시 찍어 빌보드 쪽임을
확인한 뒤, 재현 코드에서 빠뜨린 항을 하나씩 넣어 찾았습니다.

`atm_twilightPurple`에 **태양 고도 게이트가 없었습니다.**

```
태양 45°  horizonGlow = skyRadiance(0.5°, 5°, 45°) = (25.2, 19.1, 12.3)
          target = horizonGlow × TWILIGHT_W = (7.05, 2.86, 0.18)   ← R/B = 38
          influence = 1 − T = 0.72  (층적운)
          → 그늘 면의 72%가 이 주황색으로 대체
```

고도 0.5°, 태양에서 5°는 "지평선"이 아니라 "태양 옆 눈부신 연무"입니다.
황혼용으로 설계된 항이 한낮 값을 먹고 있었습니다.
`smoothstep(-2°, 8°)`로 게이트하니 같은 지점이 `(215, 226, 239)`로 돌아왔습니다.

**교훈:** 수식 검증만으로는 못 잡습니다. 재현 코드가 실제 셰이더의 부분집합이면
빠뜨린 항이 곧 사각지대가 됩니다. 픽셀을 재고, A/B로 범인을 좁혀야 합니다.

### 6-B. 하늘 방향 샘플은 지상에서 균일하게 퍼지지 않습니다

각도 리샘플링을 넣었더니 입력 운량 50%가 화면 29%로 나왔습니다.
노이즈 자체는 편향이 없었습니다(측정 평균 0.4991).

원인은 샘플 분포였습니다. 저층 1.5km는 고도각 3.6°에서 24km, 69.6°에서 0.56km라
**8개 고리 중 6개가 반경 5km 안에 몰립니다.** 그 샘플들이 노이즈 셀 하나를 공유하면
그 셀 값이 하늘 평균을 그대로 끌고 갑니다.

실현된 노이즈 평균을 빼서 편차만 남기니 오차 0.5%p 안으로 들어왔습니다.
(층별 노이즈 셀 크기도 구름 구조 규모에 맞춰 3.5 / 11 / 28 km로 잡았습니다.)

### 6-C. DNI는 τ ≲ 5까지만 분해합니다

§2-C에서 DNI 앵커링을 제안했지만, 분해능 한계를 따져보지 않았습니다.
직달광은 Beer-Lambert로 죽으므로 태양 45°에서:

| τ | 직달 투과 |
|---|---|
| 3 (권운) | 1.4e-2 |
| 30 (고층운) | 3.8e-19 |
| 110 (난층운) | 2.8e-68 |

τ가 5를 넘으면 DNI가 0에 붙어 더 이상 정보를 담지 않습니다.
그래서 `cloudTauFromDNI`가 `saturated` 플래그를 함께 반환하고,
**포화하지 않았을 때만** 관측을 신뢰합니다.

이 구분이 없으면 난층운 τ=110이 역산값 2.8에 끌려 40까지 얇아집니다 —
관측을 반영하려다 오히려 흐린 날을 밝게 만드는 셈입니다.
DNI의 쓸모는 "예보는 흐림인데 실제로는 해가 비친다"를 잡아내는 것이지,
두꺼운 구름의 두께를 재는 것이 아닙니다.

### 6-D. 평행광과 확산광을 나눠야 했습니다

§2-C는 2-stream의 `T` 하나로 층간 감쇠를 처리하려 했는데 틀렸습니다.

- `T`는 **직달+확산 총** 투과율입니다.
- 구름의 밝은 면/그늘 면 대비를 만드는 것은 **오직 평행광**입니다.
- 평행광이 죽어도 확산광은 남습니다. 흐린 날이 캄캄하지 않고 균일하게 밝은
  회색인 이유이고, 이걸 빠뜨리면 8/8 하늘이 새까매집니다.

그래서 `ColumnOptics`가 `beamFactor`(Beer-Lambert)와 `diffuseFactor`(2-stream adding)를
따로 냅니다. 태양 원반 차폐는 전자, 구름 아래 조명은 후자입니다.

### 6-E. 감광은 **모든** 하늘빛 입력에 걸어야 합니다

스카이돔만 감광했더니 8/8 일몰에서 구름만 시뻘겋게 남았습니다.
황혼 자색광의 입력(`uHorizonGlow`, `uZenithSky`)이 원본 값이었기 때문입니다.

`applyCloudDimming`을 TS/GLSL 쌍으로 두고 상수를 주입해,
스카이돔·구름 ambient·황혼 자색광 입력이 **같은 식**을 쓰게 했습니다.

### 6-F. 덱 투영은 유계여야 합니다

`cot(ε)`로 지면 투영했더니 고도각이 낮을수록 UV가 발산해 노이즈 셀을 한
프래그먼트에서 여러 개 가로지르고, 지평선 쪽에 부채꼴 세로 줄무늬가 생겼습니다.
(측정: 해당 영역 가로 변동 0.58 대 정상 0.27. 덱을 끄면 0.27로 돌아옴.)
클램프를 조여도 클램프 경계에서 기울기가 급변해 남았습니다.

방향 벡터의 수평 성분(`|xz| ≤ 1`)으로 바꿨습니다. 지평선 원근 압축이 실제보다
약해지지만, 줄무늬가 생기는 것보다 낫습니다.

### 6-G. 하네스가 uniform을 빠뜨리면 조용히 틀립니다

스카이돔에 `uCloudDiffuse`를 추가한 뒤 밤하늘 미리보기가 어두워졌습니다.
그 하네스는 ShaderMaterial을 손으로 만들어서 새 uniform을 안 넣었고,
GL 기본값 0이 들어가 `atm_cloudDim(col, 0)` = 완전 감광이 됐습니다.

앱은 `createSkydome()`이 기본값을 넣으므로 무사했지만, 셰이더에 uniform을
추가할 때 손으로 만든 머티리얼을 함께 갱신해야 한다는 신호입니다.

## 8. 머리 위 기상이 반영되지 않던 문제

"현재 내 바로 위와 주변 기상 상태를 제대로 반영하지 못하는 것 같다"는
보고를 재현해 봤습니다. 관측자는 맑고(저층운 0%) 10km 밖은 잔뜩 낀(90%) 상황에서,
**천정 방향** 저층 운량을 방위별로 읽으면:

| 올려다본 방위 | 표시 운량 | 왜 |
|---|---|---|
| 270° (팬 중심) | 4.3% | 이 레이에만 0km 표본이 있음 |
| 300° / 330° | 84.1% / 82.2% | 가장자리 레이의 10km 값으로 클램프 |
| 0° / 90° | 0.0% | 팬 밖 → 관측점 값으로 대체 |

**하나의 물리적 지점(바로 머리 위)이 방위에 따라 세 값을 동시에 갖습니다.**
평균은 28.3% — 관측값 0%와 무관한 숫자입니다.

### 원인

API 팬은 0km 표본을 `azimuthOffset = 0` 레이에만 답니다. 나머지 레이는 첫
표본이 10km라, 그보다 가까운 방향이 `WeatherFan.alongRay`의 하한 클램프에
걸려 **10km 밖 하늘 값**을 씁니다.

저층운(고도 1.5km)은 하늘에서 차지하는 영역이 전부 반경 24km 안이고,
등입체각 8개 고리 중 **7개가 10km 안쪽**입니다. 즉 저층 하늘의 대부분이
이 클램프에 지배됩니다.

### 고친 방법

0km는 **모든 레이가 만나는 같은 지점**입니다. `WeatherFan` 생성자에서
0km 표본을 찾으면 모든 레이의 시작점으로 복사합니다.

앵커링을 `WeatherFan` 한 곳에 둔 이유: 표준 팬과 강화 격자(§IA_REDESIGN 8)가
같은 문제를 갖고 있어서, 두 곳에 두면 한쪽만 고쳐지는 사고가 납니다.
`cloudGridToFan`은 이제 0km 표본을 하나만 내보내고 복제는 하지 않습니다.
