# 구름 다양성 계획 — 어떤 시간에 어떤 방향에서 어떤 하늘을 볼 것인가

목표: 권운부터 적란운까지, **다양한 운형·색·그림자·크기·층**으로
"몇 시에 어느 쪽을 보면 어떤 하늘인지"를 예측 가능하게 만든다.

기준 사진 4장이 요구하는 범위:

| | 사진 | 하늘 |
|---|---|---|
| ① | 도로 위 노을 | 고적운 알갱이 + 권운 결, 지평선에 따뜻한 띠 |
| ② | 황금빛 탑 | 짙푸른 하늘에 **수직으로 솟은** 적운(congestus) 하나 |
| ③ | 해가 비치는 층 | 고층운·권층운 판, 그 뒤로 태양 원반이 비쳐 보임 |
| ④ | 분홍 조각 | 회청색 박명에 **밑에서 붉게 받은** 적운 조각들 |

## 0. 먼저 잰 것 — 부족한 것은 광학이 아니라 배분이다

`tools/shader-preview/build-genus-range-preview.js`

같은 운량(55%)·같은 태양(12°)·같은 카메라에서 10종의 `PRESET_OPTICS`를
하나씩 덱에 먹여 렌더하고, **구름 픽셀만** 골라 밝기와 결(RMS 대비)을 쟀다.

| 운형 | τ | 그늘 | 밝기 | 결 |
|---|---|---|---|---|
| 권운 Ci | 3 | 0.12 | **208.7** | 8.8 |
| 권적운 Cc | 4.2 | 0.15 | 206.7 | 8.2 |
| 권층운 Cs | 5 | 0.10 | 206.5 | 6.6 |
| 고적운 Ac | 16 | 0.48 | 190.6 | 9.7 |
| 고층운 As | 30 | 0.38 | 180.1 | 10.2 |
| 층운 St | 22 | 0.28 | 186.6 | 10.3 |
| 적운 Cu | 32 | 0.78 | 165.2 | 10.3 |
| 층적운 Sc | 35 | 0.62 | 157.9 | 13.9 |
| 난층운 Ns | 110 | 0.88 | 118.1 | 22.0 |
| 적란운 Cb | 220 | 0.94 | **94.3** | 13.0 |

밝기 폭 **2.2배**, 결 폭 **3.3배**. 덱은 운형을 구분해 그릴 수 **있다**.

그런데 지금 덱이 실제로 받는 값은 층마다 **스칼라 하나**다:

```ts
tauFor:   layer => medianOf(byLayer(layer).map(c => c.tau), 25)
shadowFor: layer => medianOf(byLayer(layer).map(c => c.shadowContrast), 0.5)
cellFor:  layer => cellForLayer(layer, observerWeather())
```

즉 **하늘 360° 전체가 층마다 한 가지 운형**이다. 위 표의 2.2배 폭은
매 프레임 한 칸만 쓰인다. "각 지역의 기상 상태에 따라 다르다"가
운량(`vCover`)에만 걸려 있고 운형에는 안 걸려 있다.

### 그 위에 버그가 하나 더

`byLayer(layer)`는 **빌보드**를 셉니다. 그런데 `CLOUD_TEXTURE_PLAN.md`
5단계에서 빌보드를 적운·적란운으로 제한했고, 그 둘은 `low` 층에서만
나옵니다(`resolvePresetFromWeather`의 mid/high 분기는 절대 반환하지 않음).

따라서 **`byLayer('mid')`와 `byLayer('high')`는 항상 빈 배열**이고,
중·상층 덱은 언제나 폴백 **τ=25 / 그늘 0.5** 로 그려집니다.

같은 권운 무늬에 τ·그늘만 바꿔 렌더한 실측:

| | τ | 그늘 | 밝기 |
|---|---|---|---|
| 권운 도감값 | 3.0 | 0.12 | 208.7 |
| **현재 앱** | 25 | 0.50 | **179.2** |

권운이 도감보다 **29.5 어둡게** 그려집니다. 권운은 해가 비쳐 보이는
구름인데(τ=3 → 투과율 0.82), τ=25(투과율 0.35)면 회색 판입니다.
사진 ①·③의 상층이 살아나지 않던 이유가 여기 있습니다.

## 1단계 ✅ — 중·상층을 폴백에서 꺼낸다

`tauFor`/`shadowFor`도 `cellFor`와 **같은 운형**에서 뽑는다
(`representativePresetForObserver` → `PRESET_OPTICS`).
빌보드 중앙값은 빌보드가 실제로 존재하는 저층에서만 참고한다.

- 비용: 몇 줄.
- 판정: 상층 운량만 바꾼 세 하늘(권운 / 권적운 / 권층운)이 서로 다른
  밝기·결로 나온다. 권운이 205 이상으로 되돌아온다.

## 2단계 ✅ — 운형을 **방향마다** 정한다 (다양한 구름)

덱은 이미 방향별 정점 속성을 씁니다(`aCover`, `aAmbientUp/Down`).
같은 자리에 광학도 싣는다:

```
attribute float aTau;          // 이 방향 운형의 광학두께
attribute float aShadow;       // 그늘 대비
attribute vec2  aCellScale;    // 축별 uv 배율 (크기 + 이방성)
attribute float aCellStrength; // 0 = 조각 없는 층상 베일
attribute float aCellMix;      // billow ↔ fbm 채널 블렌드
```

`cellVariant`는 uniform 채널 마스크였는데, 방향마다 다르려면
두 마스크를 모두 샘플해 `aCellMix`로 섞는다(텍스처 페치 2회 → 4회,
단 `aCellStrength = 0`인 층상운은 기존처럼 건너뛴다).

방향별 운형은 이미 계산되고 있습니다 —
`placeClouds`가 방향마다 `resolvePresetFromWeather(s.layer, s.cover, …)`를
부르고, 그 중 여덟 종을 **버립니다**(5단계의 빌보드 제한). 버리는 대신
덱으로 넘긴다.

### 결과 (실측)

중층 서쪽 20% / 동쪽 90% 링을 만들고 **그 경계를 정면으로** 보는 한 프레임을
두 번 렌더했다 — 층 대표 스칼라(이전) vs 방향별(2단계). 같은 링·같은 카메라·
같은 태양이라 차이는 오직 운형 배분에서 온다.

| | 2단계 이전 | 2단계 |
|---|---|---|
| 192방향이 고른 운형 | 고적운 192 | **고적운 125 / 고층운 67** |
| τ 범위 | 16 (하나) | **16 ~ 30** |
| 좌우 밝기차 | 14.2 | **19.0** |
| 좌우 중간알파차 | −2.1%p | **+11.2%p** |
| 예보 운량 변화 | — | 0.46%p (보존) |

**중간 알파 비율**(0.15 < α < 0.85인 픽셀의 비중)이 조각 세기를 직접 읽는
지표다. 조각형은 알파가 문턱에 잘려 0/1로 몰리고, 층상형은 운량이 그대로
알파라 전부 중간값이다. 왼쪽 19.5% → 오른쪽 32.3%: 오른쪽이 요소 없는
균질한 판(고층운)으로 갈렸다.

⚠ 처음엔 **알파의 표준편차**로 쟀는데 순서가 뒤집혔다. 이항 분포의 분산은
운량 0.5에서 최대라, 운량이 다른 두 영역을 비교하면 조각 세기가 아니라
운량을 재게 된다 (층상 운량 0.61에서 0.372 > 조각 운량 0.21에서 0.335).
그 지표로는 2단계가 아무 일도 안 한 것처럼 보였다.

### 설계상 남긴 것

**채널(billow/fbm)은 층당 하나로 남겼다.** 방향마다 바꾸려면 두 채널을
섞어야 하는데, `cell_sample`은 마스크에 선형이라 독립인 균등분포 둘을
섞게 되고 분포가 좁아진다 — `cell_threshold`의 운량 보장이 깨진다.
한 층 안에서 채널이 실제로 갈리는 경우는 권운↔권적운뿐이라 손해가 작다.

**입체 음영 분기는 uniform으로 유지했다.** GLSL ES 1.0에서 `texture2D`는
암시적 미분으로 밉 레벨을 정하므로 비균일 분기 안에서는 결과가 정의되지
않는다. 층 전체의 최대 조각 세기(`uAnyCells`)로 분기하고 방향별 세기는
안에서 곱한다.

**seed는 0.5 고정.** 방향마다 난수를 넣으면 이웃한 두 방향이 무작위로 다른
운형이 되어 기상이 아니라 노이즈가 된다. 운형 차이는 오직 데이터에서 온다.

### 렌더가 잡아낸 것 두 가지 — 둘 다 숫자로는 안 보였다

3단계 화면을 찍고 나서야 드러났다. 두 번 다 원인 추측이 틀렸고,
**성분을 하나씩만 흔드는 분해 렌더**(`build-deck-tear-diag.js`)를 만들고 나서
잡혔다. τ·그늘은 깨끗한데 조각 크기·세기만 이음매를 만들고 있었다.

**(1) 조각 크기는 방향별로 줄 수 없다.** `cellSizeKm`은 텍스처 uv 배율이다.
방향마다 다르면 같은 지상 좌표가 방향마다 다른 uv로 사상되어 **무늬의 위상이
어긋나고**, 화면에서는 구름 가장자리가 두 겹으로 갈라진 이음매가 된다.
메시 해상도를 올려도 사라지지 않는다 — 타일 텍스처 하나를 공간적으로 다른
배율로 읽는 것 자체가 성립하지 않기 때문이다. 크기와 늘임비는 층당 하나로
되돌렸다. τ·그늘·조각 세기만 방향별이다.

**(2) 계단 함수를 성긴 격자로 표본하면 하늘에 네모가 찍힌다.**
`resolvePresetFromWeather`는 문턱을 넘는 계단인데, 그 입력 격자는 방위 24 ×
고도 8 (15° 간격)이다. 계단을 그 격자로 표본하면 문턱을 넘는 등고선이 격자선에
달라붙어, 축에 나란한 사각형이 그대로 보인다. 메시 해상도를 5배로 올려 봤지만
등고선의 위치를 정하는 것은 메시가 아니라 기상 격자라 소용이 없었다.

해법은 **입력 공간에서 문턱을 뭉개는 것**이다 (`blendedOpticsFromWeather`).
운량·강수 축으로 5점 스텐실을 잡아 광학을 가중 평균한다. 문턱 위치를 알
필요가 없고, 문턱 근처에서만 자동으로 섞이며 멀리서는 한 운형이 100% 이긴다.

이건 임시방편이 아니라 **더 맞는 모형**이다. 한 방향이 담당하는 입체각은
15°×약 10°이고, 30km 밖이면 한 변이 8km쯤 되는 하늘 조각이다. 그 안에 운형
하나만 들어 있을 리 없다. 대표 하나를 고르는 것보다 입력 분포 위에서 평균한
광학이 그 조각을 더 잘 나타낸다.

비용: 판정 5회/방향 × 576방향 = 0.12ms. 메시는 72×32 그대로다.

## 3단계 ✅ — 방향별 기상을 판정에 넣는다

2단계 뒤에도 판정 입력 중 **운량만** 방향별이었다. 강수·습도·상층 운량은
여전히 관측점 값 하나라, 서쪽 30km에 비가 와도 그 방향이 비구름이 되지 않았다.

이건 없는 데이터를 지어내는 문제가 아니었다. Open-Meteo 팬은 **모든 지점**에서
`precipitation`과 `relative_humidity_2m`을 이미 받고 있다 (weather.ts의 원격
지점 변수 목록). 화면까지 오지 않고 있었을 뿐이다.

### 결과 (실측)

저층 운량을 **어디나 80%로 같게** 두고 서쪽에만 강수 1.5mm/h를 주었다.
운량이 같으니 화면 차이는 오직 강수에서 온다 — 이 통제가 없으면 "구름이 더
많아서 어두운 것"과 구분되지 않는다.

| | 판정 입력 = 관측점 값 | 판정 입력 = 방향별 값 |
|---|---|---|
| 서쪽(비) 밝기 | 158.7 | **122.6** |
| 동쪽(맑음) 밝기 | 148.2 | 145.4 |
| 동 − 서 밝기차 | −10.5 | **+22.8** |
| 192방향 운형 | 층적운 위주 | 난층운 65 / 층적운 114 / 적운 13 |
| 예보 운량 변화 | — | 0.25%p (보존) |

같은 방향끼리 비교하면 **비 오는 서쪽만 36.1 어두워졌고 맑은 동쪽은 2.8**
움직였다. 부호까지 봐야 "어딘가 갈렸다"가 아니라 "비 오는 쪽이 갈렸다"를
말할 수 있다.

### 곁다리로 고친 것

`WeatherFan`이 거리·방위로 보간할 때 **강수와 습도는 보간하지 않고 있었다**
(스프레드로 가까운 쪽 값이 그대로 넘어감). 운량만 보간되고 운형 판정 입력은
계단이었던 셈이다. 두 축 모두 보간하도록 고쳤다.

타임라인은 방향별 강수·습도·상층 운량을 **Uint8로 양자화**해 키프레임마다
저장한다. 문턱 비교에만 쓰이므로(0.3·0.9 mm/h, 90%, 35%) 0.4% 해상도면
충분하고, Float32로 두면 하루치가 2.65MB인 것이 497KB가 된다.

## 4단계 ✅ — 구름이 구름에 드리우는 그림자 (다양한 그림자)

`solveColumnOptics(samples, sunAz, sunAlt)`은 **관측점 수직 기둥 하나**를
풀고, 그 `beamFactor[layer]`를 하늘 전체에 곱했습니다. 그래서 서쪽에 두꺼운
상층 띠가 있으면 **동쪽 저층까지 같이 어두워졌습니다.** 옆 구름은 그늘인데
이 구름만 빛을 받는 대비 — 사진 ②·④의 핵심 — 이 원리적으로 나올 수
없었습니다.

`solveDirectionalShade`가 방향마다 다시 풉니다. 방위 az·지상거리 d·고도 h의
구름에 닿는 햇빛은 거기서 태양 쪽으로 올라가며 위층을 지나므로, 고도 h2의
관통점은

    P = d·(sin az, cos az) + Δ·(sin az☉, cos az☉),
    Δ = dist(태양고도, h2) − dist(태양고도, h)

입니다. Δ를 두 **구면** 거리의 차로 잡으면 곡률이 자동으로 들어옵니다 —
평면 근사 (h2−h)/tan ε는 태양이 낮을 때 크게 빗나갑니다.

확산광은 그대로 전역입니다. 반구 전체에서 오므로 한 방향의 위층 운량에
거의 좌우되지 않고, 밝은 면/그늘 면 대비를 만드는 것은 평행광입니다.

### 결과 (실측)

중층 운량을 어디나 45%로 같게 두고 **상층만** 서쪽 절반을 90%로 덮었다.

| | 기둥 하나 | 방향별 |
|---|---|---|
| 직달광 배율 | 0.326 (전역 하나) | **0.0035 ~ 1.00** (286배) |
| 서(위에 상층) 밝기 | 157.0 | 158.0 |
| 동(위가 빔) 밝기 | 158.0 | **172.5** |
| 동 − 서 | 1.0 | **14.5** |
| 중층 운량 | — | 변화 0.00%p |

움직인 것은 **동쪽**이다 (+14.5), 서쪽은 그대로(+1.0). 전역 배율이 가려진
서쪽에 맞춰져 있었으므로, 고쳐진 것은 "동쪽이 억울하게 어두웠던 것"이다.
부호까지 봐야 "구름이 그림자를 드리운다"와 "한쪽을 어둡게 칠했다"가 구분된다.

### 측정 설계에서 배운 것

처음엔 **저층**에 드리운 그늘을 재려 했는데 동−서가 3.5밖에 안 나왔다.
저층은 고도 1.5km라 보이는 지상 범위가 25km쯤인데, 상층(10km)까지의 그늘
displacement가 태양 25°에서 이미 20km다. 화면 왼쪽 끝과 오른쪽 끝이 **거의
같은 지점**의 상층을 보게 되어 좌우가 갈릴 수가 없다. 중층(4.5km)은 보이는
범위 70km에 displacement 10km라 그늘 경계가 화면 안을 지난다.

또 상층 경계를 방위 부호로 갈랐더니(a>0 && a<180이면 동쪽) 링의 0°·180°
레이가 서쪽 값을 갖게 되어 보간된 경계가 15° 돌아갔고, 그 탓에 천정 쪽이
통째로 그늘에 들어갔다. 경계는 **지상 좌표 x=0** 에 놓아야 한다.

## 5단계 — 수직 발달 (다양한 크기)

사진 ②는 지금 그릴 방법이 **없습니다**.

- 덱은 고도 하나의 얇은 껍질이라 수직 두께가 없다.
- 빌보드는 있지만 각크기가 `BILLBOARD_ANGULAR_DEG.low = 14°`에
  ±25% 흔들림뿐이고(10.5~17.5°), 가로세로비는 아틀라스 사각형에서
  **`[0.8, 2.5]`로 클램프**됩니다. 적란운 템플릿조차 가로가 긴 판이라
  결과는 납작한 덩어리입니다. 세로로 솟은 구름이 나올 수 없다.

필요한 것:
- 운정 고도를 기상에서 뽑는다(강수·`liquidWater`·상층 발달). 적운
  1.6km, congestus 4~6km, 적란운 8~12km — 밑면은 응결고도로 공통.
- 각크기를 그 **물리 높이와 거리**에서 계산한다(지금은 고정 각크기).
- 가로세로비 클램프를 세로로 연다(탑형은 aspect < 1).
- 세로 조명 기울기: 밑면은 그늘, 꼭대기는 직달광. 지금 빌보드의
  `t = dot(vSunDir2D, vQuad)`는 화면 좌우 기울기라 태양이 낮을 때만
  세로가 됩니다 — 고도 성분을 명시적으로 넣는다.
- 적란운은 모루(anvil): 운정에서 상층 바람 쪽으로 퍼지는 판.

- 판정: 같은 거리·같은 운량에서 적운/congestus/적란운의 화면 **세로
  각크기**가 단조 증가하고, 탑 밑동 대비 꼭대기 밝기비가 1보다 크다.

## 6단계 — 황혼의 층 분리 (다양한 색)

사진 ④는 저층이 이미 지구 그림자에 들어갔는데 중·상층만 붉게 남은
순간입니다. 이 계산은 **이미 있습니다** — `beamAtAltitude`가 고도별
수평선 내려앉음 `acos(R/(R+h))`을 더해 주므로 10km 구름은 관측자
일몰 후 3.2°까지 햇빛을 받습니다.

그러니 이 단계는 **새로 만드는 게 아니라 재는 것**입니다. 태양
−1°/−2°/−3°/−4°에서 세 층의 밝기·붉은기를 재서, 층이 실제로
시간차를 두고 꺼지는지 확인한다. 안 갈리면 그때 원인을 찾는다.
(의심 후보: `optics.beamFactor`가 전역이라 층 간 차이를 눌러 버림 —
4단계와 같은 뿌리.)

## 순서를 이렇게 잡은 이유

1단계는 버그라 먼저. 2·3단계가 "다양한 구름"의 본체이고, 2단계 없이
3단계는 의미가 없다(방향별 판정을 해도 그릴 곳이 없으므로).
4단계는 2단계가 만든 방향별 구조 위에서만 눈에 보인다 — 하늘이 균일하면
그림자가 갈려도 알 수 없다. 5단계가 가장 크고 가장 독립적이라 마지막.
6단계는 측정부터.
