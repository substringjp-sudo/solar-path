# 땅 계획 — 디테일이 아니라 정보를 더한다

앱 화면에서 지평선 아래가 무엇인지 헷갈립니다. "흐릿한 회색이 땅인 줄 알았는데
다시 보니 하늘과 만나는 날카로운 선이 지평선이고 그 아래 흐릿한 건 빛 반사
같다"는 지적에서 출발합니다.

**지적이 맞았고, 실제로는 더 단순합니다. 그 아래는 땅이 아니라 하늘입니다.**

---

## 1. 측정 — 지금 지평선 아래에 무엇이 그려지나

`tools/shader-preview/build-horizon-preview.js` 로 재현됩니다. 앱과 **같은
모듈**(`Skydome.ts`, `TerrainRing.ts`)을 임포트해 같은 순서로 씬에 넣고,
요소를 하나씩 빼가며 지평선을 가로지르는 세로줄의 픽셀을 읽었습니다.

### 1-A. 지면 원반은 한 픽셀도 안 보입니다

| 검사 | 결과 |
|---|---|
| 지면 원반을 빼도 바뀌는 **최대 픽셀차** | **1** / 255 |

`updateGroundColors`가 매 프레임 색을 다시 칠하는데 화면에는 나오지 않습니다.

원인은 그리기 순서입니다:

| 메시 | renderOrder | depthWrite | depthTest | 형상 |
|---|---|---|---|---|
| 지면 원반 | **−2** | false | true | y=−8 수평 원반, 반지름 480 |
| 스카이돔 | **−1** | false | **false** | 반지름 500, **완전한 구** |
| 지형 링 | 0 | true | true | 고도 −2° ~ 지형각 |

지면 원반이 **먼저** 그려지고 깊이를 안 씁니다. 그다음 스카이돔이 **깊이
검사를 끄고** 전체 구를 칠하므로 지면 원반을 통째로 덮습니다.

### 1-B. 지평선 아래는 하늘 셰이더입니다

같은 세로줄의 고도대별 색:

| 고도대 | 앱 화면 | 스카이돔을 뺐을 때 |
|---|---|---|
| 0~2° (하늘) | rgb(255,255,229) | — |
| **−2~0°** | rgb(255,254,222) | rgb(42,43,41) |
| **−6~−2°** | rgb(248,229,132) | rgb(90,93,89) |
| **−15~−6°** | rgb(219,177,12) | rgb(92,95,91) |
| **−30~−15°** | rgb(167,124,0) | rgb(93,96,92) |

지평선 아래가 **하늘보다 채도 높은 금빛**입니다. 이게 "빛 반사 하이라이트"로
보이던 것의 정체입니다 — 반사가 아니라 그냥 하늘입니다.

### 1-C. 실제 지형은 받아오는데 거의 안 씁니다

`fetchTerrainProfile`이 Open-Meteo elevation API에서 **31방위 × 3거리
(5 / 15 / 40 km)** 를 실제로 받아옵니다. 그런데 `createTerrainRing`이
`maxVisualAngle = 8`로 자르고 고도 −2°~지형각의 **얇은 띠 하나**로만 그립니다.
`farAngles`(먼 거리 프로필)는 3D 씬에서 아예 안 씁니다.

---

## 2. 진단

세 가지가 겹쳤습니다.

1. **지평선 아래가 틀렸습니다.** 땅이 있어야 할 자리에 하늘이 그려집니다.
2. **땅이 너무 밝습니다.** 지적대로 대지는 햇빛을 그렇게 반사하지 않습니다 —
   알베도가 잔디 0.25, 숲 0.15, 아스팔트 0.10입니다. 하늘보다 **훨씬 어두워야**
   맞습니다. 지금은 반대입니다.
3. **가진 정보를 안 씁니다.** 그 위치에서만 참인 실제 지형 프로필이 이미
   손에 있는데 8°로 잘라 띠 하나로 씁니다.

## 3. 설계 원칙 — 디테일이 아니라 정보를 더한다

건물도 숲도 만들 수 없습니다. 그러면 사용자가 그 부재를 감안하고도 만족할
방법이 무엇인가 — 이게 이 문서의 핵심 질문입니다.

**사용자는 "디테일이 없는 것"보다 "틀린 것"에 훨씬 민감합니다.** 지금 지평선
아래는 틀렸습니다. 그것만 고쳐도 몫이 큽니다.

그다음은 디테일을 흉내 내는 방향이 아니라 **정보를 더하는** 방향입니다.
아래 셋은 전부 **그 위치에서만 참**이라 사용자가 자기 눈으로 대조할 수 있습니다:

| 더할 것 | 왜 통하나 |
|---|---|
| 실제 360° 지형 프로필 | "서쪽에 산이 있다"가 맞으면 나머지가 추상적이어도 신뢰가 생깁니다 |
| 거리별 대기 투시 | 능선이 겹쳐 멀어지는 것은 풍경 사진의 가장 강한 깊이 단서입니다 |
| 실제 수역 | 물은 **원래 디테일이 없습니다** — 없는 걸 안 만들어도 되는 유일한 지표면 |

그리고 흉내 내지 **않는** 것을 분명히 합니다. 저녁 사진의 전경은 거의 검은
실루엣입니다 — 사용자가 보낸 사진에서도 나무와 건물이 새까맣습니다.
**해 질 녘 땅은 어둡고 디테일이 없는 것이 사실적입니다.** 지금의 밝은 금빛
그라데이션이 그 반대라서 부자연스러웠습니다. 어둡게 만드는 것은 포기가 아니라
정답에 가까워지는 것입니다.

## 4. 단계

| 단계 | 내용 | 검증 |
|---|---|---|
| **1** ✅ | 지평선 아래를 하늘이 아니게 (그리기 순서) | 지면 원반을 빼면 최대 픽셀차 1 → **178** |
| **2** ✅ | 땅 밝기를 알베도에서 (하늘보다 어둡게) | 지면/하늘 휘도비 **32%**, 태양 쪽이 **1.72배** 밝음 |
| **3** ✅ | 지형을 거리별 실루엣으로 (near/far + 대기 투시) | 하늘 대비 5km **70.4** → 15km **24.9** → 40km **7.7** |
| **4** ✅ | 바다 검출과 렌더 | 수평선 **0.176°**(30m), 반대쪽 물이 육지보다 **어두움** |
| **5** ✅ | 윤슬 (Cox-Munk 파면 경사) | 기둥 **+40** 솟음, 폭 **4.9° → 11.2°** (2→8 m/s) |
| **6** | 내륙 수역 (호수·강) | 별도 데이터원 필요 — §6 |

### 4-1. 지평선 아래를 하늘이 아니게

가장 작은 고침이자 나머지 전부의 전제입니다.

스카이돔이 `depthTest: false`인 것은 의도된 것으로 보입니다(항상 배경).
그러면 **지면을 스카이돔보다 나중에** 그려야 합니다:

```
지면 원반  renderOrder −2 → 0.5,  depthWrite true
```

또는 스카이돔 구를 위쪽 반구로만 만드는 방법도 있습니다
(`SphereGeometry(r, h, v, 0, 2π, 0, π/2)`). 이쪽이 더 정직하지만
지평선 정확히 0°에서 이음매가 보일 수 있어 **렌더로 확인하고 고릅니다.**

### 4-2. 땅 밝기를 알베도에서

지금 지면 색은 `nightG/dayG/goldenG` 상수를 태양 고도로 섞습니다 — 근거가
없습니다. 물리로 바꿉니다:

```
지면 휘도 = (하늘 조도 + 직달 조도 · sin(태양고도)) × 알베도 / π
```

알베도는 지표 종류의 대표값을 씁니다:

| 지표 | 알베도 |
|---|---|
| 숲 | 0.12 |
| 풀·농지 | 0.23 |
| 도시(아스팔트·콘크리트 혼합) | 0.15 |
| 눈 | 0.75 |
| **물 (수직 입사)** | **0.06** |

`atm_display`의 톤매핑을 같이 통과시켜야 하늘과 같은 축에서 비교됩니다.
**핵심 결과**: 낮에도 땅은 하늘보다 어둡고, 해 질 녘에는 훨씬 어둡습니다.

### 4-3. 지형을 거리별 실루엣으로

이미 `panoramicAngles`(5·15·40km 최대)와 `farAngles`가 있습니다. 지금은
전자만, 그것도 8°로 잘라 씁니다.

- 상한 8°를 올립니다. 8°는 관측점에서 5km 떨어진 700m 산까지밖에 못 담습니다.
- **거리대별로 링을 나눠** 각각 `atm_aerialTransmittance`를 다르게 겁니다.
  가까운 능선은 짙고 먼 능선은 하늘색에 잠깁니다 — 이 하나로 깊이가 생깁니다.
- 능선 사이에 옅은 띠(계곡 안개)를 넣으면 겹침이 더 읽힙니다.

### 4-4. 바다 — 공짜로 얻는 신호

**Open-Meteo elevation API는 해상에서 정확히 `0.0`을 반환합니다.** 실측:

```
36.0N 126.0E (서해)   → 0.0
36.0N 124.5E (서해)   → 0.0
37.57N 126.98E (서울) → 27.0
35.18N 129.08E (부산) → 26.0
33.36N 126.53E (한라) → 1904.0
```

육지는 0이 아닌 정수로 돌아옵니다. 즉 **새 데이터원 없이** 31방위 × 3거리에서
바다 여부를 바로 읽을 수 있습니다.

방위별로 "가장 가까운 물 거리"를 구하면 해안선까지 나옵니다. 그 방위에서는
지형선 대신 **수평선**을 그립니다 — 수평선은 지형선과 달리 완벽하게 평평하고
관측점 고도로 각도가 정해집니다:

```
수평선 각도 = −acos(R / (R + 관측고도))     (관측고도 30m → −0.18°)
```

⚠ 한계: 해수면 높이의 해안 평야도 0으로 읽힐 수 있습니다. 드물고, 시각적으로
물 근처라 실패해도 크게 어긋나지 않습니다. 다만 **문서에 남깁니다.**

### 4-5. 윤슬

물이 강력한 이유가 여기 있습니다. 물의 알베도는 0.06으로 아주 낮지만,
**정반사 방향에서만은 아주 높습니다.** 그 대비가 윤슬입니다.

파면 경사 분포는 Cox-Munk (1954)가 풍속의 함수로 줍니다:

```
σ² = 0.003 + 0.00512 · U        (U = 10m 고도 풍속, m/s)
```

경사가 가우시안이면 정반사가 일어나는 면의 비율이 곧 밝기이고, 프레넬로
반사율을 곱합니다. 낮은 태양에서 프레넬 반사율은 급격히 커집니다
(수직 입사 0.02 → 입사각 85°에서 0.6 이상). **해 질 녘 물이 타오르는 이유가
정확히 이것입니다.**

풍속이 낮으면 좁고 날카로운 기둥, 높으면 넓고 부드러운 띠가 됩니다.

> ⚠ **앱은 아직 바람을 안 받아옵니다** (`CLOUD_TEXTURE_PLAN.md` §15).
> 지금은 `PLACEHOLDER_WIND_SPEED_KMH`를 쓰게 되고, 그건 윤슬 폭이 실제
> 바람을 안 따른다는 뜻입니다. 6단계 권운 이방성과 **같은 자리표시자를
> 공유**하므로, 실측 바람을 넣으면 둘이 동시에 진짜가 됩니다.

### 4-6. 내륙 수역 — 여기서 멈춥니다

호수·강은 elevation만으로는 안 나옵니다. 수면도 0이 아닌 고도로 돌아오니까요.
"주변보다 낮고 평평한 구역"으로 추정할 수는 있지만 오검출이 많습니다.

제대로 하려면 OpenStreetMap Overpass(`natural=water`) 같은 **새 네트워크
의존**이 필요합니다. 바다만으로도 노을 사진의 상당수를 덮으므로, 내륙 수역은
바다가 자리 잡은 뒤에 별도로 판단합니다.

## 4-B. 2단계 결과 (완료)

### 두 축이 달라서 상수를 맞출 수밖에 없었습니다

지면이 `MeshBasicMaterial` + 정점색이라 **`atm_display`를 통과하지 않았습니다.**
하늘만 톤매핑과 눈 순응을 거치니 두 밝기를 비교할 방법이 아예 없었고, 그래서
`nightG` / `dayG` / `goldenG` 를 손으로 맞출 수밖에 없었던 것입니다.

지면을 셰이더로 바꿔 같은 경로를 통과시키고, 밝기를 물리로 냅니다:

```
지면 휘도 = (하늘 조도 + 직달 조도) × 알베도 / π
```

하늘 조도는 `E = π·L̄` 이라 나눗셈이 상쇄되어 `L̄ × 알베도` 가 됩니다.

### 렌더가 잡아낸 것

**1. `gl_Position`에 `modelMatrix`를 빼먹었습니다.** 스카이돔은 변환이 없는
메시라 그 VERT에는 `modelMatrix`가 없습니다. 그걸 그대로 흉내 냈더니 원반이
회전(`-π/2`)·이동(`y=-8`) 전 자리, 즉 **수직면**에 그려져 지평선 아래가
통째로 비었습니다. tsc는 통과합니다.

**2. 균등 평균을 내서 지면이 초록이었습니다.** 수평면이 받는 조도는
`∫L·cosθ dΩ` 라 **천정 쪽이 크게** 기여합니다. 코사인 가중 없이 평균을 내면
지평선의 노을빛을 과대 반영합니다. 가중을 넣고 알베도를 따뜻한 쪽으로
기울여 이끼색을 없앴습니다.

**3. 물리적으로 맞는 값이 검은 띠가 됐습니다.** 지면 복사휘도는 하늘의
알베도 배(≈0.2)라 **톤 곡선의 발끝**에 박힙니다. ACES의 발끝은 거의 이차식
이라 rgb(0,1,1)이 나왔습니다. 사진에서 전경이 새까만 건 사실이지만 사람 눈은
**국소로 순응**합니다 — 노을을 보다 발밑을 보면 땅이 보입니다. 사진가가
그래듀에이티드 ND를 쓰는 것과 같은 이유로 지면에만 노출을 올립니다.
알베도를 부풀리는 것과 달리 물리를 안 고치고 **표시만** 고치는 선택이라
`GROUND_EXPOSURE` 한 상수로 분리했습니다 (렌더로 훑어 ×2.2).

### 회색 판때기를 면하는 법 — 방위별 전방산란

지면은 램버시안이 아닙니다. 풀·아스팔트·젖은 표면 모두 태양 쪽으로 강한
전방산란 로브를 갖습니다. 이 항이 없으면 지면이 방향에 무관한 한 색이 되어
회색 판때기가 됩니다 — **실루엣을 못 그리는 만큼, 이 각도 의존성이 "표면임"을
알려주는 몇 안 되는 단서입니다.**

측정: 태양 쪽이 반대쪽보다 **1.72배** 밝습니다.

| 지표 | 고치기 전 | 지금 |
|---|---|---|
| 지면 원반을 빼도 바뀌는 최대 픽셀차 | 1 | **178** |
| 지면 / 하늘 휘도비 | 98% | **32%** |
| 지평선 아래 채도 | 47% | **8%** |
| 태양 쪽 / 반대쪽 | 1.00 | **1.72** |

## 4-C. 3단계 결과 (완료)

### 지형 링도 한 번도 안 보이고 있었습니다

지면 원반과 **같은 종류의 버그가 하나 더** 있었습니다. `createTerrainRing`의
재질이 `side: THREE.FrontSide` 인데, 이 링은 관측자를 둘러싼 원통이라 항상
**안쪽에서** 봅니다. 감김 방향상 안쪽이 뒷면이라 통째로 컬링됐습니다.

검은 배경에 지형만 그려 픽셀을 세니 **0**이었습니다. 코드를 읽어서는 안
잡히고, 단독으로 그려 세어야 드러나는 종류입니다.

### 거리별 대기 투시

`bandAngles[거리대][방위]`를 새로 내보냅니다. 예전에는 세 거리(5·15·40km)의
지형각을 `panoramicAngles` 하나로 **최댓값 압축**해서, "가까운 언덕 뒤에 먼
산"이 사라지고 대기 투시를 걸 대상도 없었습니다. 이미 계산하던 값이라
내보내기만 하면 됩니다.

거리대마다 링을 하나씩 만들고 **먼 것부터** 그립니다. 각 링은 자기 거리의
`atm_aerialTransmittance`로 연무에 잠깁니다.

측정 (하늘색과의 평균 차이, 지평선 위만):

| 거리대 | 하늘 대비 |
|---|---|
| 5 km | **70.4** |
| 15 km | 24.9 |
| 40 km | **7.7** |

가까운 능선이 먼 능선보다 **9.1배** 뚜렷합니다.

### 렌더가 잡아낸 것

**1. 각도가 아니라 높이에서 출발해야 합니다.** 미리보기 지형을 각도로 손수
정했더니 40km에 8.9°짜리 산이 생겼습니다 — 높이로는 **6.3km**입니다. 실제로는
먼 산일수록 각이 **작습니다**: 1000m 산이 5km에서 11.3°, 15km에서 3.8°,
40km에서 1.4°. 그래서 실제 지평선은 비슷한 각도의 낮은 능선이 여러 겹 겹친
모습이고, **겹침은 크기가 아니라 연무 대비로 읽힙니다.**

**2. 연무색을 방위 하나로 고정하면 안 됩니다.** 처음에 태양 쪽 지평선
하늘색 하나를 온 방위에 썼더니, 먼 능선이 자기 뒤 하늘과 색이 어긋나 경계가
생기고 반대쪽은 엉뚱하게 밝아졌습니다. 정점 속성으로 **방위·고도별** 하늘색을
받아 "자기 뒤 하늘에 잠기게" 했습니다.

**3. 띠를 지평선 아래까지 내리면 지면을 덮습니다.** 처음에 −30°까지 내렸더니
띠가 지면 원반 위에 그려져(띠가 나중), 지평선 아래 전부가 "5km 대기 투시를
먹은 색"이 됐습니다. 발밑 땅은 5km가 아니라 수십 미터 앞이라 연무가 거의
없는데도요. 태양 쪽을 볼 때 특히 어긋납니다 — 어두워야 할 전경이 밝아집니다.

**4. 측정을 지평선 아래가 지배했습니다.** 대비를 화면 전체로 재니 거리 순서가
**거꾸로** 나왔습니다 (40km가 가장 대비 높음). 띠가 셋 다 지평선 아래까지
내려오기 때문입니다. 능선이 사는 곳은 지평선 바로 위이므로 거기만 재야 합니다.

### ⚠ 이 단계는 화면에서 작습니다

실제 지형각은 **몇 도**뿐입니다. 넓은 화각으로 보면 능선이 몇 픽셀이라
거의 안 보입니다 — 그게 거짓이라서가 아니라 실제로 그만큼 작기 때문입니다.
미리보기는 화각 14°로 **확대해서** 보여 줍니다.

큰 전경(1km 이내의 나무·건물)이 사진을 극적으로 만드는데, DEM은 5km부터
시작하므로 그 자료가 없습니다. 그건 §5의 "안 할 것"에 해당합니다.

## 4-D. 4·5단계 결과 (완료)

### 바다는 공짜로 검출됩니다

`weather.ts`가 이미 받아오는 elevation에서 **해상은 정확히 `0.0`** 입니다.
`waterFrac[방위]` 를 새로 내보내 방위별 수역 비율로 씁니다. 새 네트워크
의존이 없습니다.

수평선은 관측 고도 하나로 정해집니다 — `dip = acos(R/(R+h))`, 30m에서
**0.176°**. 지면 원반의 가장자리가 곧 보이는 지평선이므로, 원반 깊이를
그 각도에 맞춰 내립니다. 예전에는 `y = −8` 고정(가장자리 −0.95°)이라
**5배 아래**에 있었습니다 — 육지에서는 지형이 가려 안 보이지만 바다에서는
바로 드러납니다.

### 물의 밝기 — 낮은 알베도와 프레넬의 대비

| | 수면 평균 휘도 |
|---|---|
| 육지 | 70.3 |
| 바다 (태양 쪽) | **124.5** |
| 바다 (태양 반대쪽) | **50.2** |

물은 알베도가 0.06으로 아주 낮아 **반대쪽에서는 육지보다 어둡습니다.**
그런데 스치는 각에서는 프레넬 반사율이 1에 가까워져 하늘을 그대로 비추므로
태양 쪽에서는 육지보다 밝습니다. 이 대비가 물의 전부입니다 — 그래서 검사도
양쪽을 다 봅니다. 한쪽만 보면 "물을 그냥 밝게 칠했다"와 구분이 안 됩니다.

### 윤슬 — 잔물결을 안 그리고 분포만 씁니다

파면 하나하나는 못 그리지만 **경사의 분포**는 압니다. Cox & Munk (1954):

```
σ² = 0.003 + 0.00512 · U        (U = 10m 풍속, m/s)
```

눈과 태양을 잇는 반벡터가 그 지점에서 정반사를 일으키는 면의 법선입니다.
그 법선이 수직에서 기운 정도를 가우시안에 넣으면 그런 경사를 가진 면의
비율 = 그 방향의 밝기가 됩니다.

| 풍속 | 윤슬 폭 | 봉우리 |
|---|---|---|
| 2 m/s | **4.9°** | +40.1 |
| 8 m/s | **11.2°** | +54.5 |
| (태양 반대쪽) | 0° | +0.6 |

### 렌더가 잡아낸 것

**1. 수평선 하늘 하나로 되비추면 안 됩니다.** 지형 연무와 **똑같은 실수**를
반복했습니다 — 수평선 하늘색 하나를 모든 시선각에 썼더니 수면 전체가
노을색으로 포화돼(평균 238/255) 윤슬이 파묻혔습니다. 고도 −10°로 내려다본
물은 **+10° 하늘**을 비추지 수평선을 비추지 않습니다. `atm_skyRadiance`를
셰이더 안에서 거울 방향으로 직접 부릅니다.

**2. 화각이 좁으면 윤슬 폭을 못 잽니다.** 화각 24°로 찍었더니 2 m/s와
8 m/s 둘 다 프레임을 채워 "폭이 안 변한다"로 보였습니다 (0.515 vs 0.565).
σ로 계산하면 각각 약 13°와 24°라 24° 화각에 안 들어갑니다.

**3. 가장 밝은 곳은 윤슬이 아닙니다.** "가장 밝은 행의 절반 문턱 폭"으로
쟀더니 풍속을 4배 올려도 0.43 → 0.43. 수면에서 가장 밝은 곳은 **수평선
거울 띠**입니다.

**4. 톤 곡선이 에너지 보존을 깹니다.** 두 풍속의 차이를 봤더니 중심이
음수(−9.3)로 나왔습니다. 선형에서는 약풍이 중심에서 밝아야 하는데요.
ACES는 좁고 밝은 봉우리를 더 세게 압축하므로 **퍼진 쪽이 표시상 더
밝아집니다.** 그래서 봉우리 높이로는 판정하지 않고, 자기 바닥에서 고정
높이만큼 올라온 **폭**만 봅니다 — 그건 톤 곡선에 안 휘둘립니다.

### ⚠ 바람이 자리표시자입니다

윤슬 폭은 풍속에서 나오는데, **앱은 아직 바람을 안 받아옵니다**
(`CLOUD_TEXTURE_PLAN.md` §15). 권운 이방성과 **같은 자리표시자**
(`PLACEHOLDER_WIND_SPEED_KMH`)를 씁니다 — 실측 바람을 넣으면 둘이 동시에
진짜가 됩니다.

## 4단계 — 땅이 낮게 서던 이유 (48절)

> "육지 데이터는 잘 받아오고 있는데 자꾸 땅이 실제 해수면 대비 고도보다 낮게
> 나오거나 땅과 물의 경계면이 어색하고 땅과 물의 렌더링도 어색해"

자료가 아니라 **자료를 각도로 바꾸고 그리는 쪽**에 결함이 셋 있었습니다.
셋 다 `verify-terrain-water.js` 로 잡히고, 고치기 전에는 그 판정이 실제로
깨집니다(아래에 예전 값 같이 적음).

### 4.1 물이 능선 높이를 곱으로 깎고 있었습니다 — 가장 큰 것

```js
topDeg = topDeg * (1 - Math.min(1, water * 1.4));   // 예전
```

`water` 는 **세 거리(5·15·40km)를 하나로 뭉갠** 수역 비율입니다. 그런데 물은
그 거리대에서만 물입니다. 만 너머에 산이 있는 방위는 5km 가 물이라
`water = 1/3` 이 되고, 그 곱이 **40km 의 산에까지** 걸립니다.

| 상황 | water | 능선 높이 | 500m 산 40km (0.49°) |
|---|---|---|---|
| 전부 육지 | 0 | ×1.000 | 0.493° |
| **5km 만 바다 (만 너머 산)** | 1/3 | **×0.533** | **0.263°** |
| 5·15km 바다 (먼 섬) | 2/3 | ×0.067 | 0.033° |
| 전부 바다 | 1 | ×0.000 | 0° |

사용자가 말한 "땅이 실제 고도보다 낮게 나온다"가 이것입니다.

**고침.** 물을 `bandWater[거리대][방위]` 로 들고 다니고, 능선을 **줄이는**
것이 아니라 **바다 수평선으로 바꿉니다.**

```js
topDeg = topDeg * (1 - water) + seaHorizonDeg * water;
```

그 자리에 실제로 있는 것이 해수면이기 때문입니다. 줄이기(×)로는 물이 반쯤
섞인 방위가 "낮은 육지"가 되는데, 그런 지형은 없습니다.

### 4.2 지형각에 지구 곡률이 빠져 있었습니다

```js
const angle = Math.atan2(elev - observerElev, distMeters);   // 예전
```

멀리 있는 지면은 발밑으로 휘어 내려갑니다. 낙차 `d²/2R` 은 5km 에서 2m 지만
**40km 면 108m** 입니다.

| 거리 | 예전 (해발 0) | 곡률 넣으면 | 곡률 낙차 |
|---|---|---|---|
| 5km | −0.344° | −0.363° | 2m |
| 15km | −0.115° | −0.172° | 15m |
| **40km** | **−0.043°** | **−0.197°** | **108m** |

관측 30m 의 진짜 바다 수평선은 −0.176° 입니다. 곡률이 없으면 40km 의 해수면이
−0.043° 로 읽혀 수평선보다 **위**에 뜹니다 — 능선 띠와 지면 원반이 서로 다른
수평선을 그리니 경계가 어긋납니다.

⚠ `R` 은 `TerrainRing.seaHorizonDipDeg` 와 **같은 값**을 씁니다. 44절에서
지면과 구름이 서로 다른 지평선을 써서 0.79° 짜리 띠가 벌어진 적이 있습니다.
둘 다 대기 굴절은 아직 안 넣었고, 넣을 때는 **같이** 넣어야 합니다.

### 4.3 수역 마스크와 능선이 서로 다른 방위를 가리켰습니다

```js
const t = (i / N) * waterFrac.length;      // 예전 — 마스크
const angleIdx = azFrac * (angles.length - 1);   // 능선
```

표본 배열은 `minAz + i·range/(SAMPLES−1)` 로 만들어져 **0°와 360°가 중복**
됩니다(31개 중 0번과 30번이 같은 방위). `length` 로 나누면 360°를 31분의 30 에
욱여넣는 셈이라 방위가 어긋납니다. 즉 **물이라고 칠한 자리와 능선이 접힌
자리가 달랐습니다.**

판정은 경계 위치가 아니라 **매핑 자체**를 잽니다 — 텍스처 칸마다 그 방위에서
원본을 보간한 값과 견줍니다. 고친 뒤 최대 오차 **0.0017**, 예전 **0.5137**.

> ⚠ 처음에는 "마스크의 경계 방위"와 "능선의 경계 방위"를 각각 찾아 견주는
> 판정을 썼는데, 두 격자(64칸 = 5.625° 대 72분절 = 5°)의 양자화에 묻혀
> **예전 매핑에 더 좋은 점수를 줬습니다**(0.6° 대 6.3°). 잣대를 버리고
> 매핑을 직접 재는 것으로 바꿨습니다.

### 4.4 곁가지 둘

- `Math.max(raw, 0)` 로 **음수 지형각을 0 으로 잘랐습니다.** 관측자보다 낮은
  골짜기도 바다도 전부 지평선에 딱 붙어, 수평선 자리에 육지색 띠가 얹혔습니다.
  이제 곡률까지 넣은 진짜 각을 그대로 씁니다.
- `botDeg = -2.5` 고정. 주석은 "지면 원반의 가장자리가 −0.95°"라고 적혀
  있었는데 원반은 `setGroundHorizon` 이 **관측 고도로** 내립니다(30m → −0.176°).
  주석이 낡아 상수도 같이 낡았습니다. topDeg 가 음수로 갈 수 있게 되었으므로
  띠의 실제 최저각보다 내리도록 바꿨습니다.

### 4.5 판정

`verify-terrain-water.js` — `createTerrainBands` 가 만든 **실제 정점**을 읽습니다.

| # | 재는 것 | 고친 뒤 | 예전 |
|---|---|---|---|
| ① | 만 너머 산이 제 높이 | 0.493° | 0.263° ❌ |
| ② | 물이 바다 수평선에 (세 거리대) | −0.176° | 0.000° ❌ |
| ③ | 띠가 뒤집히지 않음 | 여유 2.32° | 2.50° |
| ④ | 육지 방위는 그대로 | 0.964° | 0.964° |
| ⑤ | 마스크 방위 매핑 | 오차 0.0017 | 0.5137 ❌ |

### 4.6 남은 한계

- **방위 해상도 12°.** 표본이 31개(0~360°)뿐이라 칼같은 해안선을 12° 보다
  가늘게 그릴 수 없습니다. Open-Meteo elevation 은 한 번에 좌표 100개인데
  지금 `1 + 31×3 = 94` 로 거의 찼습니다. 늘리려면 요청을 두 번으로 나눠야
  합니다(61 표본이면 6°). 지연과 맞바꾸는 선택이라 그대로 뒀습니다.
- **해수면 높이의 해안 평야는 물로 읽힙니다** (`elev === 0`). 예전부터 있던
  한계이고 그대로입니다.
- 대기 굴절 미반영(4.2 참고).
