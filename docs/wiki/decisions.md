# 결정 · 사용자 선호 — 지켜야 할 것

한 줄: 사용자와 정한 방향. 새 작업 전에 읽을 것. 갱신: 2026-11-26

## 소통
- 한국어로 답함(영어로 쓰면 "한국어로 말하라고" 지적). 쉬운 말, 짧게.
- 결과가 나오면 **비교 이미지**를 보여 줄 것(전 · 후, 여러 장면).
- 잘못 진단했으면 바로 밝히고 고칠 것(예: "층적운 3배 얇다" 철회, §25.9).

## 렌더 원칙
- **고도 · 상황별 특수 스위치를 피하고 일반 물리로**(2026-11-25: "일반적으로 구름에 그림자를 생성하는 로직이 충분히 그런 역할을").
- 가장자리 빛 · 색은 하드코딩이 아니라 빛 계산에서(붉은 가장자리 gRim 삭제).
- 구름 외곽은 **기본을 거칠게**(매끈하게 다듬기보다, 2026-11-26).
- 무거운 계산은 근사를 찾되, 해 쪽 추적이 프레임 드롭 원인 — 비용을 늘 같이 말할 것.
- **끄는 중에만 걸음 · 계산을 줄이는 근사는 피함**(손을 떼면 차이가 커서). 같은 계산을 미리 · 덜 자주 하고 재사용(2026-11-26).
- 실험은 옵션 · 기본 끔으로 넣고, 판정 후 켬. 끄면 바이트 동일.
- 사실주의를 내려놓고 "읽히는 하늘"(§43) — 단, 최근에는 물리 근거를 우선.

## 작업 방식
- PR 은 초안으로, 사용자가 "병합"이라고 할 때 병합(2026-11-26 #167 · #169 · #170 · #168 을 한꺼번에 병합하라고 함).
- 사용자가 앱을 바로 빌드할 수 없을 때는 원인을 가정하고 하네스로 미리 작업해도 됨(2026-11-26).
- 진단용 임시 코드는 PR 에 넣지 않음(별도 브랜치 · stash).
