# 정보 구조 재설계 (IA Redesign)

3D 시뮬레이터가 2D 시뮬레이션·구름 추적·별 추적의 기능을 흡수하면서 생긴
"표면 중복" 문제를 정리합니다. 결론부터: **문제는 3D가 2D를 잡아먹은 게 아니라
표면이 7개라는 것**입니다.

---

## 1. 현재 구조의 문제

### 1-A. 탐색이 2단계이고, 1단계가 모달입니다

`HudHeader`가 **카테고리 드롭다운(모달)** × **서브탭** 구조입니다.

| 카테고리 | 서브탭 |
|---|---|
| sun | tracker, sim, isoline |
| cloud | tracker(구름), rainbow 🔒 |
| star | tracker 🔒 (카테고리 전체 비활성) |
| sim3d | sim3dView |
| gallery | all, my |

2D 시뮬에서 3D 시뮬로 가려면 **카테고리 버튼 → 모달 열림 → 3D 선택 → 모달 닫힘**.
한 번의 탭이어야 할 이동이 3탭 + 모달입니다. 둘 다 "하늘을 본다"는 같은 일인데도요.

### 1-B. 스와이프 순서가 구조와 어긋나 있습니다

```ts
const tabOrder = ['tracker', 'sim', 'isoline', 'rainbow', 'all', 'my'];
```

카테고리를 무시한 평면 배열입니다. 그래서:

- `sim`에서 스와이프하면 `isoline` → `rainbow`(cloud 카테고리) → `all`(gallery)로
  **카테고리 경계를 넘어가는데 `selectedCategory`는 갱신되지 않습니다.**
- **`sim3dView`가 tabOrder에 아예 없습니다.** 3D는 스와이프로 오갈 수 없습니다.
- 스와이프 자체가 `selectedCategory !== 'sun'`이면 차단됩니다.

### 1-C. 같은 탭 id가 다른 화면을 뜻합니다

`tracker`가 sun에서는 `CelestialChart`, cloud에서는 `CloudTrackerChart`를 렌더합니다.
탭 id와 화면이 1:1이 아닙니다.

### 1-D. 죽은 표면

`rainbow`는 영구 비활성(`disabled: true`), `star` 카테고리는 통째로 비활성입니다.
드롭다운 5개 중 1개가 자물쇠, 서브탭 중 2개가 자물쇠입니다.

## 2. 재설계 원칙 — 시뮬레이터 개수가 아니라 **공간 프레임**

화면을 "무엇을 시뮬레이션하나"가 아니라 **"어떤 시점에서 묻는 질문인가"** 로 나눕니다.
이 축은 서로 겹치지 않습니다.

| 프레임 | 시점 | 답하는 질문 | 왜 다른 프레임이 대신 못 하나 |
|---|---|---|---|
| **하늘** | 자기중심 (돔 안) | "뭐가 보일까" | 지도는 하늘의 모습을 못 보여줌 |
| **지도** | 타자중심 (위에서) | "뭐가 오고 있나 / 어디로 갈까" | 돔 안에서는 200km 밖 구름의 이동을 볼 수 없음 |
| **기록** | 시간축 | "뭘 봤나" | — |

구름 추적기가 3D로 대체되지 않는 이유가 여기 있습니다. "저 구름이 제시간에
걷힐까"는 **자기중심 시점으로는 구조적으로 답할 수 없는** 질문입니다.

## 3. 새 구조

드롭다운을 없애고 **평면 3탭**으로 만듭니다.

```
┌──────────────────────────────────────┐
│  하늘  │  지도  │  기록      ⚙  📷   │  ← 평면 3탭 + 유틸
│  ‹ 2026/08/03 ›              오늘    │  ← 날짜 (기록 탭에서는 숨김)
└──────────────────────────────────────┘
```

| 새 탭 | 흡수한 것 | 비고 |
|---|---|---|
| **하늘** | `sim3dView` + `sim`(2D) + `tracker`(천구 차트) | 3D가 주 뷰, 나머지는 시트 안 수치로 |
| **지도** | `isoline` + `tracker`(구름) | 등시선 위에 구름 이류를 얹음 |
| **기록** | `all` + `my` | 내부 세그먼트 토글 |
| ~~rainbow~~ | 삭제 | 영구 비활성 자리표시자였음 |

스와이프 순서는 `['sky', 'map', 'log']` — 탭 순서와 정확히 일치하고,
카테고리 개념이 없으므로 어긋날 수가 없습니다.

## 4. 하늘 탭 레이아웃

작은 화면 대응의 핵심은 **나누지 말고 순서를 만드는 것**입니다.
지금은 씬 + 이벤트 박스 + 슬라이더가 세로로 쌓여 공간을 다투고 있습니다.

```
┌─────────────────────────┐
│                         │
│                         │
│     3D 돔 (full-bleed)  │  ← flex:1, 가장자리까지
│                         │
│  [나침반]        [레이어]│  ← 씬 위 오버레이만
│                         │
├─────────────────────────┤
│ ▔▔▔                     │  ← grabber
│ 87점 · 19:34 · 상층운 45%│  ← peek 한 줄
├─────────────────────────┤
│ ◀━━━━●━━━━▶  시간       │  ← 상시 노출
└─────────────────────────┘
```

- **상시 노출은 타임 슬라이더 하나만.** 시간 스크럽이 이 앱의 핵심 인터랙션입니다.
- **나머지는 peek 시트.** 닫힌 상태에서 한 줄 요약, 끌어올리면 근거와 수치.
  - 예측 카드 (점수·근거)
  - 태양/달 수치 (고도·방위·출몰)
  - 이벤트 목록 (탭하면 그 시각으로 이동)
- **레이어 토글은 씬 위 아이콘 하나.**

### 왜 수치를 별도 탭으로 빼지 않나

빼면 앱이 "예쁜 3D + 스펙시트"가 됩니다. 이 앱의 차별점은 시각화가 아니라
**예측**입니다. 3D는 예측을 보여주는 렌더러여야지, 예측이 3D의 부속이 되면 안 됩니다.

그래서 기본 카메라는 일몰 방위를 향하고, 점수가 화면에서 사라지지 않습니다.
탐험(자유 회전·별·은하수)은 그다음 동작입니다.

## 5. 2D 렌더러의 자리

탭에서는 내리지만 **삭제하지 않습니다.** 이미 탭이 아닌 곳 3군데에서 쓰입니다:

| 소비처 | 용도 |
|---|---|
| `SunCamera.tsx` | 오프스크린 렌더 → 스냅샷 → AR 오버레이 |
| `useCelestialApp.ts` | `compressToWidgetSizes` → 홈 위젯 이미지 |
| `Gallery`/`PostDetailModal` | 사진마다 붙는 `simulationImageUrl` (영구 기록) |

GL 컨텍스트를 위젯용으로 싸게 스냅샷할 수 없고, 갤러리의 사진별 시뮬 이미지는
이미 저장된 기록 포맷입니다. 즉 2D는 **이미지 생산 파이프라인**이고,
동시에 GL이 실패하는 기기의 **폴백**입니다. 매일 쓰이므로 썩지 않습니다.

다만 2D의 **10~30° 좁은 화각 프레이밍**은 잃으면 안 됩니다. 그건 "하늘 탐험"이
아니라 "사진가의 뷰파인더"고, 3D의 60° 탐험 뷰와 다른 물건입니다.
3D 카메라 프리셋으로 옮깁니다.

## 6. 단계

| 단계 | 내용 | 위험도 |
|---|---|---|
| **A** | 평면 3탭 셸 + 하늘 탭 레이아웃(peek 시트) | 중 — 셸 교체 |
| **B** | 지도 통합 (등시선 + 구름 이류 오버레이) | 낮 — 기존 지도에 레이어 추가 |
| **C** | 3D 카메라 프리셋(뷰파인더/탐험), 씬 탭 → 수치 | 낮 — 기능 추가 |

회귀 범위가 셸에 갇힙니다.

## 8. 강화 구름 격자 어댑터 (격차 1~3 해소)

### 왜 어댑터인가

격자는 2D 전용이었습니다. 그런데 **2D 전용이었던 건 격자가 아니라
격자의 마지막 단계**입니다:

```
fetchCloudGrid          → CloudDensityGrid   ← 기상 필드. 3D도 먹을 수 있음
  └ convertGridToClouds → GridCloudShape[]   ← SVG 폴리곤. 여기서 2D에 갇힘
```

폴리곤은 화면 좌표에 고정된 최종 산출물이라 돔에 붙일 수 없습니다.
하지만 그 **직전** 단계인 `CloudDensityGrid`는 (방위 오프셋, 거리) → 저·중·상층
운량이고, 이건 3D가 이미 `WeatherFan`으로 먹고 있는 `CloudData`와
필드 이름만 다릅니다. 그래서 폴리곤화 앞에서 갈라내면 됩니다.

`src/utils/cloudGridAdapter.ts` — `cloudGridToFan()`.

| | 레이 | 고리 | 점 |
|---|---|---|---|
| 기본 팬 | 5 (±20°) | 7 (10~380km) | 35 |
| 강화 격자 | 7 (±30°) | 10 (10~380km) | 70 |

### 어댑터가 실제로 하는 세 가지

단순 필드 이름 바꾸기가 아닙니다. 세 가지가 없으면 켜는 순간 오히려 나빠집니다.

**① 방위 보정.** 격자의 `azOffset`은 *받을 때의* 태양 방위(`grid.azCenter`)
기준인데, `WeatherFan`은 *현재* 태양 방위 기준으로 해석합니다. 격자는 방위 10°
버킷으로 10분간 캐시되므로 둘은 어긋납니다. 보정 없이 넘기면 하늘 구조 전체가
그 차이만큼 회전합니다 — 측정하면 절대 방위별 운량이 최대 **51%p** 틀어집니다.
보정하면 0.0%p입니다.

**② 관측점 앵커.** 격자의 첫 고리가 10km라 그보다 가까운 방향은
`alongRay`의 하한 클램프에 걸려 10km 값을 씁니다. 저층운(고도 1.5km)은
고도각 8.5° 위쪽 **전부**가 10km 안이므로, 머리 위가 통째로 10km 밖 하늘로
채워집니다. 측정: 관측점이 맑고 10km 밖이 95%일 때 머리 위가 **92.6%** 로
나왔습니다. 레이마다 0km 앵커를 붙이면 **1.5%** 가 됩니다.
(0km는 모든 레이가 만나는 같은 지점이므로, 레이 하나에만 붙이면 안 됩니다 —
부채꼴 이음매가 생깁니다.)

부가 관측값(DNI·습도·강수·시정)도 관측점에만 있습니다. 이게 빠지면
`resolvePresetFromWeather`가 비구름을 못 고르고 `cloudTauFromDNI`가 null을
돌려줘서, 강화 격자를 켠 순간 물리가 퇴화합니다.

**③ 시간축 유지.** 원래 `fetchCloudGrid`는 응답의 hourly 배열을 `targetTime`
한 점으로 보간하고 버렸습니다. 격자는 (위도, 경도, 방위버킷)으로만 캐시되므로
**시각이 캐시 키에 없습니다** — 타임 슬라이더를 움직이면 조용히 낡은 구조를
보게 됩니다. hourly 배열을 그대로 들고 있게 바꿨습니다. 같은 응답에 이미 들어
있던 값이라 추가 비용이 없고, `interpolateCloudGrid()` 로 아무 시각이나
다시 읽습니다. 재요청이 사라집니다.

### 어디에 붙었나

하늘 탭 씬 위 **레이어 아이콘** (⚡ 초단기 실황 옆). 켜면 `SkyScene3D`에
넘기는 `interpolatedWeather`가 격자 기반으로 바뀝니다.
격자 중심과 현재 태양 방위가 25° 넘게 벌어지면 (`isGridUsable`) 자동으로
기본 팬으로 되돌아갑니다 — ±30° 부채꼴이 하늘의 엉뚱한 쪽에 얹히면
기본 팬보다 나쁘기 때문입니다.

### 측정 결과

`tools/shader-preview/verify-cloud-grid.js` (23개 통과) 및
`build-grid-preview.js` — 같은 "진짜 하늘"을 두 관측 밀도로 본 A/B 렌더.

| 측정 | 기본 팬 | 강화 격자 | 해석 |
|---|---|---|---|
| 실측 신뢰 방향 비율 | 12.5% | 20.8% | 하늘의 실측 영역 1.66배 |
| 상층 40~70km 맑은 띠 대비 | 0.091 | 0.226 | 고리 간격(30→70)이 뭉갠 구조를 격자(35/55/80)가 살림 |
| 상층 방위 30° 띠 운량 | 0.635 | 0.805 | ±20° 밖은 기본 팬이 못 보던 영역 |
| 태양 투과율 (태양 6°) | 0.328 | 0.442 | 태양 경로의 중층 틈을 격자만 해상 |

### 이건 안 됐습니다 (측정으로 확인)

**저층운에는 방위 폭 확대가 거의 영향이 없습니다.** 방위 30° 띠의 저층 운량이
0.474 → 0.467 로 사실상 같았습니다.

이유는 기하입니다. 저층운 고도가 1.5km라 하늘에서 차지하는 영역이 전부
반경 24km 안이고, 그중 8개 고도 고리 중 7개가 10km(격자 첫 고리) 안쪽입니다.
그 구간은 위 ②의 관측점 앵커가 지배합니다. 즉 **저층은 관측점 값이 결정하고,
격자가 버는 건 중·상층과 태양 방향 기둥**입니다.

관측 밀도를 올려도 저층이 나아지지 않는다는 뜻이므로, 저층을 개선하려면
격자의 첫 고리를 10km보다 안쪽(2~5km)으로 넣어야 합니다. 지금은 안 했습니다.
