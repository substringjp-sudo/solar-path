# 하루치 사전 계산 (Sky Timeline)

"매번 다시 계산하지 말고, 버튼 한 번에 하루치를 다 계산해 두고
이후에는 렌더만" 을 구현한 기록입니다.

---

## 1. 무엇이 실제로 느렸나

먼저 재봤습니다. 구름 재빌드 1회는 **모바일 추정 7ms** 입니다 — 이건 병목이
아니었습니다. 진짜 원인은 네트워크였고, 원인의 모양이 특이했습니다.

```ts
fetchSunsetWeather(lat, lon, bucketedSunAz, ...)
const cacheKey = `${lat},${lon},${bucketedAzimuth}_..._${date}`;
```

날씨 팬이 **태양 방위 중심**이라 캐시 키에 방위 버킷(30°)이 들어갑니다.
시간을 옮기면 태양 방위가 버킷을 넘어가고, 그때마다 캐시 미스입니다.
하루를 스크럽하면 방위가 180° 넘게 도니 **같은 날 같은 장소인데도 6번 이상
새로 받습니다.** "날씨를 매번 받아온다"의 정체가 이것이었습니다.

---

## 2. 팬 대신 링

방위 의존을 없애려면 관측 자체가 방위에 무관해야 합니다.

| | 레이 | 고리 | 방위 커버 |
|---|---|---|---|
| 기존 팬 | 5 (±20°) | 7 | 태양 방향 40°만 |
| 링 (`fetchDayWeatherRing`) | 12 (30° 간격) | 7 | **360° 전부** |

`(위경도, 날짜)`당 요청 1건이면 끝입니다. 덤으로 품질도 올라갑니다 —
팬은 ±20° 밖을 관측점 값 + 노이즈로 메웠는데(신뢰도 0), 링은 전 방위가
실측입니다.

`azimuthOffset`에 **절대 방위**(-180~180)를 담으므로 `new WeatherFan(ring, 0)`
으로 감싸면 됩니다. 남쪽 이음매(180 / -180)는 양 끝을 복제해 메웁니다.

---

## 3. 무엇을 미리 계산하고, 무엇을 안 하나

**미리 계산 = 시간에 대해 매끄러운 연속량만.**

| 저장 | 이유 |
|---|---|
| 방향별 운량 576개 | `buildSkyColumns`는 항상 같은 (3층 × 24방위 × 8고도)를 같은 순서로 냅니다. 격자가 고정이라 **운량 배열 하나**면 충분합니다 |
| 층별 직달·확산 배율, 태양 투과율 | 스칼라. 매끄럽습니다 |
| 태양·달 고도/방위 | 5분에 1.25°, 선형으로 충분 |
| 대기 파라미터, 관측점 기상 | 시간당 변화가 작음 |

**저장하지 않는 것 = 불연속인 것.** 구름 개수·운형·아틀라스 조각은 보간하면
튑니다. 그건 렌더 시점에 보간된 운량에서 다시 뽑습니다
(`buildCloudsFromColumns`) — fBm이 빠져 훨씬 쌉니다.

### 함수 분리

`buildCloudInstances`를 둘로 갈랐습니다.

```
buildCloudInstances(weather, ...)        ← 기존 경로 (타임라인 없을 때)
  ├ WeatherFan + buildSkyColumns(576방향 fBm) + solveColumnOptics   ← 비싼 앞부분
  └ placeClouds(...)                                                ← 공유
buildCloudsFromColumns(samples, optics)  ← 타임라인 경로
  └ placeClouds(...)                     ← 앞부분을 건너뜀
```

---

## 4. 계층 정리

`skyTimeline`이 `cloudPlacement`의 `representativeTauForObserver`를 필요로 했는데,
그 파일은 `cloudAtlas`를 통해 **THREE에 의존**합니다. 사전 계산 모듈이 렌더러를
끌고 오는 건 방향이 거꾸로입니다.

순수 데이터인 `PRESET_OPTICS` / `resolvePresetFromWeather` /
`representativeTauForObserver` 를 `cloudPresets.ts`(THREE 비의존)로 내렸습니다.
사전 계산과 실시간 계산이 **같은 함수**를 쓰므로 두 경로의 광학이 갈라질 수
없습니다.

## 5. 비용

| 항목 | 값 |
|---|---|
| 키프레임 | 5분 간격, 289개 (24h) |
| 사전 계산 | 데스크톱 **166ms** (프레임당 0.57ms) |
| 모바일 추정 | **약 1초** |
| 메모리 | 576 × 4B × 289 = **0.64 MB** |
| 네트워크 | 요청 **1건** (하루·전 방위) |

1~3분까지 써도 된다고 하셨지만 실제로는 1초 수준입니다. 그래서 진행률 바는
"오래 걸려서"가 아니라 **네트워크 지연과 취소 가능성** 때문에 둡니다.

UI 스레드를 막지 않도록 12프레임마다 `setTimeout(0)`으로 양보합니다.
이게 없으면 진행률 바가 멈춘 채 화면이 얼어붙어, 진행률을 보여주는 목적
자체가 사라집니다.

## 6. 검증

`tools/shader-preview/verify-timeline.js` (32개). 핵심 질문은 하나 —
**미리 계산해 보간한 결과가 그 자리에서 직접 푼 결과와 같은가.**

| 검사 | 결과 |
|---|---|
| 키프레임 시각에서 직접 계산과 일치 | 최대 오차 **1e-6 미만** (운량·태양고도·층별 배율) |
| 보간값이 양 끝 사이에 있는가 | 이탈 **0개** |
| 중간 시각 보간 vs 직접 계산 | 평균 **1.29%p**, 최대 14.45%p |
| 1분 간격 연속성 | 최대 변화 **0.100%p** — 스크럽 시 튀지 않음 |
| 태양 방위 0/360 이음매 | 분당 최대 변화 2° 미만 (최단호 보간) |
| 범위 밖 시각 | 양 끝으로 클램프 |
| 재사용 판정 | 날짜 바뀌면 폐기, 5km 이동은 재사용, 110km는 폐기 |

평균 1.29%p 오차는 **노이즈 이류가 비선형**이기 때문입니다 (구조가 하늘을
가로질러 흐르는 항). 키프레임을 촘촘히 하면 줄지만, 1분 간격 변화가 이미
0.1%p라 눈에 띄지 않습니다.

---

## 7. 남은 것

- **기기 미검증.** 진행률 바가 실제로 부드럽게 도는지, 1초 추정이 맞는지.
- **타임라인은 메모리에만 있습니다.** 앱을 다시 켜면 다시 눌러야 합니다.
  디스크 캐시는 넣지 않았습니다 — 0.64MB × 날짜 수가 쌓이고, 예보는
  시간이 지나면 낡습니다.
- **초단기 실황(nowcast)과 강화 격자는 아직 타임라인 경로가 아닙니다.**
  둘 다 기존 팬 경로를 씁니다.
