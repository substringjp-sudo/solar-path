# 해안선 계획 — 지면 기하를 다시 잡는다

> "지면기하 전체를 다시 잡더라도 보기 좋게 만들어줘. 지금 계속 수치만 잡았지만
> 별로 깔끔하게 문제가 해결된 것 같지 않아. 기본적으로 지형을 생성하고, 지형과
> 해수면을 동시에 실제 해안가처럼 만들고, 경계를 보기 좋게 만드는 방법"

지적이 맞습니다. 44~49절에서 제가 한 것은 전부 **바닥 칠하기**였습니다.
왜 그럴 수밖에 없었는지부터 적습니다.

## 1. 지금 구조 — 해안선이라는 것이 없습니다

| 요소 | 실제 정체 |
|---|---|
| 지면 | **완전한 평면 원반** (`CircleGeometry(475, 64)`, y ≈ −1.5). 고도 없음 |
| 지형 | 반지름 480의 **원통 띠** — 가장자리에 세운 배경 그림 |
| 육지/바다 | 그 평면 위의 **2D 마스크 텍스처** 하나 |
| 고도 자료 | 31방위 × 3거리 = **93점** (실루엣이지 높이장이 아님) |
| 수평선 | 원반을 `−R·tan(dip)` 만큼 **내려서** 흉내 |

그래서 다음이 전부 **원리적으로** 불가능합니다.

- **경계가 기하가 아닙니다.** 육지와 바다가 같은 평면이고 텍스처로만 갈립니다.
  물이 땅을 만나는 선이 없으니 물가도, 젖은 모래도, 파도가 부서지는 자리도
  만들 데가 없습니다.
- **수심이 없습니다.** 얕은 물이 밝고 초록빛인 것, 깊을수록 파래지는 것,
  포말이 얕은 곳에만 생기는 것 — 전부 수심에서 나오는데 그 값이 없습니다.
- **가려짐이 없습니다.** 곶이 만을 가리거나 섬 뒤가 안 보이는 일이 없습니다.
- **눈높이가 1.6m 로 박혀 있습니다** (`eyePos = vWorld.y + 1.6`). 그래서
  20m만 넘으면 전부 스침각이고, 보이는 바다의 거의 전부가 하늘 거울입니다
  (49.8 의 남은 판정이 이것입니다).

## 2. 자료 — 93점이 아니라 진짜 높이장을 받을 수 있습니다

**AWS Terrain Tiles** (Mapzen 파생, Registry of Open Data on AWS).
이 환경에서 실제로 확인했습니다.

```
https://s3.amazonaws.com/elevation-tiles-prod/terrarium/{z}/{x}/{y}.png
→ HTTP 200, 35KB, 256×256 PNG, 인증 없음
```

- **Terrarium 인코딩**: `고도(m) = R·256 + G + B/256 − 32768`
- 해상도 **약 30m** (1 arc-second), 전 지구, **얕은 수심 포함**
- 대부도 앞바다 z12 타일 실측: 고도 −2.8m ~ 138m, 음수(수심) 표본 126개.
  해안을 가로지르는 한 줄이 `5 9 45 16 55 5 −0 −0 −1 0 0` — 육지에서
  바다로 넘어가는 것이 그대로 보입니다.

타일 하나가 **65,536점**입니다. 지금 93점의 700배.

### 실무 메모 두 개

- ⚠ **선형보간은 안전합니다.** 처음에 "RGB 세 채널에 쪼개 담았으니 텍스처
  보간을 켜면 깨진다"고 적으려다 재 봤더니 **최대 오차 0.0m** 였습니다.
  디코드가 R·256 + G + B/256 로 **채널에 대해 선형**이라, 채널별 보간과
  디코드가 교환됩니다. 짐작을 적을 뻔했습니다.
- ⚠ **텍스처를 sRGB 로 읽으면 안 됩니다.** `NoColorSpace` 로 올려야 합니다.
  감마가 걸리면 고도가 통째로 어긋납니다. 이쪽이 진짜 함정입니다.
- JS 로 화소를 꺼낼 필요가 없습니다. PNG 를 그대로 **텍스처로 올리고
  버텍스 셰이더에서 디코드**하면 됩니다 — RN 에서 PNG 디코더를 붙이는
  문제가 통째로 사라집니다.

## 3. 그리는 방법 — 경계를 "그리지" 말고 **만나게** 합니다

업계 표준은 하나로 모입니다: **물과 땅을 각각 진짜 면으로 두고, 둘이 만나는
곳을 깊이로 읽는다.** (Crest Ocean, UE Water, Unity URP 물 셰이더가 전부
같은 뼈대입니다.)

### 3-1. 지면을 진짜 높이장으로

평면 원반을 **격자 메시**로 바꾸고, 버텍스 셰이더에서 DEM 텍스처를 읽어
y 를 올립니다. 관측자 중심 반경 몇 km 를 덮고, 바깥은 지금의 능선 띠가
그대로 이어받습니다(먼 지형을 빌보드로 두는 것은 표준이고 옳습니다).

- 격자는 관측자 중심 **동심원**이 좋습니다 — 가까울수록 촘촘해 화면 화소당
  삼각형 수가 고릅니다.
- 눈높이가 비로소 의미를 갖습니다. `eyePos` 를 관측 고도로 두면 언덕에서
  내려다보는 시선이 실제로 생기고, 그때 비로소 **수체가 보입니다**
  (49.8 의 남은 판정이 여기서 풀립니다).

### 3-2. 바다는 **따로 있는 면**

해수면 y = 0 인 별도의 면을 둡니다. 그러면

- **해안선 = 두 면의 교선.** 따로 그리지 않아도 만(灣)·곶·섬이 자동으로
  제 모양입니다. 지금처럼 마스크 가장자리를 다듬는 일 자체가 없어집니다.
- 방위 해상도 12° 한계가 사라집니다 — 30m 격자가 정하니까요.

### 3-3. 경계는 **수심**이 정합니다

물 셰이더가 같은 DEM 을 읽어 `수심 = 0 − 지형고도` 를 구합니다. 그 하나로
보기 좋은 것들이 전부 따라옵니다.

| 보이는 것 | 수심에서 어떻게 |
|---|---|
| 물가 포말 띠 | 수심 < 약 0.5m 에서 띄우고 부드럽게 꺼짐 |
| 포말 폭이 지형마다 다름 | 완만한 모래밭은 넓고, 절벽은 좁음 — **거리가 아니라 수심**으로 재니 저절로 |
| 얕은 물의 초록빛 | 수체 흡수를 `exp(−k·수심)` 로. 붉은빛이 먼저 먹혀 청록이 남음 |
| 젖은 모래 | 물가 안쪽 육지를 **어둡게 + 매끈하게**(거칠기↓). 색만 바꾸면 안 됩니다 |
| 파도가 얕은 데서 서는 것 | 진폭을 수심으로 눌러 부서지게 |

깊이 버퍼(screen-space) 방식도 있지만 우리는 **DEM 을 이미 들고 있으므로**
바로 샘플하면 됩니다 — 더 간단하고 합성 순서에 안 휘둘립니다.

### 3-4. 지금 것 중 살릴 것

49절에서 물리로 되돌린 것들은 그대로 씁니다 — 조도 × 알베도로 바뀐 수체·
거품, 진짜 프레넬, Cox-Munk 윤슬, 순응 몫으로 나눈 밤빛. 그 위에 **기하와
수심**이 얹히는 구조입니다.

## 4. 단계

| 단계 | 내용 | 판정 |
|---|---|---|
| 1 | DEM 타일 가져오기 · 셰이더 디코드 · 캐시 | 알려진 좌표의 고도가 맞는가 |
| 2 | 지면을 동심원 격자 + 버텍스 변위로 | 능선 실루엣이 자료와 맞는가 |
| 3 | 눈높이를 관측 고도로 | 수평선 각도가 `dip` 과 맞는가 |
| 4 | 해수면 별도 면 · 교선 | 해안선이 마스크가 아니라 기하인가 |
| 5 | 수심 기반 포말·색·젖은 모래 | 포말 폭이 지형 경사를 따르는가 |

## 5. 값과 위험

- **자료량**: z12 타일 하나 35KB. 반경 몇 km 면 2×2~3×3 장이면 됩니다.
  타일은 정적 S3 라 캐시가 잘 듣습니다. (SLA 는 없습니다 — 실패하면 지금
  방식으로 물러나는 길을 남겨야 합니다.)
- **삼각형 수**: 동심원 격자 128×256 이면 약 6.5만 삼각형. 모바일에서
  버텍스 변위만 하는 정적 메시라 감당할 만하지만 **실측이 필요합니다.**
- **가장 큰 위험**: 눈높이를 바꾸면 지금 화면 전체의 구도가 바뀝니다.
  능선 띠·나침반·천체 궤적이 전부 지금 기하에 맞춰져 있습니다. 3단계를
  독립적으로 재고 넘어가야 합니다.
- **바다 수심의 한계**: 이 자료는 먼바다를 대체로 0 으로 둡니다(실측: 표본
  1024개 중 정확히 0 이 406개). 근해 수심은 −1~−3m 로 살아 있으므로 물가
  표현에는 충분하지만, 먼바다 색을 수심으로 만들려 하면 안 됩니다 —
  거기는 지금처럼 거리로 두는 것이 맞습니다.
