# 해안선 계획 — 지면 기하를 다시 잡는다

> "지면기하 전체를 다시 잡더라도 보기 좋게 만들어줘. 지금 계속 수치만 잡았지만
> 별로 깔끔하게 문제가 해결된 것 같지 않아. 기본적으로 지형을 생성하고, 지형과
> 해수면을 동시에 실제 해안가처럼 만들고, 경계를 보기 좋게 만드는 방법"

지적이 맞습니다. 44~49절에서 제가 한 것은 전부 **바닥 칠하기**였습니다.
왜 그럴 수밖에 없었는지부터 적습니다.

## 1. 지금 구조 — 해안선이라는 것이 없습니다

| 요소 | 실제 정체 |
|---|---|
| 지면 | **완전한 평면 원반** (`CircleGeometry(475, 64)`, y ≈ −1.5). 고도 없음 |
| 지형 | 반지름 480의 **원통 띠** — 가장자리에 세운 배경 그림 |
| 육지/바다 | 그 평면 위의 **2D 마스크 텍스처** 하나 |
| 고도 자료 | 31방위 × 3거리 = **93점** (실루엣이지 높이장이 아님) |
| 수평선 | 원반을 `−R·tan(dip)` 만큼 **내려서** 흉내 |

그래서 다음이 전부 **원리적으로** 불가능합니다.

- **경계가 기하가 아닙니다.** 육지와 바다가 같은 평면이고 텍스처로만 갈립니다.
  물이 땅을 만나는 선이 없으니 물가도, 젖은 모래도, 파도가 부서지는 자리도
  만들 데가 없습니다.
- **수심이 없습니다.** 얕은 물이 밝고 초록빛인 것, 깊을수록 파래지는 것,
  포말이 얕은 곳에만 생기는 것 — 전부 수심에서 나오는데 그 값이 없습니다.
- **가려짐이 없습니다.** 곶이 만을 가리거나 섬 뒤가 안 보이는 일이 없습니다.
- **눈높이가 1.6m 로 박혀 있습니다** (`eyePos = vWorld.y + 1.6`). 그래서
  20m만 넘으면 전부 스침각이고, 보이는 바다의 거의 전부가 하늘 거울입니다
  (49.8 의 남은 판정이 이것입니다).

## 2. 자료 — 93점이 아니라 진짜 높이장을 받을 수 있습니다

**AWS Terrain Tiles** (Mapzen 파생, Registry of Open Data on AWS).
이 환경에서 실제로 확인했습니다.

```
https://s3.amazonaws.com/elevation-tiles-prod/terrarium/{z}/{x}/{y}.png
→ HTTP 200, 35KB, 256×256 PNG, 인증 없음
```

- **Terrarium 인코딩**: `고도(m) = R·256 + G + B/256 − 32768`
- 해상도 **약 30m** (1 arc-second), 전 지구, **얕은 수심 포함**
- 대부도 앞바다 z12 타일 실측: 고도 −2.8m ~ 138m, 음수(수심) 표본 126개.
  해안을 가로지르는 한 줄이 `5 9 45 16 55 5 −0 −0 −1 0 0` — 육지에서
  바다로 넘어가는 것이 그대로 보입니다.

타일 하나가 **65,536점**입니다. 지금 93점의 700배.

### 실무 메모 두 개

- ⚠ **선형보간은 안전합니다.** 처음에 "RGB 세 채널에 쪼개 담았으니 텍스처
  보간을 켜면 깨진다"고 적으려다 재 봤더니 **최대 오차 0.0m** 였습니다.
  디코드가 R·256 + G + B/256 로 **채널에 대해 선형**이라, 채널별 보간과
  디코드가 교환됩니다. 짐작을 적을 뻔했습니다.
- ⚠ **텍스처를 sRGB 로 읽으면 안 됩니다.** `NoColorSpace` 로 올려야 합니다.
  감마가 걸리면 고도가 통째로 어긋납니다. 이쪽이 진짜 함정입니다.
- JS 로 화소를 꺼낼 필요가 없습니다. PNG 를 그대로 **텍스처로 올리고
  버텍스 셰이더에서 디코드**하면 됩니다 — RN 에서 PNG 디코더를 붙이는
  문제가 통째로 사라집니다.

## 3. 그리는 방법 — 경계를 "그리지" 말고 **만나게** 합니다

업계 표준은 하나로 모입니다: **물과 땅을 각각 진짜 면으로 두고, 둘이 만나는
곳을 깊이로 읽는다.** (Crest Ocean, UE Water, Unity URP 물 셰이더가 전부
같은 뼈대입니다.)

### 3-1. 지면을 진짜 높이장으로

평면 원반을 **격자 메시**로 바꾸고, 버텍스 셰이더에서 DEM 텍스처를 읽어
y 를 올립니다. 관측자 중심 반경 몇 km 를 덮고, 바깥은 지금의 능선 띠가
그대로 이어받습니다(먼 지형을 빌보드로 두는 것은 표준이고 옳습니다).

- 격자는 관측자 중심 **동심원**이 좋습니다 — 가까울수록 촘촘해 화면 화소당
  삼각형 수가 고릅니다.
- 눈높이가 비로소 의미를 갖습니다. `eyePos` 를 관측 고도로 두면 언덕에서
  내려다보는 시선이 실제로 생기고, 그때 비로소 **수체가 보입니다**
  (49.8 의 남은 판정이 여기서 풀립니다).

### 3-2. 바다는 **따로 있는 면**

해수면 y = 0 인 별도의 면을 둡니다. 그러면

- **해안선 = 두 면의 교선.** 따로 그리지 않아도 만(灣)·곶·섬이 자동으로
  제 모양입니다. 지금처럼 마스크 가장자리를 다듬는 일 자체가 없어집니다.
- 방위 해상도 12° 한계가 사라집니다 — 30m 격자가 정하니까요.

### 3-3. 경계는 **수심**이 정합니다

물 셰이더가 같은 DEM 을 읽어 `수심 = 0 − 지형고도` 를 구합니다. 그 하나로
보기 좋은 것들이 전부 따라옵니다.

| 보이는 것 | 수심에서 어떻게 |
|---|---|
| 물가 포말 띠 | 수심 < 약 0.5m 에서 띄우고 부드럽게 꺼짐 |
| 포말 폭이 지형마다 다름 | 완만한 모래밭은 넓고, 절벽은 좁음 — **거리가 아니라 수심**으로 재니 저절로 |
| 얕은 물의 초록빛 | 수체 흡수를 `exp(−k·수심)` 로. 붉은빛이 먼저 먹혀 청록이 남음 |
| 젖은 모래 | 물가 안쪽 육지를 **어둡게 + 매끈하게**(거칠기↓). 색만 바꾸면 안 됩니다 |
| 파도가 얕은 데서 서는 것 | 진폭을 수심으로 눌러 부서지게 |

깊이 버퍼(screen-space) 방식도 있지만 우리는 **DEM 을 이미 들고 있으므로**
바로 샘플하면 됩니다 — 더 간단하고 합성 순서에 안 휘둘립니다.

### 3-4. 지금 것 중 살릴 것

49절에서 물리로 되돌린 것들은 그대로 씁니다 — 조도 × 알베도로 바뀐 수체·
거품, 진짜 프레넬, Cox-Munk 윤슬, 순응 몫으로 나눈 밤빛. 그 위에 **기하와
수심**이 얹히는 구조입니다.

| 단계 | 내용 | 판정 |

| 2 ✅ | 지면을 동심원 격자 + 버텍스 변위로 | 능선 실루엣이 자료와 맞는가 |

### 1단계 결과 (`src/utils/demTiles.ts`, `verify-dem.js` — 15개 단언)

대부도 앞바다 (37.25N 126.58E) 반경 3km, 줌 13, 3×3 타일 (589,824점):

| | 값 |
|---|---|
| 셰이더 대 CPU 직접 디코드 (같은 자료) | 중앙 0m · **최대 0.01m** |
| 셰이더 대 Open-Meteo (다른 DEM) | 상관 **0.9687** · 치우침 0.23m · 중앙 2.5m |
| 바다(참조 0m) 평균 / 뭍(≥20m) 평균 | 1.67m / 40.26m |

Open-Meteo 와의 최대 차 21.7m 는 우리 결함이 아니라 **자료끼리의 차이**입니다.
문제의 봉우리를 Terrarium z13/14/15 최근접으로 따로 풀어보면 114 / 116 / 115m
로, 셰이더가 읽은 115.3m 이 맞습니다. Open-Meteo 쪽이 137m 라고 합니다.

**여기서 실제로 잡은 결함 둘:**

1. **합성할 때 타일 줄을 뒤집어** 놓아 블록 y 가 반사됐습니다 (최대 137m).
   원인은 "카메라 위쪽이 2 이니 타일 y 를 뒤집어야 한다"는 짐작이었는데,
   `flipY = false` 라 판 아래쪽(uv v=0)이 이미 PNG 첫 줄(북쪽)이었습니다.
   두 번 뒤집은 셈입니다.
2. **2×2 블록이면 관측자에서 한 타일이 남는다**고 잘못 알았습니다 (최대
   50.6m). 실제로 보장되는 여유는 **(한 변 − 1) / 2 타일**이라 2×2 는 반
   타일뿐입니다. 블록을 **홀수 3×3** 으로 바꿔 관측자 타일을 정중앙에 두고,
   줌 선택도 그 여유로 계산하게 고쳤습니다.

**판정을 짜면서 배운 것 — 참조 하나로는 부족합니다.**
뒤집기를 일부러 되살려 대조했더니, 관측자가 블록 정중앙이라 뒤집기가 표본
무게중심에 대한 **반사**가 되어 Open-Meteo 상관이 0.9118 로 **통과해 버렸고**,
치우침도 −2.82m 로 통과했습니다. 잡은 것은 CPU 직접 디코드 비교(최대 42.11m)
뿐이었습니다. 반대로 **평행이동**은 상관이 잘 잡습니다 — 0.03타일(117m)만
어긋나도 0.9687 → 0.8300 으로 떨어집니다. 그래서 둘 다 답니다.
같은 이유로 ① 에서 일하는 값은 중앙이 아니라 **최대**입니다(반사는 가운데
표본을 안 건드려 중앙오차가 0m 인 채로 통과합니다).

### 2단계 결과 (`src/components/SkyScene3D/TerrainField.ts`, `verify-terrain-field.js` — 17개 단언)

**미터 평면이 아니라 각도 격자입니다.** 이 씬은 반경 500 돔에 각도로 그리고
구름·능선 띠·나침반·천체가 전부 그 규약 위에 있습니다. 여기에만 미터
좌표계를 들이면 3km 지점이 돔 밖으로 나가 깊이 순서가 통째로 깨집니다.
그래서 정점을 **실제로 보이는 고도각**에 놓습니다:

    낙차   = d² / 2R          (지구 곡률)
    고도각 = atan2(고도 − 눈높이 − 낙차, d)

가림은 **반경이 정합니다.** 반경을 거리의 단조 증가 함수로 두면, 카메라가
메시 원점에 있으므로 깊이 = 반경이고 "가까운 것이 항상 앞"이 공짜로
성립합니다. 반경은 오직 깊이 순서만 나르고, 보이는 자리는 전부 고도각이
정합니다.

| 재는 것 | 값 |
|---|---|
| 그려진 실루엣 대 CPU 참조 | 중앙 **0.018°** · 최대 0.119° · 상관 **0.99999** |
| 치우침 | −0.0028° |
| 평평한 판 대조 (손으로 푼 −0.044°) | 실측 −0.0243° · 편차 0.020° (화소 양자화) |
| 열 → 방위 직접 대조 | 최대 0.054° |
| 삼각형 | 65,024 (고리 128 × 살 256) |

**눈은 반드시 그려지는 그 면 위에 서야 합니다.** 처음에 바깥 고도(0m)를
믿었다가 DEM 이 말하는 이 지점의 실제 42m 에 눈이 파묻혀 지평선각이 **72°**
로 나왔습니다. 가장 가까운 고리(12m)에서는 5m 차이가 22° 로 벌어집니다.
그래서 발밑 고도를 `dem_elevationAt(vec2(0.0))` 으로 **DEM 자신이** 정하게
했습니다. (3단계가 여기서 이미 풀렸습니다.)

**판정이 잡은 결함 — 지상 좌표의 남북 부호.** 방위 A(북에서 시계방향)의
지상 좌표는 `(동, 남) = (sin A, −cos A)` 인데 참조와 `horizonAngleDeg` 가
`+cos A` 를 썼습니다. 격자 생성기도 같은 실수를 했지만 거기서는 한 바퀴를
반대로 돌 뿐이라 **아무 증상이 없어** 놓치기 쉽습니다.

    거울상일 때:  중앙 1.339° · 최대 6.537° · 상관 0.883
    고친 뒤:      중앙 0.018° · 최대 0.119° · 상관 0.99999

⚠ **상관 이동으로 어긋남을 찾으면 안 됩니다.** 그렇게 했다가 −19.9° 에서
봉우리가 나왔는데, 지형 신호의 저주파 성분이 만든 가짜였습니다. 실제 방위
매핑은 멀쩡했고(0.054°), 틀린 것은 지상 좌표 쪽이었습니다. **매핑을 직접**
재야 합니다 — 48절에서 배운 것과 같습니다.

**살 수는 훑어서 골랐습니다** (최대오차 / 삼각형):

    128 (2.81°) 0.240° / 32,512     512 (0.70°) 0.085° / 130,048
    256 (1.41°) 0.119° / 65,024 ←   1024(0.35°) 0.085° / 260,096 (수렴)

256 의 0.119° 는 읽기 해상도(행 0.0586°)의 두 칸입니다. 512 로 가도 0.034°
밖에 못 줄이는데 삼각형은 두 배입니다.

### ⚠ 3단계가 아니라 **4단계**가 먼저 필요했습니다 (해결됨)

격자는 3km 에서 끝나고, 바다 방위에서 바깥 고리는 **−0.846°** 입니다.
그런데 눈높이 43.6m 의 진짜 수평선은 **−0.212°** 입니다. 그 사이 **0.634°**
가 격자가 안 덮는 띠였습니다 (44절에서 지면과 구름이 서로 다른 지평선을 써서
0.79° 띠가 벌어진 것과 같은 부류).

**4단계의 해수면이 그 자리를 이어받았습니다.** 해수면은 수평선 거리
`sqrt(2Rh)` 까지 뻗고 그 너머는 접습니다. 4단계 판정이 "맨 위가 물인 방위의
각 = −dip" 을 손으로 푼 답과 견줘 확인합니다.

### 4단계 결과 (`SeaPlane.ts` + `groundProjection.ts`, `verify-coastline.js` — 17개 단언)

**투영을 한 곳으로 뽑았습니다.** 땅과 물이 같은 자로 재야 교선이 성립합니다
(44절에서 지면과 구름이 서로 다른 지평선을 쓰다 0.79° 띠가 벌어졌습니다).
`groundProjection.ts` 의 `gp_project` 하나를 양쪽이 쓰고, 눈높이도 DEM 이 정한
같은 값을 씁니다.

**가림이 공짜로 맞습니다.** 반경이 거리의 단조 증가 함수라서:

- 물 위의 땅 → 같은 각의 바다는 **더 먼** 곳 → 반경이 큼 → 땅이 이김 ✓
- 물 아래의 땅 → 같은 각의 바다는 **더 가까운** 곳 → 반경이 작음 → 물이 이김 ✓

| 재는 것 | 값 |
|---|---|
| **화소마다** 땅/물이 맞는가 (지면 화소 298,280) | **99.23%** (틀림 2,282 — 경계 반 칸) |
| 실루엣 위가 하늘인가 (하늘 화소 471,487) | 99.999% (틀림 6) |
| 물 맨위 / 땅 맨위 | 중앙 0.019° / 0.021° (읽기 해상도 0.059°/행) |
| 대조 ① 수평선 (손으로 푼 −0.0534°) | 실측 −0.0894° · 방위 흔들림 0.116° |
| 대조 ② 한 광선에서 2회 이상 땅↔물 | 참조 986열 = **측정 986열** |
| 해안 구조가 방위를 따라 바뀌는 횟수 | 101회 (12° 마스크는 한 바퀴에 30칸) |

⚠ 관측점을 1·2단계와 **다른 곳**으로 옮겼습니다. 같은 점(37.25, 126.58)은
고도 42m 에 사방이 더 높아 **어느 방위로도 물이 안 보입니다** (1km 앞 지면이
45.2m 로 눈보다 1.6m 높아 그 너머를 다 가립니다). 물을 대상이 없으면 판정이
헛돕니다. DEM 을 훑어 고도 1~30m 이면서 바다와 뭍이 같이 보이는 점을 골랐고,
그 자리에서 72방위 중 47방위가 한 광선에서 2회 이상 땅↔물을 오갑니다.

**판정이 잡은 결함 셋:**

1. **발밑 각도 구멍.** 지면 격자가 12m 부터 시작해서, 눈높이 2.77m 기준
   −6.3° 아래로는 지면이 **아예 없었습니다.** 더 낮은 각까지 뻗는 해수면이
   그 구멍을 메워 물가에 선 관측자가 물을 밟고 선 것처럼 그려졌습니다.
   격자를 0.6m 부터 시작하는 **두 구간**(발밑 24고리 + 바깥 128고리)으로
   바꿨습니다. ⚠ 발밑 고리를 바깥에서 빼내면 안 됩니다 — 한 구간 로그
   간격으로 발밑까지 덮으려다 2단계 최대오차가 0.119° → 0.161° 로
   나빠졌습니다. 새로 덮는 구간이므로 고리를 **더합니다** (152개, 삼각형
   77,312).
2. **먼바다가 통째로 뭍으로 그려짐.** Terrarium 이 **먼바다를 정확히 0 으로
   자르는** 성질(조사 때 1024개 중 406개가 정확히 0) 때문에 지면 메시가
   해수면과 같은 높이에 면을 깔고 깊이 동률에서 이겼습니다. 해수면 아래를
   그리지 않도록(`discard`) 고쳤습니다 — 거기서 보이는 것은 땅이 아니라
   물입니다. 맨 위 물이 −0.481° → −0.089° (이론 −0.053°).
   알려진 한계: 고도가 정확히 0m 인 **간척지·갯벌**도 물로 읽힙니다.
3. **판정 자신의 결함.** 참조의 "하늘 시작점"으로 경계 목록의 마지막 항목을
   썼는데 그건 마지막 **종류 변화**이지 맨 위가 아닙니다. 하늘 일치율이 0.77 로
   나왔고 렌더가 아니라 측정이 틀린 것이었습니다. 0.99999 로 고쳤습니다.

**전환 수를 문턱으로 쓰지 않습니다.** 참조는 고리 표본 사이의 화소보다 얇은
조각까지 셉니다(참조 11회 대 측정 4회). 못 그리는 것을 세는 것은 불공정하므로
문턱은 **화소 단위 일치율**로 잡고, 전환은 "그런 구조가 나오는가"로만 씁니다.

### 5단계 결과 (`verify-shore.js` — 21개 단언)

땅색은 조도 × 알베도 위에 **경사 · 조간대 · 공기원근**을 얹었습니다. 물빛은
**수심 하나**에서 흡수·바닥비침·포말이 전부 따라옵니다.

| 재는 것 | 값 |
|---|---|
| 얕은 물(<0.5m) 대 0.5~1m | **1.160배** (얕을수록 밝음) |
| 같은 수심에서 거리로 묶으면 | **0.27%** 변동 (수심 응답 16.0%) |
| 경사 대 땅색 색조 상관 | **0.793** (뒤섞은 경사 귀무 0.006) |
| 조간대 대 마른 땅 밝기 | **0.746배** |
| 공기원근 (600~1500m) | 맑은 날 7.5/255 · 뿌연 날(β 0.5) 21.2/255 |
| 대조 ⓪ 등록 (실루엣) | 최대 차 **0px** |

**판정이 잡은 결함 넷:**

1. **`slope = 1 − n.y` 는 기울기가 아닙니다.** 흔한 축약인데 작은 각에서
   θ²/2 라, 기울기 0.21(12°) 사면도 0.022 밖에 안 됩니다. 기울기 기준 문턱
   (0.10~0.50)에 넣었더니 **경사 항이 통째로 죽어** 화소 11,366개의 색조가
   **0.5918 하나로 고정**됐습니다. 땅이 판지처럼 보이던 원인이 이것입니다.
   `tanθ = sqrt(1−n.y²)/n.y` 로 고친 뒤 상관 0.79, 색조 폭 0.59~0.73.
2. **Terrarium 의 0 을 0m 수심으로 믿음.** 먼바다가 정확히 0 으로 잘려 있어,
   그걸 0m 로 읽으면 바닥이 다 비치고 포말이 1 이 되어 **만 전체가 밝은
   모래펄**이 됩니다. "모르는 곳은 깊다"로 고쳤습니다. 4단계와 같은 함정이
   다른 자리에서 또 나왔습니다.
3. **표시 하한(minGlow)이 음영을 통째로 먹습니다.** 조도가 낮으면 지면이
   `atm_display_ground` 의 최소 밝기에 눌려 경사도 젖은 모래도 전부 같은 색이
   됩니다 (젖음 54.26 대 마름 57.21 — 사실상 같음). 현실적인 낮 조도에서는
   90.94 대 121.93 으로 갈립니다. **어두운 장면에서는 땅의 음영이 원리적으로
   안 보인다**는 뜻이라 기억해 둘 값입니다.
4. **판정 자신의 상하 반전.** `readRenderTargetPixels` 는 아래에서 위로 오는데
   접근자를 뒤집어, 위아래가 뒤집힌 그림과 견주고 있었습니다. 증상은 "가장
   얕은 물이 가장 어둡다". 그래서 대조 ⓪(실루엣 등록)을 넣었습니다.

**버린 지표.** "포말 폭"을 화면 밝기 문턱으로 재려다 두 번 실패했습니다 —
화소로 재면 거리가 1/d² 로 섞여 상관이 **반대 부호**(+0.40)로 나왔고,
미터로 고쳐도 문턱이 고르는 등수심선이 제멋대로라 0 이 됐습니다. 문턱을
쓰지 않는 쪽으로 바꿨습니다: 수심으로 묶으면 크게 변하고 **거리로 묶으면
안 변한다**는 대비가 판정입니다.

### 남은 것 두 가지

- **갯벌에서 포말 띠가 너무 넓습니다.** `수심 < 0.5m` 을 포말로 삼는데,
  이 자리는 갯벌이라 그 구간이 **448m** 입니다. 화면에서 흰 띠가 지나치게
  넓게 보입니다. 물리적으로 파도는 `수심 < 약 1.3 × 파고` 에서 부서지고
  그 뒤로 거품이 **흩어집니다.** 앱에는 풍속이 있으니 파고를 구할 수
  있습니다 — 상수를 줄여 눈속임할 것이 아니라 **부서지는 띠**로 모형을
  바꾸는 것이 맞습니다.
- **깊은 물빛은 여기서 확인 못 했습니다.** 이 관측점은 보이는 물이 전부
  수심 1m 미만이라, 흡수 `exp(−k·2d)` 로 청록이 남는 것을 가릴 표본이
  없습니다.

### 씬 연결 (`SkyScene3D.tsx`, `verify-sea-reflect.js` 12개 · `verify-handoff.js` 8개)

`TerrainField`·`SeaPlane` 를 실제 앱 씬에 붙였습니다. **옛 원반(`ground
Plane`)·능선 띠(`terrainBands`)는 그대로 둡니다** — 새 메시는 그 위에
`renderOrder` 만 앞세워 얹는 **보강**입니다. DEM 이 없거나 아직 받는 중이면
`uDemValid=0` 으로 물러나 원반이 그대로 비치고, 3km 밖은 새 메시 자체가
없어 원반·능선 띠가 자연히 이어받습니다. 렌더 순서:

    terrainField(−0.6) → seaPlane(−0.55) → ground(−0.5) → bands(−0.4+)

새 메시가 real depth 를 먼저 쓰고(depthWrite:true), 원반은 depthWrite:false
라 어디서도 남을 가리지 못합니다 — 있는 곳은 새 지형이, 없는 곳은 원반이
자연히 남는 구조입니다.

> ⚠ **이 문단은 틀렸습니다. 6절에서 실기 보고로 뒤집혔습니다.**
> depthWrite 를 꺼도 depthTest 로 이겨 **색은 덮어씁니다.** 순서는 지금
> `ground(−0.5) → terrainField(−0.48) → seaPlane(−0.47) → bands(−0.4+)`
> 입니다. 아래 6절을 보세요.

**연결하며 판정이 잡은 결함 둘:**

1. **카메라 Y 와 물리 눈높이가 겹칠 뻔했습니다.** 이 씬의
   `camera.position.y` 는 실제 미터가 아니라 화면단위 dip 트릭 값입니다
   (지면 원반을 기울여 수평선 침강을 흉내 내던 예전 방식). `TerrainField`·
   `SeaPlane` 은 눈높이를 이미 **미터**로 셰이더 안에서 계산하므로,
   `updateTerrainFieldEye`/`updateSeaPlaneEye` 가 카메라 위치를 그대로
   복사하면 두 셈법이 겹쳐 **이중으로** 셉니다. X/Z(항상 0)만 따라가고
   Y 는 0 으로 고정하도록 고쳤습니다 — 기존 2·4·5단계 판정은 카메라를
   이미 Y=0 에 뒀으므로 이 수정으로 회귀가 하나도 안 깨졌습니다.
2. **하늘 되비침(프레넬)이 아예 없었습니다.** 49절에서 물로 되돌린 물리

**`verify-sea-reflect.js`** 가 그 프레넬 항을 DEM 없이 고립시켜 잽니다

## 6. 실기가 뒤집은 것 — 내륙의 물과 너무 넓은 윤슬

실기(서울 도곡동, 37.489130/127.043169, 해발 70m)에서 두 가지가 보고됐습니다:
"내가 선 자리 둘레 땅이 전부 해발 0 처럼 되는지 물이 고여 있다", "물도
하나같이 파도 진폭이 어마어마하게 큰지 윤슬 폭이 너무 넓어 물 같지 않다".

여기까지의 판정은 **하나같이 바닷가 관측점(대부도)** 만 썼습니다. "물이 없는
곳에서 물을 그리지 않는가" 를 아무도 묻지 않았고, 그래서 결함 셋이 판정을
전부 통과한 채 실기까지 갔습니다.

### 6.1 해수면이 방위를 안 가렸다

수심은 재면서 **"여기가 물이긴 한가"** 는 묻지 않았습니다. 3km 격자 안은
지형이 가려 주니 안 보였지만, 그 밖에는 가려 줄 것이 없어 수평선까지 물이
깔렸습니다.

같은 3×3 블록을 **줌 9(화소 약 243m)** 로 한 벌 더 받아 60km 물 마스크로
씁니다(`SEA_MASK_RADIUS_M`, `demGlsl('seaMask')`). 3km 안은 30m 자료가
정하고 그 밖만 마스크가 말합니다.

⚠ 성긴 것을 앞에 두면 안 됩니다. 화소 한 칸이 243m 라 해안선이 뭍 쪽으로
뭉개져 **바닷가에 선 관측자의 발밑 물이 통째로 뭍으로 읽혔습니다**
(675 → 128화소). 촘촘한 것이 먼저입니다.

### 6.2 옛 지면 원반이 새 지형을 덮고 있었다

5절에 "원반은 depthWrite:false 라 어디서도 남을 가리지 못한다"고 적었는데,
**깊이를 안 쓰는 것과 깊이 시험에서 이기는 것은 다른 이야기입니다.** 원반은
눈 아래 0.5 에 놓인 평평한 판이라 내려본각 θ 에서 깊이가 `0.5/sin θ`
입니다 — θ=1° 에서 29, θ=7° 에서 4.1. 새 지형·해수면은 반지름 120~470 의
각도 돔 위에 있으니 **거의 언제나 원반이 더 가깝고**, 나중에 그려지므로
색을 덮어씁니다. 실기에서 살아남은 것은 수평선 바로 아래 얇은 띠뿐이었고
(polygonOffset 이 스치는 각에서 크게 밀어 주는 자리), 나머지는 평평한
원반이었습니다. 사용자가 본 "둘레 땅이 전부 해발 0" 이 이것입니다.

고침은 순서 하나입니다 — 원반이 **먼저** 배경을 칠하고 새 메시가 그 위에
그립니다. 하늘 천체(은하수 −0.6, 해·달 −0.55, 별 −0.5)와 원반의 앞뒤는
건드리지 않습니다. 뒤집으면 지평선 아래로 진 해가 땅 위에 뜹니다.

**`verify-inland.js`** 가 해수면 메쉬가 **깊이 겨루기에서 이긴 화소**를
셉니다(같은 장면을 해수면만 끄고 한 번 더 찍어 차이를 봄 — 색으로 "물
같다"를 추측하지 않습니다). 네 방위 합:

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 내륙 도곡동 (70.7m) | 1,191화소 · 띠 0.46° | **0화소 · 0°** |
| 대부도 서안 (1.2m) | 675화소 · 띠 0.31° | 5,307화소 · 2.79° |
| 마니산 정상 (455.7m) | 1,328화소 · 띠 0.31° | 14,740화소 · 8.58° |

대조가 **둘**인 이유: 낮은 바닷가는 "바다를 통째로 지우기"를, 높은
바닷가는 "격자 가장자리 한 점만 보고 잇기"를 잡습니다(마니산은 바다가
거의 다 3km 밖이라 후자면 통째로 사라집니다).

### 6.3 물이 제가 비추는 하늘보다 밝았다

윤슬 폭을 재려 했더니 어떤 항을 더해도 폭이 **한 도도 안 움직였습니다** —
태양 쪽 수면이 이미 톤 곡선 천장(220~255)에 눌려 있었기 때문입니다. 그래서
더 날카로운 자로 바꿨습니다: **거울은 제가 비추는 것보다 밝을 수 없습니다.**
프레넬 반사율은 1 이하이고 내려본각 θ 의 잔잔한 수면은 고도각 θ 의 하늘을
비추므로, 같은 화면에서 `수면(−θ) ≤ 하늘(+θ)` 여야 합니다.

재 보니 **1.148 ~ 1.196배**. 원인은 물빛을 `atm_display_ground` 로 표시한
것이었습니다 — 그 함수에는 어두운 흙바닥을 살리려는 눈 순응(해가 낮으면
최대 3배)이 들어 있는데, 거울에 비친 하늘까지 그 배수를 먹었습니다.
되비침(하늘·태양)에서만 그 배수를 미리 나눠, 되비침이 하늘과 **같은
노출**로 표시되게 했습니다(`atm_groundEyeAdapt`). 수체·바닥·포말은 조도 ×
알베도라 지면과 같은 것이므로 그대로 둡니다.

### 6.4 윤슬 항이 아예 없었다

태양 쪽이 밝은 것은 프레넬 × 하늘뿐이었고, 좁고 반짝이는 길이 없었습니다.
Cox-Munk 경사 확률밀도를 그대로 넣습니다 — 폭을 정하는 것은 σ 하나입니다
(`σ² = 0.003 + 0.00512·U`, 바람은 옛 원반 물과 같은 값을 씁니다).

**`verify-glitter.js`** 는 윤슬을 **켜고 끈 두 장의 차이**로 윤슬만
남깁니다(넓은 하늘 되비침이 천장을 채우고 있어 화면을 통째로 재면 안
움직입니다). 방위 방향 반높이 폭:

| 내려본각 | U=1 | U=4 | U=8 |
|---|---|---|---|
| 0.6° | 2° | 4° | 5° |
| 1.2° | 3° | 4° | 5° |
| 2.4° | 3° | 5° | 6° |
| 5.0° | 4° | 6° | 8° |

고치기 전에는 밝은 얼룩의 폭이 43~68° 였고 풍속에 **전혀** 반응하지
않았습니다. 물/하늘 비는 1.148~1.196 → 0.983~1.000 이 됐습니다.

### 6.5 남은 것

- 태양 둘레 ±20° 가 여전히 밝게 포화합니다. 그 자리 **하늘 자체**가 같은
  밝기라(비 0.99) 수면은 하늘과 어긋나지 않습니다 — 남은 것은 수면이
  아니라 하늘 노출·톤 곡선의 문제입니다.
- 물 마스크 밖(60km 너머)은 여전히 가장자리 값으로 잇습니다. 눈높이
  300m 를 넘는 자리에서만 닿는 거리입니다.
- 3km 밖 지형은 아직 옛 31방위 능선 띠가 맡습니다.

## 7. 두 번째 실기 보고 — 그림자와 먼 산

> 산의 높이나 기울기가 실제 높이보다 조금 과장돼 보여. 그리고 땅에는 태양에
> 의한 물리적 그림자가 생기지 않아. 그러니까 산에 의해 산 뒤쪽 땅에
> 그림자같은게 안생겨. 그리고 구름의 그림자도 땅에 안보여

### 7.1 지형이 제 뒤 땅에 그림자를 드리우지 않았다

지면 조명이 램버트 `ndl` 하나였습니다. 그건 **제 사면이 해를 등졌는가**만
답합니다. 산이 그 뒤 땅을 가리는지는 전혀 다른 질문이고, 아무도 묻지 않고
있었습니다.

프래그먼트에서 태양 쪽으로 DEM 을 훑어 **지평선각**을 구합니다. 그 각이
태양 고도보다 높으면 그늘입니다. 걸음은 로그(화소 한 칸 → 약 3.5km,
36걸음)이고, 경계는 **태양 원반**(각반경 0.265°)만큼 흐립니다 — 임의로 고른
흐림이 아니라 반그림자의 실제 폭입니다. 자료 밖으로 나가면 거기서 멈춥니다.

⚠ 깎는 것은 **직달 몫뿐**입니다. 그늘도 하늘은 봅니다.

`verify-terrain-shadow.js` (마니산 정상, 3km 안 455m 기복):

| 해 고도 | 그늘 비율 | 그늘 밝기 | 양지 밝기 |
|---|---|---|---|
| 5° | 6.30% | 57 | 161.7 |
| 15° | 2.60% | 54.8 | 130.5 |
| 40° | 0.64% | 55.6 | 156.6 |
| 80° | 0% | — | 172.5 |

면적만 보면 "어디든 어둡게 칠하기"가 만점이라 대조가 넷입니다: 해를 올리면
단조 감소하고 머리 위에선 0, 해 방위를 180° 돌리면 그늘 집합이 바뀌고
(IoU 0.0868), 평평한 땅에는 0/116,148화소, 그늘이 새까맣지 않으면서
(밝기 ≥ 20) 뚜렷이 어둡습니다(양지의 0.35~0.42배).

### 7.2 구름 그림자가 땅에 없었다

그림자는 **구름끼리**(상층 → 중층)만 있었습니다(`verify-cloud-shadow.js`).

새 자료는 필요 없었습니다. 구름은 이미 (방위 × 고도) 격자로 있고, 고도 H
의 층을 고도각 ε 로 본다는 것은 곧 지상 거리 `H / tan ε` 를 본다는 뜻이라
그 격자가 곧 그 층 수평면의 극좌표 지도입니다. 지상 점 p 에 해가 닿으려면
햇빛이 층을 지나는 자리는 `q = p + 태양수평방향 · (H / tan 태양고도)` 이고,
그 q 를 관측자 기준 방위·고도각으로 되돌려 **CloudDeck 과 같은 운량장**을
읽습니다. JS 에서 96×96 투과율 지도로 구워 셰이더에 넘깁니다.

⚠ **관측자 발밑을 1 로 맞춰** 내보냅니다. 씬은 이미 직달광에
`1 − overheadOvercast` 를 곱하고 있어서, 그 위에 절대값을 다시 곱하면
운량을 제곱합니다. 이 항이 더하는 것은 **무늬**뿐입니다.

`verify-cloud-ground.js`: 저층 1.5km · 해 20° → 그늘 무게중심 남 −4,125m
(예상 −4,121m). 해 12° 로 낮추면 −7,113m (예상 −7,057m). 화면(평지 1km
위): 맑음 σ 0 · **온통 흐림 σ 0** · 구름 한 덩이 σ 31.3.

### 7.3 "산이 과장돼 보인다" — 앞산이 아니라 뒷산 문제였다

짐작 둘이 다 틀렸습니다. 카메라 시차도, 기하 부풀림도 아니었습니다. 화면
에서 재 보니 **앞산이 커진 게 아니라 뒷산이 주저앉아** 있었습니다.

3km 밖을 맡던 옛 능선 띠는 방위마다 **5·15·40km 딱 세 점**만 봅니다.
진짜 봉우리는 그 사이 아무 데나 있으므로(도곡동에서 2.6·6.7·8.1·12.9·
19.6km …) 대부분 놓칩니다. 3km 안은 진짜 높이장이라 제 높이로 서니,
앞산만 우뚝하고 뒤는 납작한 그림이 됩니다.

같은 방식을 3km 밖으로 잇습니다 — 이미 물 마스크로 받고 있던 성긴
패치(줌 9)를 그대로 써서 3~55km 격자를 하나 더 놓습니다. **새로 받는
타일은 없습니다.** 발밑 고도만은 촘촘한 패치로 짚습니다(`eyePatch`) —
성긴 것으로 읽으면 70.7m 대 59.8m 라 3km 이음매에 0.21° 층계가 섭니다.

`verify-far-terrain.js` (도곡동 24방위):

| | 치우침 | 절대중앙값 | 최대 |
|---|---|---|---|
| 옛 능선 띠만 | −0.346° | 0.298° | 3.258° |
| 먼 지형 격자 | −0.003° | 0.080° | 0.588° |

남쪽이 가장 나빴습니다 — 6.7km 의 3.99° 짜리 산이 0.73° 로 깔려
있었습니다. 지금은 3.72° 입니다.

⚠ **판정이 먼저 틀렸습니다.** 참조를 전부 성긴 DEM(화소 121m)으로 만들었는데
화면은 3km 안을 촘촘한 DEM(화소 15m)으로 그립니다. 성긴 쪽이 봉우리를 깎아
(같은 자리 발밑 59.8m 대 70.7m) 그 차이가 통째로 "결함"으로 나왔습니다 —
남서쪽 +4.4°. 참조를 앱과 같은 자료로 맞추고서야 진짜 결함이 드러났습니다.
**자료 차이를 우리 결함으로 읽는** 함정입니다.

### 7.4 남은 것

- 먼 지형이 화소 243m 라 봉우리가 조금 깎입니다. 더 촘촘하게 하려면 패치를
  한 벌 더 받아야 합니다.
- 옛 능선 띠는 그대로 둡니다 — 성긴 패치가 없을 때 그 자리를 받습니다.
- 지형 그림자 레이마치가 화소당 36탭입니다. 실기에서 프레임이 무거우면
  먼 지형 격자에서만 걸음 수를 줄이는 것이 첫 손댈 곳입니다.

## 8. 세 번째 실기 보고 — 첨탑·엉킨 물가·판지 같은 산·파란 앞산

> 첫번째 사진은 대부도에서 찍은 사진인데 기괴하게 솟아오른 지형이 있어.
> 그리고 물가와 바닷가가 엉켜서 보여. 두번째 사진을 보면 바닷가와 땅 사이
> 경계에 이상하게 상자 모양으로 각진 모양이 발생해. 세번째사진을 보면
> 여전히 지형에 자연스러운 그림자가 존재하지 않아서 산에 입체감이 느껴지지
> 않아. 마지막 사진을 보면 앞쪽의 산이 원인불명으로 파랗고 밝게 보여져.

### 8.1 바다 한복판의 첨탑 — 저줌 타일의 튀는 화소

원시 화소를 떠 보니 대부도 서쪽 6.6km 바다에서 이웃이 전부 0~31m 인데
**한 열만** R 이 128 → 125·134 로 어긋나 −648m 와 **+1572m** 이 나왔습니다.
화면에는 고도각 **8.96°** 짜리 첨탑입니다(그 방위의 99.9% 값은 0.87°).

R 한 단계가 곧 **256m** 이므로 결함은 반드시 그만큼씩 어긋나고, 실제 지형은
화소 한 칸(줌 9 에서 243m)에서 200m 를 못 뜁니다. 그 사이에 문턱을 둡니다.
이웃은 **대각선 넷**만 씁니다 — 결함이 한 화소 폭의 줄이라 상하좌우는 그
줄에 같이 얹힐 수 있어도 대각선은 행도 열도 다릅니다.

| | CPU 원본 | CPU 걷어냄 | 화면 끔 | 화면 켬 |
|---|---|---|---|---|
| 대부도 | 8.96° @280° | 1.66° @63° | 7.97° | **1.62°** |
| 도곡동 | 3.90° @179° | 3.90° @179° | 3.77° | **3.77°** |

아랫줄이 대조입니다 — 진짜 산은 한 치도 안 움직입니다.

### 8.2 엉킨 물가 — 0 을 믿는 기준을 값에서 기울기로

대부도 근거리 DEM 58만 화소 중 **38.55% 가 정확히 0**, 10.21% 가 −0.5~0
입니다. 옛 규칙 "정확히 0 = 모르는 곳 = 999m" 는 값 하나로 갈랐고, 그러면
화소 한 칸 차이로 수심이 999m 와 0.2m 를 오갑니다.

가르는 **재료**를 바꿉니다: 잘린 먼바다는 값이 0 일 뿐 아니라 **기울기가
0 인 고원**이고, 진짜 얕은 바닥은 기울어져 있습니다. 포말도 바닥 기울기로
폭을 정합니다(부서지는 띠 = 수심 ÷ 기울기, 넓게 퍼지면 옅어짐).

| | 옛 규칙 | 지금 |
|---|---|---|
| 줄당 갈래 뒤집힘 | 3.13 | **1.58** |
| 포말 | 14.02% | **7.67%** |
| 물 | 4,535화소 | 11,249화소 |
| 뭍 | 86,281 | 86,281 (안 옮김) |

**두 번 헛짚었고 두 번 다 기존 판정이 잡았습니다.** "반경 150m 안에 뭍이
있으면 얕다" 는 5단계에서 없앤 **거리 고리**를 되살려 거리 변동 69.44% 로
걸렸고, "값이 0 에 가까울수록 못 믿는다" 는 진짜 얕은 물까지 깊게 만들어
**얕을수록 밝다**를 0.488배로 뒤집었습니다.

**남은 것:** 경계의 각짐(2차 차분 **1.634**)은 그대로입니다. 매끄럽게 한
고도로 갈라 봤지만 **1.945** 로 오히려 나빠져 뺐습니다 — 0 등고선이 곡선이
아니라 고원의 가장자리, 곧 화소 모서리이기 때문입니다.

⚠ **이 두 수치는 나중에 고쳐졌습니다.** 예전에는 2.286 · 2.571 로 적혀
있었는데, 그것을 낸 자가 줄마다 경계를 **하나만** 세어 384줄 중 29~37줄만
쓰고 있었습니다. 그 표본으로는 1.4 와 2.5 를 못 가르고, 실제로 격자 밀도를
바꾸면 값이 오르락내리락했습니다. 모든 경계를 세도록 고쳐 표본이 176~254 로
늘었고, 위 값은 그 자로 다시 잰 것입니다 — **화면이 달라진 것이 아니라 자가
달라졌습니다.**

### 8.3 판지 같은 산 — 재 보고 짐작 셋을 다 버렸다

마니산 정상에서 네 조명으로 쟀더니 어느 쪽이든 σ 가 평균의 1% 안팎입니다.
원인을 하나씩 지웠고 **짐작이 세 번 다 틀렸습니다**:

① 법선이 뭉개졌나 → 아닙니다. 수평 해로 비추면 σ 6.38, 범위 43~118.
② 표시의 최소 밝기 바닥이 지우나 → 앱 조도에서는 아닙니다. 해 1° 에서도
   지형이 155 라 바닥(54)에 안 닿고, 껐다 켠 값이 같습니다. (처음에 σ 가
   0 으로 나온 건 하네스 조도를 10배 작게 어림잡은 **제 자의 잘못**입니다.)
③ 직달광이 약한가 → 앱 모형의 수평면 직달은 하늘의 0.094배로 실제(약 3.4배)
   보다 36배 작습니다. 그런데 물리 비율로 올려도 σ 는 1.68 → 2.16 뿐입니다.

남은 설명은 **기하 그 자체**입니다. 해가 25° 면 거의 수직인 법선들이 전부
sin25° = 0.42 라는 같은 받침 위에 놓이고, 이 자리 DEM 의 경사 중앙값이
13.6° 로 완만합니다. 그래서 **아무것도 고치지 않았습니다.** 시험 삼아 넣었던
천공률 `(1+cos θ)/2` 는 물리로는 맞지만 급사면을 밝게 하는 암반 알베도와
정확히 반대로 작용해 **음영을 오히려 줄여**(σ 1.192 → 0.618) 뺐습니다.

`verify-relief.js` 는 고침을 주장하지 않고 **재 본 값을 못 박습니다.**

### 8.4 파란 앞산 — 연무 색은 그 방향의 하늘이라야

새 지형은 방위 여섯 곳을 평균한 **한 값**을 연무 끝색으로 썼습니다. 새벽
해 쪽 지평선은 주황, 반대쪽은 파랑인데 그 둘을 섞은 값을 양쪽에 다 발랐던
것입니다. 옛 능선 띠는 이미 방향별 하늘색을 쓰고 있었으니 새 지형만
뒤처져 있었습니다.

**연무는 하늘 쪽으로 섞는 것이므로 지형이 제 뒤 하늘보다 더 파랄 수는
없습니다.** 그런데 그랬습니다:

| | 지형 색조(파랑/빨강) | 하늘 색조 | 어긋남 |
|---|---|---|---|
| 옛 평균 한 값 | 1.099 | 0.900 | 0.199 |
| 방향별 하늘색 | 0.913 | 0.922 | **0.009** |

대조로 **가까운 지형은 제 흙색을 지킵니다**(해 반대쪽 색조 0.624).

곁들여 `verify-shore` 가 한 번 깨졌는데 하네스가 태양 자리를 안 넣고 있어서
였습니다. 넣으니 β 응답이 오히려 강해졌습니다(뿌연날 25.0 대 맑은날 13.7,
예전엔 5.6 대 7.4).

## 9. 네 번째 물음 — 옛 원반과 태양의 절대 밝기

> "일단 옛 원반은 없애도 되지 않을까? 그리고 태양을 실제 우주의 거리와 우주의
> 크기로 반영하고 실제 밝기로 해서 계산하는건 효과가 있을까? 그게 무리라면
> 물리비로 옮기고 노출을 조정하자"

### 9.1 옛 원반 — 평소엔 안 보이지만 지우면 안 됩니다

원반을 껐다 켠 두 장의 차이 화소를 셌습니다(세 자리 × 여덟 방위 × 두 내려본각,
`build-disc-need.js`). 색으로 "원반 같다"를 추측하지 않고 **원반이 실제로 이긴
화소**만 셉니다.

| 자리 | 원반 화소 | 총 화소 | 비율 | 최악 한 장 |
|---|---|---|---|---|
| 내륙(도곡동) | 167 | 1,048,576 | 0.016% | 81 |
| 바닷가(대부도) | 481 | 1,048,576 | 0.046% | 89 |
| 높은 곳(마니산) | 8,482 | 1,048,576 | 0.809% | 1,406 |
| **DEM 없음** | 734,752 | 1,048,576 | **70.07%** | 54,272 |

DEM 이 실리면 원반은 화면의 1% 아래입니다 — 화면을 만드는 것은 근거리 지형 ·
먼 지형 · 해수면입니다. 그런데 **DEM 이 없으면 원반이 지면의 70%** 입니다.
타일을 받기 전, 못 받았을 때, 자료가 없는 자리에서 유일한 지면이 그것입니다.
그러니 원반은 죽은 코드가 아니라 **대비책**이고, 지우는 대신 그 자리에 못
박습니다(`verify-disc-need.js`, 단언 15).

⚠ 예전 `verify-handoff.js` 는 **하늘 구멍**만 봤고, 원반을 통째로 빼도 구멍이
0 이었습니다 — 그 자로는 이 물음에 답할 수 없습니다.

⚠ 하네스가 스스로를 속인 적도 있습니다. 카메라를 원반과 같은 높이(y=0)에 뒀더니
원반이 모로 서서 한 화소도 안 잡혔고, "원반이 안 보인다"가 그냥 결함이었습니다.
그래서 **지면 화소 > 0** 단언을 먼저 겁니다.

### 9.2 태양의 실제 거리·크기 — 이미 들어 있습니다

- 시직경 0.533° 로 원반을 그립니다 (`SunMesh.ts`).
- 그림자 경계도 그 각반경 0.265° 만큼 흐립니다 (`TerrainField.ts` 의 반그림자).
- 거리는 각크기에 흡수됩니다 — 1억 5천만 km 를 좌표로 들고 있어 봐야 화면에
  나타나는 것은 각크기 하나뿐이고, 부동소수 정밀도만 잃습니다.

**빠져 있던 것은 거리도 크기도 아니라 밝기의 눈금이었습니다.**
`directBeamRGB` 가 돌려주는 것은 **투과율**입니다(0~1). 대기가 얼마나 깎아
먹는지만 있고 깎이기 전의 절대 밝기 — 태양 상수 — 가 없습니다. 반면 하늘 쪽
`skyRadiance` 는 사진에 맞춰 눈금이 잡힌 복사휘도입니다. 둘을 그대로 더하면
**직달이 확산보다 어두운** 세상이 나옵니다.

필요한 배수를 재 봤습니다. `S(고도) = ρ(고도) · π · L̄ / (beam · sin(고도))`,
ρ 는 이 저장소가 이미 쓰는 Meinel & Meinel 짝(직달 `0.7^(AM^0.678)`,
확산 `0.3·(1 − 0.7^AM)`):

| 해 고도 | beam(투과율) | 하늘 L̄ | 물리 직달/확산 ρ | 필요한 눈금 S |
|---|---|---|---|---|
| 80° | 0.791 | 1.155 | 7.65 | 35.7 |
| 60° | 0.770 | 0.817 | 6.67 | 25.7 |
| 40° | 0.711 | 0.746 | 4.85 | 24.8 |
| 20° | 0.548 | 0.546 | 2.48 | 22.7 |
| 10° | 0.333 | 0.385 | 1.23 | 25.7 |
| 6° | 0.191 | 0.263 | 0.73 | 30.2 |

중앙값 **26**, 폭 22.7~35.7. **상수 하나로 −12%/+37% 안에 듭니다** — 빠져
있던 것이 고도에 따라 변하는 무엇이 아니라 그냥 눈금이었다는 뜻입니다.
그래서 "실제 밝기로 계산하자"와 "물리비로 옮기자"는 **같은 한 상수**입니다.

⚠ 4° 아래에서는 S 가 발산합니다(3° 45, 1° 110). Meinel 의 확산 근사가 큰
대기질량에서 무너지기 때문입니다. 그 자리는 `sin(고도)` 가 작아 직달 항 자체가
거의 0 이라 화면에 안 나타납니다. 근거 없는 고도별 곡선을 넣지 않습니다.

### 9.3 옮긴 결과 — 직달을 두 번 세고 있었습니다

눈금을 채우는 김에 드러난 결함이 하나 더 있습니다. `uSurfaceIrr` 에는 이미
수평면이 받는 직달 몫이 들어 있는데 거기에 `uSunRadiance · ndl` 을 **또**
더하고 있었습니다. 사면의 향과 무관한 직달 받침이 깔리니, 해를 등진 면도
마주한 면과 같은 몫을 먼저 받습니다. 8.3절의 판지가 여기서도 나옵니다.

받침을 빼고 제 각도의 몫만 넣었습니다. 평평하고 위를 보는 면은 `ndl = sin(고도)`
라 값이 정확히 같고, 기울어진 곳만 달라집니다.

노출은 같은 자리에서 되맞춥니다 — `보정 = (L̄ + beam·sin/π) / (L̄ + S·beam·sin/π)`.
**평평한 지면의 밝기는 그대로**이고 사면만 밝고 어두워집니다. 그래야 물·옛
원반과의 밝기 견줌이 그대로 성립합니다.

마니산 정상, 해 25°, 같은 셰이더에서 눈금만 바꾼 A/B:

| | 평균 | 음영의 퍼짐 σ |
|---|---|---|
| 옛 눈금 (S=1) | 131.9 | 1.492 |
| 물리 눈금 (S=26) | 152.5 | **2.088** (+39.9%) |

네 방위 전체로도 σ 가 1.02~1.65 에서 **1.83~2.87** 로 올랐고, 무엇보다
**해의 방향이 화면을 좌우하게 됐습니다** — 가장 밝은 방위가 가장 어두운 쪽의
1.06배였던 것이 **1.86배**(94 / 153 / 147 / 82)가 됩니다. 어느 쪽에서 비추든
같은 그림이던 것이 판지의 정의였습니다.

⚠ **물과 옛 원반에는 걸지 않았습니다.** 수면은 평평해서 `ndl` 로 얻을 입체감이
없고, 윤슬은 이미 클램프가 봉우리를 자르고 있어 스물여섯 배를 그대로 넣으면
잘리는 자리가 넓어져 **윤슬이 다시 두꺼워집니다** — 6절에서 고친 결함입니다.
평평한 지면의 밝기가 보존되므로 물·육지의 밝기 견줌은 그대로입니다.

남은 것은 여전히 태양 고도와 완만한 경사입니다. 수평에서 비추면 σ 가 8.62 라,
2.088 은 아직 그 4분의 1 입니다.

## 10. 물가를 거리장으로 — 자료를 바꾸기 전에 잰 것

> "지금 우리가 이쁘게 지형이 안 만들어지는 게 rgb로 만들어진 고도 데이터를 써서
> 그런 거 같은데, 이걸 등고선 데이터를 기반으로 만들면 특히 수면과 이어지는
> 부분이 이쁘게 그려지지 않을까?"

### 10.1 먼저 — 자가 결론을 낼 만큼 두껍지 않았습니다

8.2절의 경계 각짐은 줄마다 "뭍에서 물로 넘어가는 **첫** 자리" 하나만 적었습니다.
384줄 중 **29~37줄**만 쓰였습니다. 그 표본으로는 1.4 와 2.5 를 못 가르고,
실제로 격자 밀도를 흔들자 값이 오르락내리락해서 **"거리장이 오히려 나쁘다"는
잘못된 결론이 나올 뻔했습니다.**

모든 경계를 적도록 고쳤습니다 — 뭍↔물이 바뀌는 자리를 방향 가리지 않고 전부
모으고, 이웃 줄에서 8화소 안에 있는 것끼리 짝지어 2차 차분을 냅니다. 표본이
**176~254줄**로 늘고 숫자가 단조로워졌습니다.

두 하네스가 서로를 확인합니다: `build-shore-sdf.js` 의 '앱 그대로' 칸이
**1.634** 로 `verify-shorepatch` 와 같은 값을 냅니다. 다르면 둘 중 하나가
앱이 아닌 것을 재고 있다는 뜻입니다.

### 10.2 진단 — RGB 인코딩이 아니라 잘린 고원

대부도 근거리 패치(줌 13, 화소 15.21m) 78.6만 화소:

| | 비율 |
|---|---|
| 정확히 0 (잘린 먼바다) | **41.38%** |
| 0 < 고도 < 1m (갯벌) | 10.14% |
| 음수 (물속) | 12.50% |

가장 작은 양수가 **0.004m** — B 채널 눈금 1/256m 그대로입니다. **인코딩은
무손실이고 갯벌에는 밀리미터 값이 살아 있습니다.** 문제는 41% 짜리 평평한
고원입니다. 그 안에서는 기울기가 정확히 0 이라 **텍셀 안 어디에 물가가 있는지에
대한 정보가 없습니다.**

계단이 화면에서 차지하는 각(½텍셀 = 7.6m 기준): 100m 에서 4.35°, 500m 에서
0.87°, 1km 에서 0.44°, **7.5km 에서 0.06°(화면 1화소)**. 그러니 이 문제는
근거리 3km 패치에만 있고 먼 지형에는 없습니다.

### 10.3 잰 것 — 격자를 흔들고, 거리장을 넣고, 고도 흐리기와 견주고

`bake-shore-sdf.js` 가 같은 래스터에서 부호거리장을 만들어(정확한 유클리드
거리변환 → 가우시안 σ 1.6텍셀 → 띠 ±90m 안에서 고도를 `s·sdf` 로 재구성,
s = 그 띠의 실제 고도-거리 기울기 1:31) Terrarium 타일로 되씁니다.
**렌더러는 한 줄도 안 건드립니다** — 자료만 바꾼 A/B 입니다.

| 경우 | 경계 각짐 | 표본 |
|---|---|---|
| 앱 그대로 (해수면 96고리) | 1.634 | 191 |
| 원본 · 기본 격자 | 1.774 | 195 |
| 원본 · 살 2배 | 2.057 | 210 |
| 원본 · 살 4배 | 2.193 | 254 |
| **고도 흐리기 · 기본** | **1.945** (+9.6%) | 183 |
| **거리장 · 기본** | **1.568** (−11.6%) | 176 |
| **거리장 · 살 4배** | **1.936** (−11.7%) | 187 |

**① 경계는 격자가 아니라 자료가 정합니다.** 살을 늘릴수록 각짐이 **커집니다**.
성긴 격자가 계단을 뭉개 주고 있었을 뿐이라, 렌더링 쪽에서 더 짜낼 것이 없습니다.

**② 거리장은 −12% 를 줍니다.** 두 격자 밀도에서 11.6% / 11.7% 로 같으니
우연이 아닙니다. 그리고 **−12% 가 전부입니다** — 같은 래스터에서 만든 거리장은
텍셀 안의 정보를 지어낼 수 없고, 양자화된 계단을 고를 뿐입니다.

**③ 고도를 그냥 흐리면 오히려 나빠집니다**(+9.6%). 오래 논증으로만 있던 말이
이제 측정입니다. 이유도 분명합니다 — 고원 위에서 고도는 기울기가 0 이라 흐려도
여전히 0 이고 등고선이 다른 모서리로 옮겨갈 뿐입니다. **거리장은 어디서나
기울기가 1** 이라 흐리면 양자화된 계단이 원래 곡선으로 돌아옵니다. 갈래가 바뀐
화소도 거리장 0.836% 대 고도흐림 3.424% 로, 고도흐림이 해안선을 네 배 더
옮기면서 더 각집니다.

⚠ 거리장 타일은 고원(기울기 0)을 1:31 경사로 바꾸므로 셰이더의 `trust` 가 그
자리를 믿기 시작합니다 — 포말 8.1% → 10.7%. **−12% 가 순수한 경계 이득만은
아닙니다.** 판정에 그것도 못 박았습니다.

### 10.4 그래서 등고선인가 벡터 해안선인가

- **등고선으로 지형 면을 만드는 것은 뒷걸음입니다.** 등고선은 10~20m 간격이고
  애초에 DEM 에서 뽑은 파생물이라, 사이를 보간하면 계단식 단구가 생깁니다.
  면에는 래스터가 맞는 구조입니다.
- **벡터 해안선은 맞는 답입니다.** 선에는 벡터가 맞는 구조이고, 무엇보다
  래스터가 갖고 있지 않은 정보 — 텍셀 안의 물가 위치 — 를 가져옵니다.
- 다만 **이진 마스크로 구우면 계단이 그대로 돌아옵니다.** 부호거리장으로 구워야
  합니다. 그리고 같은 SDF 로 DEM 을 강제해야(hydro-enforcement) 두 자료가 다른
  말을 할 때 땅이 바다 위로 솟지 않습니다.

앱은 이미 OSM Overpass 를 쓰지만 **내륙 강·호수만**, 그것도 옛 원반용
128×128(7.4m/px) 텍스처에만 굽습니다. 해안선은 안 받습니다. Overpass 는
런타임 의존으로 위험하고(지금도 실패 시 0m 해안선으로 물러납니다), 벡터 타일은
MVT 디코딩 의존성이 늡니다. Terrarium 이 키 없는 AWS 공개 자료라는 장점과
맞바꿔야 하는 결정이라 자료원은 아직 정하지 않았습니다.

## 11. 다섯 번째 물음 — 해발 0m 이하가 다 물인가

> "내륙인데 해발고도가 0미터 이하인 곳들이 전부 내해일까? 실제 내해는 오히려
> 해발고도가 마이너스인 경우가 많던데."

지금 해수면 셰이더는 `hm <= uShoreOverlapM` 하나로 물을 가릅니다. 사실상
**"고도가 0 이하면 물"** 입니다. 정말 그런지 원시 타일에서 셌습니다.

### 11.1 재는 법

타일을 그대로 풀어 고도 배열을 만들고, **블록 테두리에서 0 이하만 밟고
번져 들어갑니다**(4-이웃 flood fill). 거기 닿은 0 이하는 "바다에 이어진 곳",
못 닿은 0 이하가 **"내륙인데 0 이하"** 입니다.

### 11.2 잰 것 — 근거리(줌 13)

| 자리 | >0 | 정확히 0 | 음수 | 가장 깊은 곳 |
|---|---|---|---|---|
| 대부도 (바닷가) | 46.12% | 41.38% | 12.50% | −9.00m |
| 마니산 (산꼭대기) | 51.76% | 42.32% | 5.92% | −5.33m |
| **도곡동 (순수 내륙)** | **99.97%** | **0.01%** | **0.018%** | **−15.00m** |

도곡동은 바다가 한 뼘도 안 걸치는 강남 한복판 11.6km 상자입니다. 그런데도
0 이하가 **150화소(0.025%, 0.034km²)** 있습니다. 20개 덩어리로 흩어져 있고
하나하나가 2,300~3,900m² — **건물 한두 채 크기**입니다:

```
  17화소 최저  −6.0m  @ 37.48870, 127.05893
  16화소 최저  −6.0m  @ 37.51636, 127.00688
  15화소 최저  −5.0m  @ 37.49031, 127.06676
  13화소 최저 −15.0m  @ 37.52958, 127.06547
  12화소 최저 −15.0m  @ 37.52097, 127.00009
```

전부 시가지 한복판입니다. **내해가 아니라 DEM 잡음** — SRTM 계열이 고층
건물 사이에서 레이더 그늘·보정 흔적으로 남긴 구덩이입니다. 깊이 분포도
−1~−4m 에 몰려 있고(78/150) 꼬리만 −15m 까지 갑니다.

### 11.3 그래서 "0 이하 = 물" 은 세 가지를 뭉갭니다

1. **먼바다** — 맞습니다. 이게 압도적 다수입니다.
2. **해수면보다 낮은 마른 땅** — 틀립니다. 투르판 −154m, 데스밸리 −86m,
   네덜란드 간척지. 한국에는 사실상 없어서 지금은 안 터집니다.
3. **0 보다 낮은 내해·호수** — 물인 것은 맞지만 **높이가 틀립니다.** 질문이
   정확히 짚은 대목입니다: 카스피해 수면은 −28m, 사해는 −430m 입니다.
   우리 해수면은 `y = 0` 짜리 한 장이라 카스피해에 가면 **주변 육지를
   28m 깊이로 잠급니다.** 물을 안 그리는 것보다 나쁩니다.

### 11.4 화면에서는 얼마나 되나

`verify-disc-horizon` 이 이미 재고 있습니다. 겹침을 0 → 10m 로 넓혀도
**내륙 물화소가 57,871 에서 한 개도 안 늡니다.** 그 57,871 은 도곡동의
60km 마스크가 서해에 닿아서 생긴 진짜 바다이고, 11.2절의 150화소짜리
구덩이들은 화면에 사실상 안 나옵니다. **지금 고칠 값이 아닙니다.**

### 11.5 덤으로 나온 것 — 줌에 따라 바다의 인코딩이 다릅니다

같은 자를 광역 타일(줌 9, 화소 243m)에 대 봤더니 딴판이었습니다:

| | 줌 13 (근거리) | 줌 9 (광역) |
|---|---|---|
| 정확히 0 | 41.38% | **0.08%** |
| 음수 | 12.50% | **43.87%** |
| 가장 깊은 곳 | −9m | **−648m** |

**광역 타일에는 수심이 들어 있습니다.** 8.2절·10.2절의 "Terrarium 은 먼바다를
정확히 0 으로 자른다" 는 **줌 13 이야기**이고, 광역에서는 틀립니다 — 낮은
줌의 바다는 SRTM(육지 전용)이 아니라 해저 지형 자료에서 옵니다.

실용적 결론은 안심하는 쪽입니다. 마스크 패치 쪽 바다는 0 고원이 아니라
뚜렷한 음수라, `hm <= 3` 판정이 근거리보다 **더** 안전합니다. 지형 쪽으로
겹침을 주면 안 된다는 금기(10절 ⚠)는 여전히 줌 13 의 0 고원 때문입니다.

### 11.6 진짜 빈 구멍은 반대쪽입니다

0 **이하**가 아니라 0 **보다 높은** 물 — 한강 수면(+5m 안팎), 소양호(+190m)
— 은 이 규칙으로 영원히 안 잡힙니다. 옛 원반의 OSM 마스크(uWaterTex2D)가
유일한 경로였는데 원반을 껐으니 그 경로가 사라졌습니다. 내륙 강·호수를
그리려면 해수면이나 지형 셰이더에 새로 넣어야 합니다 (9절 ⚠ 와 같은 항목).
