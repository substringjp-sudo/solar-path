# 해안선 계획 — 지면 기하를 다시 잡는다

> "지면기하 전체를 다시 잡더라도 보기 좋게 만들어줘. 지금 계속 수치만 잡았지만
> 별로 깔끔하게 문제가 해결된 것 같지 않아. 기본적으로 지형을 생성하고, 지형과
> 해수면을 동시에 실제 해안가처럼 만들고, 경계를 보기 좋게 만드는 방법"

지적이 맞습니다. 44~49절에서 제가 한 것은 전부 **바닥 칠하기**였습니다.
왜 그럴 수밖에 없었는지부터 적습니다.

## 1. 지금 구조 — 해안선이라는 것이 없습니다

| 요소 | 실제 정체 |
|---|---|
| 지면 | **완전한 평면 원반** (`CircleGeometry(475, 64)`, y ≈ −1.5). 고도 없음 |
| 지형 | 반지름 480의 **원통 띠** — 가장자리에 세운 배경 그림 |
| 육지/바다 | 그 평면 위의 **2D 마스크 텍스처** 하나 |
| 고도 자료 | 31방위 × 3거리 = **93점** (실루엣이지 높이장이 아님) |
| 수평선 | 원반을 `−R·tan(dip)` 만큼 **내려서** 흉내 |

그래서 다음이 전부 **원리적으로** 불가능합니다.

- **경계가 기하가 아닙니다.** 육지와 바다가 같은 평면이고 텍스처로만 갈립니다.
  물이 땅을 만나는 선이 없으니 물가도, 젖은 모래도, 파도가 부서지는 자리도
  만들 데가 없습니다.
- **수심이 없습니다.** 얕은 물이 밝고 초록빛인 것, 깊을수록 파래지는 것,
  포말이 얕은 곳에만 생기는 것 — 전부 수심에서 나오는데 그 값이 없습니다.
- **가려짐이 없습니다.** 곶이 만을 가리거나 섬 뒤가 안 보이는 일이 없습니다.
- **눈높이가 1.6m 로 박혀 있습니다** (`eyePos = vWorld.y + 1.6`). 그래서
  20m만 넘으면 전부 스침각이고, 보이는 바다의 거의 전부가 하늘 거울입니다
  (49.8 의 남은 판정이 이것입니다).

## 2. 자료 — 93점이 아니라 진짜 높이장을 받을 수 있습니다

**AWS Terrain Tiles** (Mapzen 파생, Registry of Open Data on AWS).
이 환경에서 실제로 확인했습니다.

```
https://s3.amazonaws.com/elevation-tiles-prod/terrarium/{z}/{x}/{y}.png
→ HTTP 200, 35KB, 256×256 PNG, 인증 없음
```

- **Terrarium 인코딩**: `고도(m) = R·256 + G + B/256 − 32768`
- 해상도 **약 30m** (1 arc-second), 전 지구, **얕은 수심 포함**
- 대부도 앞바다 z12 타일 실측: 고도 −2.8m ~ 138m, 음수(수심) 표본 126개.
  해안을 가로지르는 한 줄이 `5 9 45 16 55 5 −0 −0 −1 0 0` — 육지에서
  바다로 넘어가는 것이 그대로 보입니다.

타일 하나가 **65,536점**입니다. 지금 93점의 700배.

### 실무 메모 두 개

- ⚠ **선형보간은 안전합니다.** 처음에 "RGB 세 채널에 쪼개 담았으니 텍스처
  보간을 켜면 깨진다"고 적으려다 재 봤더니 **최대 오차 0.0m** 였습니다.
  디코드가 R·256 + G + B/256 로 **채널에 대해 선형**이라, 채널별 보간과
  디코드가 교환됩니다. 짐작을 적을 뻔했습니다.
- ⚠ **텍스처를 sRGB 로 읽으면 안 됩니다.** `NoColorSpace` 로 올려야 합니다.
  감마가 걸리면 고도가 통째로 어긋납니다. 이쪽이 진짜 함정입니다.
- JS 로 화소를 꺼낼 필요가 없습니다. PNG 를 그대로 **텍스처로 올리고
  버텍스 셰이더에서 디코드**하면 됩니다 — RN 에서 PNG 디코더를 붙이는
  문제가 통째로 사라집니다.

## 3. 그리는 방법 — 경계를 "그리지" 말고 **만나게** 합니다

업계 표준은 하나로 모입니다: **물과 땅을 각각 진짜 면으로 두고, 둘이 만나는
곳을 깊이로 읽는다.** (Crest Ocean, UE Water, Unity URP 물 셰이더가 전부
같은 뼈대입니다.)

### 3-1. 지면을 진짜 높이장으로

평면 원반을 **격자 메시**로 바꾸고, 버텍스 셰이더에서 DEM 텍스처를 읽어
y 를 올립니다. 관측자 중심 반경 몇 km 를 덮고, 바깥은 지금의 능선 띠가
그대로 이어받습니다(먼 지형을 빌보드로 두는 것은 표준이고 옳습니다).

- 격자는 관측자 중심 **동심원**이 좋습니다 — 가까울수록 촘촘해 화면 화소당
  삼각형 수가 고릅니다.
- 눈높이가 비로소 의미를 갖습니다. `eyePos` 를 관측 고도로 두면 언덕에서
  내려다보는 시선이 실제로 생기고, 그때 비로소 **수체가 보입니다**
  (49.8 의 남은 판정이 여기서 풀립니다).

### 3-2. 바다는 **따로 있는 면**

해수면 y = 0 인 별도의 면을 둡니다. 그러면

- **해안선 = 두 면의 교선.** 따로 그리지 않아도 만(灣)·곶·섬이 자동으로
  제 모양입니다. 지금처럼 마스크 가장자리를 다듬는 일 자체가 없어집니다.
- 방위 해상도 12° 한계가 사라집니다 — 30m 격자가 정하니까요.

### 3-3. 경계는 **수심**이 정합니다

물 셰이더가 같은 DEM 을 읽어 `수심 = 0 − 지형고도` 를 구합니다. 그 하나로
보기 좋은 것들이 전부 따라옵니다.

| 보이는 것 | 수심에서 어떻게 |
|---|---|
| 물가 포말 띠 | 수심 < 약 0.5m 에서 띄우고 부드럽게 꺼짐 |
| 포말 폭이 지형마다 다름 | 완만한 모래밭은 넓고, 절벽은 좁음 — **거리가 아니라 수심**으로 재니 저절로 |
| 얕은 물의 초록빛 | 수체 흡수를 `exp(−k·수심)` 로. 붉은빛이 먼저 먹혀 청록이 남음 |
| 젖은 모래 | 물가 안쪽 육지를 **어둡게 + 매끈하게**(거칠기↓). 색만 바꾸면 안 됩니다 |
| 파도가 얕은 데서 서는 것 | 진폭을 수심으로 눌러 부서지게 |

깊이 버퍼(screen-space) 방식도 있지만 우리는 **DEM 을 이미 들고 있으므로**
바로 샘플하면 됩니다 — 더 간단하고 합성 순서에 안 휘둘립니다.

### 3-4. 지금 것 중 살릴 것

49절에서 물리로 되돌린 것들은 그대로 씁니다 — 조도 × 알베도로 바뀐 수체·
거품, 진짜 프레넬, Cox-Munk 윤슬, 순응 몫으로 나눈 밤빛. 그 위에 **기하와
수심**이 얹히는 구조입니다.

| 단계 | 내용 | 판정 |
|---|---|---|
| 1 ✅ | DEM 타일 가져오기 · 셰이더 디코드 · 캐시 | 알려진 좌표의 고도가 맞는가 |
| 2 ✅ | 지면을 동심원 격자 + 버텍스 변위로 | 능선 실루엣이 자료와 맞는가 |
| 3 ✅ | 눈높이를 관측 고도로 | 수평선 각도가 `dip` 과 맞는가 (2단계에서 같이 풀렸습니다) |

| 5 ✅ | 수심 기반 포말·색·젖은 모래 · 땅색 | 물빛이 거리가 아니라 수심을 따르는가 |

### 1단계 결과 (`src/utils/demTiles.ts`, `verify-dem.js` — 15개 단언)

대부도 앞바다 (37.25N 126.58E) 반경 3km, 줌 13, 3×3 타일 (589,824점):

| | 값 |
|---|---|
| 셰이더 대 CPU 직접 디코드 (같은 자료) | 중앙 0m · **최대 0.01m** |
| 셰이더 대 Open-Meteo (다른 DEM) | 상관 **0.9687** · 치우침 0.23m · 중앙 2.5m |
| 바다(참조 0m) 평균 / 뭍(≥20m) 평균 | 1.67m / 40.26m |

Open-Meteo 와의 최대 차 21.7m 는 우리 결함이 아니라 **자료끼리의 차이**입니다.
문제의 봉우리를 Terrarium z13/14/15 최근접으로 따로 풀어보면 114 / 116 / 115m
로, 셰이더가 읽은 115.3m 이 맞습니다. Open-Meteo 쪽이 137m 라고 합니다.

**여기서 실제로 잡은 결함 둘:**

1. **합성할 때 타일 줄을 뒤집어** 놓아 블록 y 가 반사됐습니다 (최대 137m).
   원인은 "카메라 위쪽이 2 이니 타일 y 를 뒤집어야 한다"는 짐작이었는데,
   `flipY = false` 라 판 아래쪽(uv v=0)이 이미 PNG 첫 줄(북쪽)이었습니다.
   두 번 뒤집은 셈입니다.
2. **2×2 블록이면 관측자에서 한 타일이 남는다**고 잘못 알았습니다 (최대
   50.6m). 실제로 보장되는 여유는 **(한 변 − 1) / 2 타일**이라 2×2 는 반
   타일뿐입니다. 블록을 **홀수 3×3** 으로 바꿔 관측자 타일을 정중앙에 두고,
   줌 선택도 그 여유로 계산하게 고쳤습니다.

**판정을 짜면서 배운 것 — 참조 하나로는 부족합니다.**
뒤집기를 일부러 되살려 대조했더니, 관측자가 블록 정중앙이라 뒤집기가 표본
무게중심에 대한 **반사**가 되어 Open-Meteo 상관이 0.9118 로 **통과해 버렸고**,
치우침도 −2.82m 로 통과했습니다. 잡은 것은 CPU 직접 디코드 비교(최대 42.11m)
뿐이었습니다. 반대로 **평행이동**은 상관이 잘 잡습니다 — 0.03타일(117m)만
어긋나도 0.9687 → 0.8300 으로 떨어집니다. 그래서 둘 다 답니다.
같은 이유로 ① 에서 일하는 값은 중앙이 아니라 **최대**입니다(반사는 가운데
표본을 안 건드려 중앙오차가 0m 인 채로 통과합니다).

### 2단계 결과 (`src/components/SkyScene3D/TerrainField.ts`, `verify-terrain-field.js` — 17개 단언)

**미터 평면이 아니라 각도 격자입니다.** 이 씬은 반경 500 돔에 각도로 그리고
구름·능선 띠·나침반·천체가 전부 그 규약 위에 있습니다. 여기에만 미터
좌표계를 들이면 3km 지점이 돔 밖으로 나가 깊이 순서가 통째로 깨집니다.
그래서 정점을 **실제로 보이는 고도각**에 놓습니다:

    낙차   = d² / 2R          (지구 곡률)
    고도각 = atan2(고도 − 눈높이 − 낙차, d)

가림은 **반경이 정합니다.** 반경을 거리의 단조 증가 함수로 두면, 카메라가
메시 원점에 있으므로 깊이 = 반경이고 "가까운 것이 항상 앞"이 공짜로
성립합니다. 반경은 오직 깊이 순서만 나르고, 보이는 자리는 전부 고도각이
정합니다.

| 재는 것 | 값 |
|---|---|
| 그려진 실루엣 대 CPU 참조 | 중앙 **0.018°** · 최대 0.119° · 상관 **0.99999** |
| 치우침 | −0.0028° |
| 평평한 판 대조 (손으로 푼 −0.044°) | 실측 −0.0243° · 편차 0.020° (화소 양자화) |
| 열 → 방위 직접 대조 | 최대 0.054° |
| 삼각형 | 65,024 (고리 128 × 살 256) |

**눈은 반드시 그려지는 그 면 위에 서야 합니다.** 처음에 바깥 고도(0m)를
믿었다가 DEM 이 말하는 이 지점의 실제 42m 에 눈이 파묻혀 지평선각이 **72°**
로 나왔습니다. 가장 가까운 고리(12m)에서는 5m 차이가 22° 로 벌어집니다.
그래서 발밑 고도를 `dem_elevationAt(vec2(0.0))` 으로 **DEM 자신이** 정하게
했습니다. (3단계가 여기서 이미 풀렸습니다.)

**판정이 잡은 결함 — 지상 좌표의 남북 부호.** 방위 A(북에서 시계방향)의
지상 좌표는 `(동, 남) = (sin A, −cos A)` 인데 참조와 `horizonAngleDeg` 가
`+cos A` 를 썼습니다. 격자 생성기도 같은 실수를 했지만 거기서는 한 바퀴를
반대로 돌 뿐이라 **아무 증상이 없어** 놓치기 쉽습니다.

    거울상일 때:  중앙 1.339° · 최대 6.537° · 상관 0.883
    고친 뒤:      중앙 0.018° · 최대 0.119° · 상관 0.99999

⚠ **상관 이동으로 어긋남을 찾으면 안 됩니다.** 그렇게 했다가 −19.9° 에서
봉우리가 나왔는데, 지형 신호의 저주파 성분이 만든 가짜였습니다. 실제 방위
매핑은 멀쩡했고(0.054°), 틀린 것은 지상 좌표 쪽이었습니다. **매핑을 직접**
재야 합니다 — 48절에서 배운 것과 같습니다.

**살 수는 훑어서 골랐습니다** (최대오차 / 삼각형):

    128 (2.81°) 0.240° / 32,512     512 (0.70°) 0.085° / 130,048
    256 (1.41°) 0.119° / 65,024 ←   1024(0.35°) 0.085° / 260,096 (수렴)

256 의 0.119° 는 읽기 해상도(행 0.0586°)의 두 칸입니다. 512 로 가도 0.034°
밖에 못 줄이는데 삼각형은 두 배입니다.

### ⚠ 3단계가 아니라 **4단계**가 먼저 필요했습니다 (해결됨)

격자는 3km 에서 끝나고, 바다 방위에서 바깥 고리는 **−0.846°** 입니다.
그런데 눈높이 43.6m 의 진짜 수평선은 **−0.212°** 입니다. 그 사이 **0.634°**
가 격자가 안 덮는 띠였습니다 (44절에서 지면과 구름이 서로 다른 지평선을 써서
0.79° 띠가 벌어진 것과 같은 부류).

**4단계의 해수면이 그 자리를 이어받았습니다.** 해수면은 수평선 거리
`sqrt(2Rh)` 까지 뻗고 그 너머는 접습니다. 4단계 판정이 "맨 위가 물인 방위의
각 = −dip" 을 손으로 푼 답과 견줘 확인합니다.

### 4단계 결과 (`SeaPlane.ts` + `groundProjection.ts`, `verify-coastline.js` — 17개 단언)

**투영을 한 곳으로 뽑았습니다.** 땅과 물이 같은 자로 재야 교선이 성립합니다
(44절에서 지면과 구름이 서로 다른 지평선을 쓰다 0.79° 띠가 벌어졌습니다).
`groundProjection.ts` 의 `gp_project` 하나를 양쪽이 쓰고, 눈높이도 DEM 이 정한
같은 값을 씁니다.

**가림이 공짜로 맞습니다.** 반경이 거리의 단조 증가 함수라서:

- 물 위의 땅 → 같은 각의 바다는 **더 먼** 곳 → 반경이 큼 → 땅이 이김 ✓
- 물 아래의 땅 → 같은 각의 바다는 **더 가까운** 곳 → 반경이 작음 → 물이 이김 ✓

| 재는 것 | 값 |
|---|---|
| **화소마다** 땅/물이 맞는가 (지면 화소 298,280) | **99.23%** (틀림 2,282 — 경계 반 칸) |
| 실루엣 위가 하늘인가 (하늘 화소 471,487) | 99.999% (틀림 6) |
| 물 맨위 / 땅 맨위 | 중앙 0.019° / 0.021° (읽기 해상도 0.059°/행) |
| 대조 ① 수평선 (손으로 푼 −0.0534°) | 실측 −0.0894° · 방위 흔들림 0.116° |
| 대조 ② 한 광선에서 2회 이상 땅↔물 | 참조 986열 = **측정 986열** |
| 해안 구조가 방위를 따라 바뀌는 횟수 | 101회 (12° 마스크는 한 바퀴에 30칸) |

⚠ 관측점을 1·2단계와 **다른 곳**으로 옮겼습니다. 같은 점(37.25, 126.58)은
고도 42m 에 사방이 더 높아 **어느 방위로도 물이 안 보입니다** (1km 앞 지면이
45.2m 로 눈보다 1.6m 높아 그 너머를 다 가립니다). 물을 대상이 없으면 판정이
헛돕니다. DEM 을 훑어 고도 1~30m 이면서 바다와 뭍이 같이 보이는 점을 골랐고,
그 자리에서 72방위 중 47방위가 한 광선에서 2회 이상 땅↔물을 오갑니다.

**판정이 잡은 결함 셋:**

1. **발밑 각도 구멍.** 지면 격자가 12m 부터 시작해서, 눈높이 2.77m 기준
   −6.3° 아래로는 지면이 **아예 없었습니다.** 더 낮은 각까지 뻗는 해수면이
   그 구멍을 메워 물가에 선 관측자가 물을 밟고 선 것처럼 그려졌습니다.
   격자를 0.6m 부터 시작하는 **두 구간**(발밑 24고리 + 바깥 128고리)으로
   바꿨습니다. ⚠ 발밑 고리를 바깥에서 빼내면 안 됩니다 — 한 구간 로그
   간격으로 발밑까지 덮으려다 2단계 최대오차가 0.119° → 0.161° 로
   나빠졌습니다. 새로 덮는 구간이므로 고리를 **더합니다** (152개, 삼각형
   77,312).
2. **먼바다가 통째로 뭍으로 그려짐.** Terrarium 이 **먼바다를 정확히 0 으로
   자르는** 성질(조사 때 1024개 중 406개가 정확히 0) 때문에 지면 메시가
   해수면과 같은 높이에 면을 깔고 깊이 동률에서 이겼습니다. 해수면 아래를
   그리지 않도록(`discard`) 고쳤습니다 — 거기서 보이는 것은 땅이 아니라
   물입니다. 맨 위 물이 −0.481° → −0.089° (이론 −0.053°).
   알려진 한계: 고도가 정확히 0m 인 **간척지·갯벌**도 물로 읽힙니다.
3. **판정 자신의 결함.** 참조의 "하늘 시작점"으로 경계 목록의 마지막 항목을
   썼는데 그건 마지막 **종류 변화**이지 맨 위가 아닙니다. 하늘 일치율이 0.77 로
   나왔고 렌더가 아니라 측정이 틀린 것이었습니다. 0.99999 로 고쳤습니다.

**전환 수를 문턱으로 쓰지 않습니다.** 참조는 고리 표본 사이의 화소보다 얇은
조각까지 셉니다(참조 11회 대 측정 4회). 못 그리는 것을 세는 것은 불공정하므로
문턱은 **화소 단위 일치율**로 잡고, 전환은 "그런 구조가 나오는가"로만 씁니다.

## 5. 값과 위험

- **자료량**: z13 타일 하나 26~40KB, 3×3 이면 약 300KB (실측). 반경이
  늘면 줌이 내려가 장수는 그대로입니다.
  타일은 정적 S3 라 캐시가 잘 듣습니다. (SLA 는 없습니다 — 실패하면 지금
  방식으로 물러나는 길을 남겨야 합니다.)
- **삼각형 수**: 동심원 격자 128×256 이면 약 6.5만 삼각형. 모바일에서
  버텍스 변위만 하는 정적 메시라 감당할 만하지만 **실측이 필요합니다.**
- **가장 큰 위험**: 눈높이를 바꾸면 지금 화면 전체의 구도가 바뀝니다.
  능선 띠·나침반·천체 궤적이 전부 지금 기하에 맞춰져 있습니다. 3단계를
  독립적으로 재고 넘어가야 합니다.
- **바다 수심의 한계**: 이 자료는 먼바다를 대체로 0 으로 둡니다(실측: 표본
  1024개 중 정확히 0 이 406개). 근해 수심은 −1~−3m 로 살아 있으므로 물가
  표현에는 충분하지만, 먼바다 색을 수심으로 만들려 하면 안 됩니다 —
  거기는 지금처럼 거리로 두는 것이 맞습니다.

### 5단계 결과 (`verify-shore.js` — 21개 단언)

땅색은 조도 × 알베도 위에 **경사 · 조간대 · 공기원근**을 얹었습니다. 물빛은
**수심 하나**에서 흡수·바닥비침·포말이 전부 따라옵니다.

| 재는 것 | 값 |
|---|---|
| 얕은 물(<0.5m) 대 0.5~1m | **1.160배** (얕을수록 밝음) |
| 같은 수심에서 거리로 묶으면 | **0.27%** 변동 (수심 응답 16.0%) |
| 경사 대 땅색 색조 상관 | **0.793** (뒤섞은 경사 귀무 0.006) |
| 조간대 대 마른 땅 밝기 | **0.746배** |
| 공기원근 (600~1500m) | 맑은 날 7.5/255 · 뿌연 날(β 0.5) 21.2/255 |
| 대조 ⓪ 등록 (실루엣) | 최대 차 **0px** |

**판정이 잡은 결함 넷:**

1. **`slope = 1 − n.y` 는 기울기가 아닙니다.** 흔한 축약인데 작은 각에서
   θ²/2 라, 기울기 0.21(12°) 사면도 0.022 밖에 안 됩니다. 기울기 기준 문턱
   (0.10~0.50)에 넣었더니 **경사 항이 통째로 죽어** 화소 11,366개의 색조가
   **0.5918 하나로 고정**됐습니다. 땅이 판지처럼 보이던 원인이 이것입니다.
   `tanθ = sqrt(1−n.y²)/n.y` 로 고친 뒤 상관 0.79, 색조 폭 0.59~0.73.
2. **Terrarium 의 0 을 0m 수심으로 믿음.** 먼바다가 정확히 0 으로 잘려 있어,
   그걸 0m 로 읽으면 바닥이 다 비치고 포말이 1 이 되어 **만 전체가 밝은
   모래펄**이 됩니다. "모르는 곳은 깊다"로 고쳤습니다. 4단계와 같은 함정이
   다른 자리에서 또 나왔습니다.
3. **표시 하한(minGlow)이 음영을 통째로 먹습니다.** 조도가 낮으면 지면이
   `atm_display_ground` 의 최소 밝기에 눌려 경사도 젖은 모래도 전부 같은 색이
   됩니다 (젖음 54.26 대 마름 57.21 — 사실상 같음). 현실적인 낮 조도에서는
   90.94 대 121.93 으로 갈립니다. **어두운 장면에서는 땅의 음영이 원리적으로
   안 보인다**는 뜻이라 기억해 둘 값입니다.
4. **판정 자신의 상하 반전.** `readRenderTargetPixels` 는 아래에서 위로 오는데
   접근자를 뒤집어, 위아래가 뒤집힌 그림과 견주고 있었습니다. 증상은 "가장
   얕은 물이 가장 어둡다". 그래서 대조 ⓪(실루엣 등록)을 넣었습니다.

**버린 지표.** "포말 폭"을 화면 밝기 문턱으로 재려다 두 번 실패했습니다 —
화소로 재면 거리가 1/d² 로 섞여 상관이 **반대 부호**(+0.40)로 나왔고,
미터로 고쳐도 문턱이 고르는 등수심선이 제멋대로라 0 이 됐습니다. 문턱을
쓰지 않는 쪽으로 바꿨습니다: 수심으로 묶으면 크게 변하고 **거리로 묶으면
안 변한다**는 대비가 판정입니다.

### 남은 것 두 가지

- **갯벌에서 포말 띠가 너무 넓습니다.** `수심 < 0.5m` 을 포말로 삼는데,
  이 자리는 갯벌이라 그 구간이 **448m** 입니다. 화면에서 흰 띠가 지나치게
  넓게 보입니다. 물리적으로 파도는 `수심 < 약 1.3 × 파고` 에서 부서지고
  그 뒤로 거품이 **흩어집니다.** 앱에는 풍속이 있으니 파고를 구할 수
  있습니다 — 상수를 줄여 눈속임할 것이 아니라 **부서지는 띠**로 모형을
  바꾸는 것이 맞습니다.
- **깊은 물빛은 여기서 확인 못 했습니다.** 이 관측점은 보이는 물이 전부
  수심 1m 미만이라, 흡수 `exp(−k·2d)` 로 청록이 남는 것을 가릴 표본이
  없습니다.
