# 박명 곡선 (Twilight)

"해가 지고 난 직후에 지나치게 빨리 어두워진다"를 고친 기록입니다.

---

## 1. 증상과 진단

`skyRadiance`의 지평선 글로우를 태양 고도별로 재봤습니다.

| 태양 고도 | 지평선 글로우 | 직전 대비 |
|---|---|---|
| 0° | 0.3959 | — |
| **-1°** | **0.0778** | **0.196배** |
| -2° | 0.0550 | 0.707배 |
| -3° | 0.0385 | 0.700배 |
| -4° | 0.0267 | 0.692배 |
| -6° | 0.0127 | 0.476배 |

**지평선을 넘는 1도에서 5.1배가 빠집니다.** 그 뒤로는 도당 0.7배로 완만합니다.
절벽 하나 뒤에 평지 — 실제 박명(완만하게 시작해 점점 가팔라짐)과 **정확히
반대 모양**입니다. 태양은 분당 약 0.25° 내려가므로, 사용자가 느낀
"직후에 확 어두워짐"은 이 4분 구간입니다.

### 원인

두 줄이 겹쳐 있었습니다.

```ts
const sunAltForT = Math.max(sunAltDeg, TRANSMITTANCE_MIN_SUN_ALT); // = -1.0
const mSun = airMass(sunAltForT) * Math.exp(-hFrac);
```

Kasten-Young 대기질량은 **지표 관측자용** 식이라 0° 부근에서 폭발합니다 —
`airMass(0) = 37.9`, `airMass(-1) = 55.8`. 하한이 -1이면 이 구간이 살아 있어
`tSun = exp(-τ·mSun)`이 무너집니다. -1° 아래로는 하한에 걸려 얼어붙고,
그래서 그 뒤가 평평해집니다.

애초에 **해가 진 뒤 하늘을 밝히는 빛은 지표 대기를 통과하지 않습니다.**
관측자보다 위로 들어와 고층을 접선으로 스치는 경로입니다. 지표 대기질량 식을
지평선 아래로 외삽하는 것 자체가 무의미합니다.

두 번째 줄은 임의 램프였습니다.

```ts
const twilight = clamp01((sunAltDeg + 16) / 16);
const sunLit = sunAltDeg >= 0 ? 1 : Math.pow(twilight, 2.2);
```

고도에 선형인 값을 2.2제곱한 것으로, 물리적 근거가 없습니다.

## 2. 고친 방법

### 2-A. 투과율 하한을 0으로

`TRANSMITTANCE_MIN_SUN_ALT: -1.0 → 0.0`. 일몰 순간의 색·투과 기하를 그대로
얼리고, 지평선 아래의 어두워짐은 **전부** 아래 항이 담당하게 합니다.
0° 이상은 아무것도 바뀌지 않으므로 **낮 렌더는 완전히 불변**입니다.

### 2-B. 지구 그림자 높이

해가 지면 지구 그림자가 대기를 아래에서 위로 쓸고 올라갑니다.
관측자 접선 방향으로 나아간 빛이 지구를 스치는 높이는 `R(sec δ − 1)`:

| 복각 δ | 그림자 높이 |
|---|---|
| 1° | 0.97 km |
| 2° | 3.9 km |
| 4° | 15.6 km |
| 6° | 34.9 km |

6°(시민박명 끝)에서 이미 산란 대기 대부분을 지나갑니다 — 관측과 맞습니다.

남은 산란 질량은 척도고도 H로 `exp(-h/H)`. 이것이 `earthShadowLit`입니다.

### 2-C. 단일산란과 다중산란에 **다르게** 적용

처음에는 스칼라 하나를 전체에 곱했습니다. 그랬더니 렌더가 이렇게 나왔습니다:

| 태양 고도 | -4° | -6° | -8° |
|---|---|---|---|
| 화면 밝기 | 23/255 | 2.7/255 | 0 |

**일몰 절벽을 고치고 그 절벽을 5도 뒤로 옮긴 것**뿐이었습니다.
수치 검증만 봤으면 통과했을 것이고, 렌더해서 봤기 때문에 잡혔습니다.

원인은 물리입니다. 단일산란은 시선 기둥이 **직접** 햇빛을 받아야 생기므로
그림자가 그 기둥을 덮으면 사라집니다. 반면 다중산란으로 들어오는 빛은 아직
햇빛을 받는 **먼 상층 대기**에서 여러 번 튕겨 옵니다 — 내 머리 위가 그늘에
들어갔다고 사라지지 않습니다. 이것이 박명의 긴 꼬리입니다.

```ts
out.push((single * sunLit + multi * sunLitMS) * SKY_EXPOSURE);
```

파일이 이미 `mSun` / `mSunMS`를 같은 이유로 나눠 두고 있었습니다.
같은 구분을 그림자 항에도 적용한 것입니다.

## 3. 다중산란 척도고도를 정한 근거

자유 파라미터는 `TWILIGHT_MS_SCALE_HEIGHT_KM` 하나입니다.
렌더한 화면 밝기(서쪽 지평선 띠)를 **수정 전으로 나눈 값**:

| H_MS | -1° | -2° | -4° | -6° | -8° | 천정 0°→-6° |
|---|---|---|---|---|---|---|
| (꼬리 없음) | — | — | — | — | ~0 | 43.7배 |
| 22 | 2.15x | 2.23x | 2.37x | **0.77x** | **0.02x** | 20.9배 |
| 30 | 2.17x | 2.28x | 2.69x | 1.11x | 0.48x | 14.6배 |
| 34 | 2.18x | 2.30x | 2.79x | 1.42x | 0.65x | — |
| **42** | 2.20x | 2.32x | 2.95x | 2.38x | 0.94x | 10.8배 |

실측 천정휘도 감소(0°→-6°)는 약 40배이므로 **22가 측광비에는 더 가깝습니다.**
그런데 22를 쓰면 -6°/-8°가 **지금 배포된 앱보다 어두워집니다.**

사용자가 재보지도 않을 측광비를 맞추려고 이미 나가 있는 화면을 퇴화시키는 것은
잘못된 거래입니다. **어느 고도에서도 회귀가 없는 최소값 42**를 택했습니다.

### 알려진 한계

그래서 늦은 박명의 **천정**이 실제보다 밝게 남습니다 (10.8배 vs 실측 40배).

근본 원인은 `sunLitMS`가 스칼라라는 것입니다. 실제로는 시선 방향마다 그림자에
들어가는 시점이 다릅니다 — 천정 기둥은 일찍 그늘에 들어가고, 태양 쪽 지평선을
따라가는 경로는 훨씬 오래 빛을 받습니다. **시선 의존으로 만들면 두 관측을
동시에 만족시킬 수 있습니다.** 기기에서 확인한 뒤 손대는 것이 맞다고 봅니다.
